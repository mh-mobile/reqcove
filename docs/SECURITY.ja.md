# Reqcove のセキュリティモデル

[English](SECURITY.md)

Reqcove はスマートフォンの HTTPS を復号し、読んだものを AI エージェントに渡します。このページでは、Reqcove が何を守り、何を信頼し、何をしようとしていないかを説明します。テストではなくコードを読んで書いた点には、その旨を書いています。対象は v0.8 です。

## 信頼

- **あなたの OS ユーザーを信頼します**。状態ディレクトリ（`~/.reqcove`、モード 0700）と、その中の MCP ソケットは、そのユーザーにだけ開かれています。そのユーザーとして動くプロセスはどれも、記録と CA の秘密鍵を読めます。Reqcove は、それより強いことは何も約束しません。
- **指定したデバイスは、Exit Node を使うことについてだけ信頼します**。tailnet のほかのデバイスからの通信は、Exit Node でも Remote Proxy でも拒否します。デバイス名は各デバイスが自分で名乗るものなので、`--device` がデバイス名を受け付けるのは、あなた自身のユーザーのデバイスからだけで、そのデバイスにも Reqcove のノードにもタグが付いていない間だけです（タグ付きのノードは、タグを付けた人のユーザー ID を持ち続けます）。ほかのデバイスは、マシン名、IP、StableID で指定してください。
- **LAN モード（`--lan`）では、許可したアドレスを、プロキシを使うことについて信頼します**。パスワードはありません。信頼するのはアドレスで、デバイスではありません（[下記](#lan-モード--lan)）。

## コンテナで動かす場合

（docs/container.ja.md）サイトが送ってきたものを開く mitmproxy は、コンテナの中で動きます。そこに欠陥があっても、届くのはコンテナ（記録と、volume にある CA の鍵）までで、ユーザーのほかのファイルには届きません。イメージにはシェルもパッケージ管理もなく、root ではない専用のユーザーで動きます。その代わり、Docker デーモンのソケットを使える人は、CA の鍵を含めて volume を読めます。また、コンテナにターミナルを付けたとき（`docker run -t`）は、コンテナを削除するまで、`docker logs` にログイン用の URL、`--ui`/`--web` のリンク、`--mcp-http` のトークンが残ります（付けなければ、`run` はそれらの代わりに `reqcove links` の名前を出します）。`reqcove mcp` は `--log-driver none` で動かすので、ツールの答えはログに残りません。`scripts/container-smoke.sh` で確かめました（状態ディレクトリの持ち主とモード。ネットワークは不要）。攻撃で確かめたものではありません。

## CA の秘密鍵

`~/.reqcove/mitmproxy/mitmproxy-ca.pem` と、その隣の `mitmproxy-ca.p12`（パスフレーズのない PKCS#12 ファイル）には、あなたの iPhone が信頼する CA の秘密鍵が入っています。これを持つ人は、その iPhone に対して任意の HTTPS サイトになりすませます。このディレクトリは自分だけのものにしておいてください。Reqcove を使うのをやめるときは、先に iPhone からプロファイルを削除し、それからディレクトリを削除します（`reqcove cleanup` が手順を表示します）。ディレクトリを別のコンピュータにコピーすると、鍵もコピーされます。

CA のない `--state` のディレクトリは、起動時に `~/.reqcove` の CA のコピーを受け取ります（1 台のコンピュータで複数の Exit Node、iPhone のプロファイルは 1 つ）。コピーするのは、鍵の入った `mitmproxy-ca.pem` と証明書のファイルです。`mitmproxy-ca.p12` と mitmweb のパスワードはコピーしません。`run` はコピーした先をログに出します。また、どのコマンドも `~` で始まる `--state` を断ります（`--state=~/x` はシェルがそのまま渡すので、鍵が `./~/x` に置かれ、`cleanup` は本物のディレクトリがなくなったと言ってしまいます）。こうして鍵は、そうしたディレクトリのそれぞれに入ります。ディレクトリはどれも 0700 で、ファイルは 0600 です（テスト）。1 つを削除しても、鍵はほかのディレクトリに残ります。すべてを止めるのは、iPhone からプロファイルを削除することです。`~/.reqcove/ca-copies` にコピーの一覧があり、`~/.reqcove` の `cleanup` は、まだ CA を持っているものを挙げます。コピーの `cleanup` は、そのプロファイルが両方に使われていると伝えます。したがって、上の「ディレクトリを削除する」は、それぞれのディレクトリを削除するという意味です。

## 記録するもの

- 記録するのは、`--allow-hosts` にある（そして `--pass-hosts` にない）ホストへのリクエストだけです。2 つの確認でこれを守ります。mitmproxy はほかの接続を復号せずに通し、さらにリクエストごとに Host を確認し直します。許可したホストへの接続は、ほかのホストへのリクエストを運ぶことがあります（HTTP/2 の接続の再利用）。それらは接続と一緒に復号され、記録はされませんが、`--web` には表示され、`--upstream-proxy` に転送されることがあります。一覧にないホストへのリクエストと TLS の失敗は数えるだけで、決して記録しません。
- Apple のホストへの接続は、常に復号せずに通します。
- `--pass-hosts` のホスト（許可したホストのうち、アプリが Reqcove の証明書を拒否するもの）も復号せずに通し、その接続だけを記録します。記録するのは、クライアントが名指ししたホスト（SNI）、サーバーのアドレス、開始と終了、それぞれの向きのバイト数、提示されたプロトコルです。TLS の中のものは何も保持せず、見もしません。記録はもう一度 --allow-hosts と照合するので、そこにないホストは何も残しません。別のホストの復号された接続に相乗りした pass host へのリクエスト（HTTP/2）も記録しません。バイト数は接続全体のものです。相乗りした別のホストのリクエストも、見えないままその数に入ります（コードを読んだもの）。`reqcove status` が `--pass-hosts` 用に提案するホストは、スマートフォンの TLS（SNI。アプリが自由に選べます）から来ます。提案するのはホスト名と IPv4 アドレスだけで（ホストを名指ししないクライアントは、宛先で通します）、mitm.it は決して提案せず、コマンドはシェル向けに引用符でくくります（テスト）。`@FILE` のリストはホストとして読むだけで、決して実行しません。ホストでない行があると `run` は止まり、その行は行番号だけで示します。間違ったファイル（たとえば .env）の中身を表示し返さないためです（テスト）。pass host の TLS 接続は、`--rules` と `--upstream-proxy` を通らずに、サーバーへ直接向かいます。pass host の平文の HTTP と、別のホストの復号された接続に相乗りしたリクエストは、それでも復号されます。範囲外として数え、記録はせず、`--upstream-proxy` があればそこを通して送ります（テスト）。そのときの検証は、プロキシを通るすべての HTTPS と同じです。`--upstream-ca` だけで検証し、指定がなければ公開の CA で検証します。これらは `--rules` を通りません（コードを読んだもの）。Apple のリストにある pass host は、mitmproxy 自身が通すので記録を残しません（テスト）。`run` が警告します。
- Reqcove が見分けられるシークレットは、届いた時点でマスクするので、どのツールも返せません。ヘッダー、クエリパラメータ、ボディのフィールドは、名前でシークレットと判断します。名前に token、secret、password、passwd、passphrase、passcode、credential、signature、session、jwt、apikey、privatekey、authorization、authentication、csrf、xsrf、ticket（WebSocket の `wsTicket` が、マスクされないまま見つかりました）、dpop のどれかを含むもの（`accesstoken`、`X-AuthToken` のようにつなげて書いたものも）と、auth、key、sid、sig、sign（アプリのリクエスト署名用のヘッダー `sign` が、マスクされないまま見つかりました）、pwd、pw、pass、otp、totp、pin、code のどれかを 1 つの単語として持つものです（名前は記号と、大文字・小文字の切り替わりで区切るので、`apiKey`、`XAuth`、`X-Amz-Signature` は当たり、`author` と `keyword` は当たりません）。日常の単語の隣にある `code` と `key`（`country_code`、`error_code`、`sort_key`）、`token_type`、`ticket_id`、`ticketNumber`、CORS の `Access-Control-Allow-Credentials`（値は `true` にしかなりません。実際の利用で、マスクされているのが見つかりました）はシークレットではありません。ボディの `"key"` で、値がドット区切りの小文字の名前であるものも同じです。OpenTelemetry が属性をそう書きます（`{"key": "service.name", …}`。実際の利用で、マスクされているのが見つかりました）。そこに入る鍵は、大文字と小文字が混じっているか、ドットがありません。JWT と下に挙げるほかの形は、フィールドが何であってもマスクします。URL の `key=` はシークレットのままです。Cookie の値はマスクし（名前は残します）、クエリパラメータは URL が現れるところならどこでもマスクします（`Referer`、`Location`、`Link` などのどのヘッダーでも。`#/callback?access_token=` のようなフラグメント。別のパラメータの中の URL。ボディ。エラーメッセージ）。URL のパスワード（`https://user:…@host`）と、レスポンスの理由の文（reason）も同じです。mitmproxy がエラーメッセージに引用する生のバイト列（`b'…'`）は、全体をマスクします。`--no-redact` でこれをオフにできます。
- ボディも、見分けられる範囲で、届いた時点でマスクします。JSON では（Content-Type が何と言っていても）、同じ規則で名前がシークレットとなるフィールドの、文字列と数値の値をマスクします。JSON の中に文字列として入った JSON や、フォームのフィールドとして送られた JSON でも同じです（1 段まで）。レスポンスでは、単独の `code` は残します。たいていエラーコードだからです（`verification_code` と `device_code` はマスクします）。リクエストではマスクします。ワンタイムコードや OAuth のコードを運ぶからです。フォーム（またはフォームに見えるボディ）では、そうしたフィールドの値をマスクし、単独の `code` も含みます。ヘッダーの値、URL、ボディ、エラーメッセージのどこにあっても、形で見分けられる認証情報はマスクします。認証情報に見える `Bearer`/`Basic`/`Token` の値（文の次の単語ではないもの）、JWT、よく知られた接頭辞を持つキー（GitHub、`sk-…`、Slack、AWS のアクセスキー ID、Google の API キー）で、パーセントエンコードの奥にあるものも含みます（フォームのフィールドや URL パラメータにエンコードされた JSON、`Bearer+…`）。`WWW-Authenticate` はチャレンジ（スキーム、realm、error）を残し、そうした形だけをマスクします。GraphQL の文書ではないテキストのボディや、JSON の文字列の中の `name: value` という行で、名前がシークレットのもの（STOMP フレームの `passcode:`。SockJS の JSON の中のものも。YAML のマッピング。ボディに書き込まれたヘッダー）は、行の残りをマスクします。YAML のリストの項目（`- password: …`）と引用符付きの名前は見ません。シークレットを含む JSON オブジェクトの base64 を持つ URL パラメータやフォームのフィールド（AppSync の `?header=`）は全体をマスクします。`Sec-WebSocket-Protocol` で運ばれる認証情報も同じです（`access_token` のような名前のあと、AppSync の `header-` の base64 の JSON として、Kubernetes の bearer の接頭辞のあと、または、ドット区切りの名前ではない、認証情報の形をした長い値）。（テスト。）名前がシークレットのフィールドで、値がリストやオブジェクトのものは、全体をマスクします（`{"password": "[redacted]"}`）。GraphQL の文書は字句解析器（lexer）で読みます。引数、入力オブジェクトのフィールド、変数のデフォルト値のうち、名前がそうしたものは、JSON のフィールドと同じく、値全体をマスクします（`login(password: "[redacted]", pin: "[redacted]")`：文字列、数値、リスト、オブジェクト）。enum と真偽値の値、`$variables`、エイリアスは残します。文書は、文書らしく始まるところで見つけます。トップレベルの JSON の文字列か、文字列の中の JSON にあるもの（どのキーの下でも。リクエストでも、それをそのまま返すレスポンスでも）、ボディ、URL パラメータ（GET の `?query=`。マスクしてからエスケープし直します）です。文書らしく始まるのに読めないものは、全体をマスクします。ただし、スクリプトのオブジェクトのように始まるもの（`{a: b, …}`。最初の値のあとにカンマ）は、そのまま残します。（テストとファズテスト。）パラメータの中の URL は、2 重や 3 重にエンコードされていても中を見ます。ボディは 64 KiB まで、メモリにだけ保持します。マスクは、途中で切れているかもしれない先頭部分に対して働きます。閉じる引用符の前で切れた値もマスクします（これらの形を対象に、どこで切っても確かめるファズテスト。2 重にエンコードされた URL と、バックスラッシュのあとで切れた GraphQL の値を見つけ、どちらも直しました）。
- あなた自身の規則（起動時に固定）：`--mask-names` は、名前が意味を持つところすべてで、シークレットとして扱う名前を足します。名前全体が一致したときだけです（表記は問いません。`clientRef` は `client_ref` と `Client-Ref` に当たり、`X-Client-Ref` には当たりません）。組み込みの例外（OpenTelemetry の `key`、チャレンジとして残す `WWW-Authenticate`、Cookie の属性）より先に効きます（テスト）。`--mask-values` は RE2 のパターンを足し、一致した部分を、どこに現れてもマスクします（どんな名前のヘッダーでも。User-Agent の `key=…` もその 1 つです。URL、ボディ、エラーの文）。パターンは 512 バイトまでのものを 32 個までで、空の文字列に一致するものは使えません。エラーはパターンを番号で示し、その中身は決して出しません。`capture_stats` は、名前ごと、パターンの番号ごとに一致の数を数えます（1 つの値を 2 回以上数えることがあります）。（テスト。）コマンドラインに書いたパターンは `ps` に出るので、シークレットそのものを書くなら `@FILE` に入れ、`+`、`/`、`.` がその文字自身に一致するよう `\Q…\E` と書きます。どちらも `--no-redact` のときは何もしません（`run` が警告します）。
- **これで見つけられないもの**：そうとは分からない名前の下にあるシークレット（`{"data": "…"}`。`--mask-names` や `--mask-values` で足せます）と、JSON、フォーム、テキスト以外の形式の中のシークレット（`multipart/mixed`。protobuf、`multipart/form-data`、XML は下のとおりに読みます）。XML は名前だけでマスクします。ほかの名前の要素や属性にあるシークレットは通ります。シークレットの要素の外でトークンに分けられないもの（XML 1.1 の宣言、`1 < 2`、不正なコメントや名前）には、テキストのマスクだけがかかります。ただし、デコーダーが拒否する開始タグ（`a=b!c`、引用符のない値）は、それでも開始タグとして、その名前と属性で読みます。DTD の中のもの（`<!ENTITY p "…">`）と、シークレットの要素の外のコメントは、名前ではマスクしません。要素の中にテキストとして入った XML（エスケープされたもの（`&lt;Password&gt;`）や、シークレットの要素の外の CDATA に入ったもの）は、XML として読みません（テスト）。WebSocket のメッセージには Content-Type がないので、`<?xml` で始まるときだけ XML として読みます（XMPP の `<auth mechanism='PLAIN'>…</auth>` は通ります：テスト）。宣言されたエンコーディングは使いません。有効な UTF-8 でない先頭部分（ASCII の外の文字を含む Latin-1 や Shift_JIS、UTF-16）は、そうしたボディがどれもそうであるようにマスクせず、そのため渡しもせず、検索の対象にもしません（テスト）。SAML の POST バインディングは、アサーションを base64 の `SAMLResponse` というフォームのフィールドで送ります。これはデコードしないので通ります（テスト）。GraphQL でも同じです。何でもない名前の下にあるシークレットは通ります。そのため id は読めるままで、`diff_flows` で比べられます（OpenTelemetry や Apollo など、GraphQL を解析するツールは、その代わりに、クエリに書かれた値をすべて落とします）。また、前に文章があって、メッセージの途中に引用された文書は見つけられません。GraphQL の変数として送られた値は JSON のフィールドなので、名前でマスクします。メールアドレスや名前などの個人データはマスクしません。デバッグに必要だからです。ボディを渡し、検索の対象にするのは、マスクが中を見られたものだけです。デコードされていて（元に戻せなかったエンコーディングの、通信上のバイト列ではなく）、かつテキストであるものです。テキストかどうかは Content-Type で判断します（JSON、XML、フォーム、テキスト、…。`application/x-amz-json-1.1` のように `json` を名前に含むほかの型と、Sentry の envelope は、制御文字がないときだけ）。Content-Type がなければ、バイト列で判断します。それ以外は、たまたま有効な UTF-8 である protobuf も含めて、マスクが有効な間は渡さず、検索の対象にもしません。`--no-redact` のときは返します。protobuf（Content-Type で判断するか、gRPC のフレームの中のもの）は例外です。reqcove は、バイト列の代わりに、自分で書き起こしたものを渡します（`view` がその印です）。最後まで protobuf として読めないボディは何も出しません。印字できるテキストも、全体が文字列とサブメッセージだけとして読める場合を除いて、何も出しません（印字できる長さの文字列フィールド 1 つは、印字できるテキストです）。終わりの前で切れた先頭部分は、読めた分に文字列か完全なサブメッセージがあったときだけ、読めた分を出します。スキーマがないときは構造だけです。フィールドの番号、ワイヤタイプ、長さ、文字列はその長さだけで中身は決して出さず、レスポンスでは数値を出します。リクエストでは 1 バイトの数値だけ（0 から 127。enum や真偽値ですが、そのくらい小さい PIN や CVV も）を出し、それより大きいものはバイト数として出します。単独の `code` をリクエストでマスクするのと同じです。印字できるテキストの並びは常に文字列として扱い、メッセージとしては決して読みません。メッセージとして読むと、そのバイトが数値として出てしまうからです。ランダムなバイト列（`bytes` のフィールド）は、それでもメッセージとして読めることがあります。そのとき、レスポンスでは、たいていそのバイトがすべて数値として出ます（16 バイトの値ではおよそ 100 個に 1 個が全体として、32 バイトの値では 1,000 個に 1 個）。リクエストでは、その一部が出ます（フィールドの番号と 1 バイトの数値）。長さは出ます（パスワードの長さ）。`--proto FILE`（コンパイルしたスキーマ）を付けると、型がわかるメッセージ（パスから決まる gRPC、Connect、Twirp のメソッド、または Content-Type の `messageType`）は、フィールドの名前（proto の名前で、`json_name` は決して使いません）付きの JSON として読み、JSON と同じく名前でマスクします。`bytes` は長さを出し、スキーマにないフィールドは構造を出します。古いスキーマや間違ったスキーマは、トークンに何でもない名前を付けることがあり、それは通ります。組み込みのリストがシークレットと数えない名前の下にある値も、JSON と同じく通ります（ヘッダーのマップの `cookie` の項目、`cvv`）。（テスト。ファズテストは、スキーマなしの読み方を対象にしています。上の `protoc` コマンドは、protoc 33.0 で 1 回実行しました。）
- `multipart/form-data`（アップロード）：reqcove が書き起こしたもの（`view`）として、パートごとに渡します。名前がシークレットのパート（リクエストでは単独の `code` も）は全体をマスクし、名前がシークレットのパートヘッダーも同じです。テキストのパート（ファイル名がなく、テキストか JSON の型）は、ボディと同じようにマスクします。ファイルのパート、テキストでないかエンコードされたパート（`Content-Transfer-Encoding: base64`）、`Content-Disposition` が読めない（または 2 回ある）パートは、ヘッダーと大きさだけを残し、バイト列は決して出しません。行が LF だけのボディは、パートを 1 つも出しません。プリアンブルとエピローグは出しません。読むのは 256 パートまでです。（テストと、Go の multipart writer を使った E2E テスト。）
- XML（`text/xml`、`application/xml`、SOAP の `application/soap+xml` のような `application/*+xml`、または `<?xml` で始まるボディ）は、トークンごとに読みます。ローカル名（`wsse:Password` なら `Password`）が上の規則（JSON と同じ規則）でシークレットとなる要素は、内容全体をマスクします（テキスト、CDATA、子要素、コメント：`<wsse:Password>[redacted]</wsse:Password>`）。マスクは、同じローカル名の終了タグまで続きます（中に紛れた `</i>` では終わりません）。ローカル名がシークレットの属性は、値をマスクします。名前空間の宣言は残します。それ以外は、届いたまま、1 バイトも変えません（接頭辞、実体参照、空白）。SAML の `Assertion` と `EncryptedAssertion` は全体をマスクします。これは bearer の認証情報で（持っている人は、期限が切れるまで提示できます）、そのため subject と属性も出ません。Apple の plist では、`<dict>` の中で、テキストがシークレットの `<key>` のあとの値をマスクします（`<key>access_token</key><string>[redacted]</string>`）。JSON の `key` と同じく、`Key` という名前の要素はマスクします。S3 のオブジェクト名もその 1 つです。シークレットの要素や属性値の中で、先頭部分が切れているか、トークンに分けられないときは、その終わりまでマスクします。それ以外の場所では、そこを越えて（不正なコメントなら `-->` のあとから）読み続けます。かかる時間には上限があります（テスト）。DTD は読みません。実体は展開せず、取得もしません（billion laughs のテスト）。上のテキストのマスクは、この上に重ねてかかります。XML のマスクは、テキストのマスクが手がかりにするもの（マスクした要素の中の引用符）を取り去ることがあります。そのため、テキストのマスクだけならマスクするものを、すべてマスクするかどうかは確かめていません。マークアップのファズテストは、決して失敗しないことと、どのマークアップよりも前にあるシークレットの要素と属性がマスクされたままであることを確かめます。（テスト、ファズテスト、mitmproxy を通した SOAP リクエストの E2E テスト。）
- gRPC：レスポンスのトレーラーは、ヘッダーと同じようにマスクします。`-bin` で終わるメタデータ（バイナリ）は、大きさだけを残します。`grpc-message` はデコードしてからマスクし、1 KiB に切ります。マスクはほかのヘッダーの値と同じです（形と URL で行うので、その中に自由な文で書かれた `password=…` は見つけられません）。フレームに入った JSON のメッセージは、JSON としてマスクします。protobuf のメッセージは、上のとおりに書き起こします。gRPC の型なのにフレームになっていないボディは、ボディとしてマスクします。（テストと、HTTP/2 での E2E テスト。）
- WebSocket のメッセージ：テキストのメッセージは、先頭の 4 KiB を、ボディと同じく届いた時点でマスクします（クライアントのものにはリクエストの規則を使い、単独の `code` も含みます）。残すのは、マスクが読めたものだけです（制御文字のないテキスト。ただし、STOMP フレームを閉じる NUL と、SignalR が JSON オブジェクトの間に置く 0x1e は別です）。クライアントからのものでは、メッセージにしかない形もマスクします。トークンの形をした 1 語だけのメッセージ（そのまま、または 1 つの JSON の文字列として）、イベントの配列で認証のイベント名のあとにある文字列（socket.io の `42["authenticate","…"]`。名前空間や ack の id が付いていても）、ターゲットがそうした名前である SignalR の呼び出しの引数です（SignalR のレコードは 1 つずつ読みます。読むのは最初の `target` だけで、socket.io のものと同じく、引数のより深いところに入れ子になった文字列は読みません）。バイナリのメッセージと、1 つのソケットで毎秒およそ 20 件を超えた分は、大きさだけを残します。ソケットごとに、最初の 5 件と新しい 100 件を残します。渡すのは `list_ws_messages`（と `reqcove har`）だけです。close の理由は、エラーの文と同じようにマスクします。（テストと、本物のソケットを使った E2E テスト。）見つけられないもの：ほかの方法で、位置で送られる認証情報（そうしたイベント名のない配列、独自のバイナリのフレーム）。ボディと同じです。
- ボディを返すのは、ツールがそれを求められたとき（`get_flow` と `search_flows` の `bodies`）と、ボディを比べる `diff_flows` だけです。`diff_flows` が返すのは、違っている値とキーで、300 バイトに切ります。テキストでないボディは、マスク中はまったく返しません。
- 記録はメモリにあります（フローは 10,000 件まで、ボディの先頭部分、ヘッダー、URL、そのほかのテキストは合わせて 64 MiB まで。サイトの理由の文、`Content-Encoding`、エラーメッセージは、それぞれ 1 KiB、64 バイト、1 KiB に切ります）。`reqcove run` が止まると消えます。reqcove 自身は、フローをディスクに書きません。`reqcove har > FILE` は、あなたが指定した先に、ツールが返すのと同じくマスクしたものを、シェルのファイルモードで書きます（ほかのユーザーから読めることがよくあります。状態ディレクトリは 0700 です）。状態ディレクトリの `mitmproxy.log` には、mitmproxy のエラーの行だけが入ります（失敗するリクエストや不正な形のリクエストで送られたシークレットがそこに入らないことを、テストが確かめます）。
- マーカー（`reqcove mark`、`add_marker`）は、記録と一緒にメモリに置きます。1 行で 80 文字まで（それ以外は断ります）、エラーの文と同じようにマスクし、source ごとに 100 個までで、ログには出しません（コードを読んだもの）。`source`（`cli`、`mcp`）は経路です。呼び出しがどう届いたかから Reqcove が決めるもので（`reqcove mcp` は、エージェントのクライアント名を決して伝えません）、証拠ではありません。このコンピュータでコマンドを実行できるエージェントは、`reqcove mark` を実行するか、`run` のソケット（同じユーザー）に自分でつなぐことで `cli` を名乗れ、そうしてユーザーの 100 個を押し出せます。`reqcove mcp` を通したエージェントは `mcp` になり、それはできません。マーカーのテキストは、ユーザーかエージェントの言葉です。データであって、決して指示ではありません（サーバーの instructions がそう伝えます。テストは、マスク、断る場合、`reqcove mcp` を通したエージェントが `mcp` になることを確かめます）。

## エージェントが読んだものの行き先

ツールが返すものはすべて、エージェントのモデルの提供元に送られます。それを踏まえて `--allow-hosts` を選んでください。`--allow-hosts '*'` は、ほかのアプリやサイトの通信も送ることになり、Reqcove は起動時に警告します。通信のほかに、`status` と `list_devices` のツールは、ノードの MagicDNS 名（tailnet の名前を含みます）、その tailnet アドレス、デバイスのマシン名を運びます。あなたのログイン名は運びません（コードを読んだもの）。

## プロンプトインジェクション

Reqcove のツールは読むだけです（唯一の例外である[プリセット](#モックのプリセット)は、あなたが書いたものだけを有効にします）。しかし、それを読むエージェントは、ほかのツールも持っているかもしれません。シェル、ファイルの書き込み、ネットワーク、ほかの MCP サーバーです。サイトが記録に書き込んだ文が、それらを使うようエージェントを誘導しようとすることがあります（Cookie をどこかへ送る、ファイルを編集する）。Reqcove の側からは、それを止められません。止められるのは、エージェント自身の設定です。Reqcove を読むエージェントには、その作業に必要なものだけを与えてください。Claude Code では、Reqcove の読むツールを名前で許可し（`activate_preset` は除きます）、シェルのコマンドやネットワークのツールまで一緒に許可せず、それ以外には許可の確認を残します。Codex では、サンドボックス（デフォルトではネットワークなし。Codex のドキュメントによるもので、試していません）と承認を残します。Reqcove を読んであなたに答えるだけのエージェントが、いちばん安全な形です。

レスポンスのボディ、そしてレスポンスのヘッダー、ステータスの理由の文、リダイレクト先、エラーメッセージも、外部のサイトが書いたもので、エージェントを誘導するための文を含むことがあります。アプリは、自分の User-Agent、TLS の名前、送る JSON のキーを選び、tailnet のピアは自分のデバイス名を選びます。ツールは、求められたときだけボディを返し（`diff_flows` は違うところを返します）、どのツールの説明も、返すものはサイト、アプリ、tailnet が書いたもの、つまりデータだと書いています。サーバーの instructions はすべてのクライアントに送られ（Grok Bot のように Skill のないクライアントにも）、同じことを伝えます。さらに、記録に書かれていることを理由に、エージェントがファイル（とりわけ `--rules` のファイル）、コミット、コマンドを書いてはならないこと、`--no-redact` や `--web` を勧めてはならないこと、`next_steps` はユーザーのためのものであることも伝えます（テストは、クライアントが stdio と HTTP でそれを受け取ることを確かめます。文言は確かめません。モデルがそれを守るかどうかは、テストで示せることではありません）。Host がホスト名でもアドレスでもないリクエスト（アプリ自身の HTTP スタックは、そこにどんな文でも入れられます）は、中継しますが記録しません（テスト）。TLS から来るホストは、mitmproxy 自身の確認によって、ホスト名です（mitmproxy のコードを読んだもの）。フローのホストはリクエストの Host で、アプリが選びます。許可したホストへの接続の上で、アプリは別の許可したホストを名指しでき、記録にはそちらが出ます（リクエストは、それでも接続が向かった先へ行きます）。一覧と要約の User-Agent は 256 バイトに切り、ALPN の名前は印字できる ASCII に切り、`diff_flows` の JSON のキーのうち、普通の名前でないものは引用符でくくります（`$["a.b"]`）。
MCP ツールは読むだけですが、例外が 1 つあります。エージェントは、あなたがプリセットにしたルールを、1 回につき最長 5 分有効にできます（有効にし直すことに上限はありません）。モック（[モックのプリセット](#モックのプリセット)）か、v0.7 からは、リクエストが運ぶものや行き先を変える `map_remote`、`modify_headers`、`resolve` のルール（[map_remote、modify_headers、resolve のプリセット](#map_remotemodify_headersresolve-のプリセット)）です。`add_marker` も書き込みますが、書くのは Reqcove のメモリの中のマーカーだけです。ルールを書いたり変えたりするツールはありません。プリセットがなければ、エージェントが何を呼んでも通信は変わりません。（`--rules` はあなたのもので、ファイルから、起動時に読みます。）

## フラグのファイル（`--config`）

`run --config FILE`（`brew services` と `reqcove service install` 用）は、run のフラグをファイルから読みます。そのファイルに書き込めるものが、次の起動のフラグを決めることになります。そのため、ファイルはあなたのもので、あなただけが読めるものでなければなりません（そうでなければ断ります。`--mask-values` のパターンが入っていることがあります）。エラーは行を示し、値は決して出しません。また、マスクを外すフラグ、通信をマスクなしで見せるフラグ、すべてのサイトを記録するフラグ、動いている間にファイルでリクエストの行き先を変えられるようにするフラグは、コマンドラインに残します。`--no-redact`、`--web`、`--allow-hosts '*'`（`@FILE` を通したものも）、`--rules-reload`、`--lan`（LAN に開いたプロキシ）は、ファイルでは断ります（テスト）。`--upstream-proxy` や `--rules` などのほかのフラグは、ファイルに書けます。

## モックのプリセット

`--rules` のファイルで `preset: NAME` を付けたモックは、エージェントが `activate_preset`（`list_presets`、`deactivate_preset`）で有効にするまで何もしません。v0.7 からは、`map_remote`、`modify_headers`、`resolve` のルールもプリセットにできます。[下記](#map_remotemodify_headersresolve-のプリセット)を見てください。これらはリクエストを別の場所へ送れます。
プリセットを書くことが、エージェントが有効にしてよいという、あなたの同意です。起動時のスイッチはありません。Skill とサーバーの instructions は、どのルールもそうであるように、`preset:` を書くのは会話の中であなたが頼んだときだけで、記録に書かれていることを理由には決して書かないよう、エージェントに伝えます。頼まれてプリセットを書いたエージェントは（`--rules-reload` があれば）すぐに有効にできます。そのときは、会話の中での依頼が同意です。モデルがそれを守るかどうかは、テストで示せることではありません。

v0.5 から新しくなったこと：Reqcove のツールだけを許可されたエージェント（MCP だけのクライアントや、サンドボックスに入ったクライアント）が、デバイスが受け取るものを、自分の選んだときに、そして呼び直すことで、呼び続ける限り変えられるようになりました。サイトが記録に書き込んだ文が、そうするようエージェントを誘導しようとすることがあります。エージェントが有効にできるのは、あなたが書いたものだけです。モックのプリセットでは、新しい中身、送り先、ホストは生まれず、このコンピュータから新しく出ていくものもありません。最悪の場合は、すべてのプリセットがずっと有効にされ続け、それぞれがサイトの名前で、あなたの書いたものを応答することです（許可したホストの HTML ページのモックは、どのモックもそうであるように、そのホストの Cookie を持って Safari で動きます）。

- 上限（Reqcove で確かめ、mitmproxy のアドオンでもう一度確かめます）：1 回につき最長 5 分で、`times` を付けると最大 20 件のリクエストまでです。有効にし直すことに上限はありません。一致したリクエストは、誰が送ったものでも回数を使います。
- このコンピュータでだけ：ツールは `run` のソケットと `reqcove mcp` にあります。`--mcp-http` には、それらを持たない専用のサーバーがあります（`run` が作る 2 つのサーバーのテスト）。アドオンは、状態ディレクトリにある自分のソケット（0600）で、`run` が渡した秘密を持つ要求だけを受け付けます（テスト）。
- `reqcove mcp` は、呼び出しの途中で `run` への接続が切れたあと、書き込みを決して送り直しません（テスト）。効いたかもしれないし、効いていないかもしれない、と伝えます。
- 書き込みのツールには読み取り専用の印を付けていないので、ほかのツールの前に確認するクライアントは、これらの前にも確認します。v0.5 で `"mcp__reqcove"` をまとめて許可したユーザーでは、これらも確認なしで許可されます。読むツールを名前で許可してください。
- Skill とサーバーの instructions は、プリセットを有効にするのは会話の中でユーザーが頼んだテストのためだけで、記録やプリセットの説明に書かれていることを理由には決して有効にしないこと、ルールファイルに `preset:` を足すのはユーザーが頼んだときだけであることを、エージェントに伝えます。モデルがそれを守るかどうかは、テストで示せることではありません。
- 見えること：`run` は、エージェントがプリセットを有効・無効にするたびにログに出します。`reqcove status` と `status` ツールは、有効なものを一覧にします（または、mitmproxy が答えなかったと伝えます）。プリセットが応答したフローには `preset: NAME` と出ます。`--rules-reload` のときは、ルールファイルが変わるとすべて無効になります。mitmproxy や `run` の再起動でも同じです。
- 終わりは 2 つの時計で確かめるので、終わりの時刻を過ぎてスリープしていたコンピュータでも、有効のまま残りません（テスト）。すでに `delay_ms` で待っている応答 1 つは、プリセットを無効にしたあとも返ります。
- `list_presets` は、それぞれが何に一致するかと、ステータス、遅延、fault を返します。ボディやヘッダーの値は決して返しません。

### map_remote、modify_headers、resolve のプリセット

これらの種類のプリセットは、有効な間、アプリが受け取るものだけでなく、デバイスのリクエストの行き先や、リクエストが運ぶものを変えます。

- `map_remote` のプリセットは、一致したリクエストを、アプリの Cookie、トークン、ログインのボディ、そのほか中にあるものすべてと一緒に、あなたが書いた送り先へ送ります。記録しているすべてのデバイスからのものが対象です（LAN モードでは、許可したすべてのアドレス）。エージェントは送り先を選べません。選べるのは、いつ有効にするかと、有効にし直すことでどれだけ続けるかだけです。サイトが記録に書き込んだ文による最悪の場合は、あなたの本番の認証情報が、プリセットに書かれたステージングや開発用のサーバーへ、何度も送られることです。考えておくべきリスクは、古くなった送り先です。いまは別の人が持っている、古いトンネルやステージングの名前です。
- 5 分が区切るのは切り替えで、その影響ではありません。有効な間にアプリが書いたもの（注文、編集）は、そのサーバーにあります。アプリは、そこで得たトークン、Cookie、キャッシュを持ち続け、無効になったあとで、いつものサーバーへ送ることがあります。
- `resolve` は、名前の接続先を別の場所にしますが、Host、SNI、TLS の検証はその名前のままです（コードを読んだものと、平文の HTTP での E2E テスト）。HTTPS では、別のサーバーにその名前の証明書が必要なので、こちらのほうが安全な種類です。
- `modify_headers` のプリセットが変えるのはリクエストだけです。レスポンスに対するもの（`~s`）は、読み込みで断ります。ページの保護（CSP、HSTS）を外したり、Safari が表示するホストに Cookie を設定したりできてしまうためです。その値は決して表示しません。
- 送り先を表示して確かめられるように、読み込みで断るもの：置き換えが `http://` か `https://`、ホスト、`/` の形でない `map_remote` のプリセット、ユーザーやパスワードがあるもの、ホストをリクエストから取るもの、リンクローカルのアドレスへ向かうもの。このコンピュータか LAN のアドレス（`localhost`、`*.local`、プライベートアドレス）以外への平文の `http://`。リクエストごとに、書き換えた URL のスキーム、ホスト、ポートを、表示している送り先と照合します。URL の途中に一致した正規表現には 502 を返し、ほかの場所へリクエストを送ることは決してありません（テスト）。
- 有効な `modify_headers` のプリセットは、普通のルールのあとに当てるので、送られるのはプリセットのヘッダーです（テスト）。
- 表示するもの：それぞれのプリセットの送り先（`map_remote`）やアドレス（`resolve`）を、`run` の準備完了の表示とログ、`list_presets` に出し、有効なものを `reqcove status` に出します。フィルター、正規表現、ヘッダーの値は決して出しません。プリセットが変えたフローは、`presets` にそのプリセットを並べます。Skill とサーバーの instructions は、そうしたフローの応答を、いつものサーバーのものとして決して報告しないよう、エージェントに伝えます。
- `activate_preset` には読み取り専用の印がなく、そうしたツールの前に確認するクライアントは確認します。`"mcp__reqcove"` をまとめて許可したクライアントは、これも許可します。これはすべての種類を受け付けるので、確認なしで許可すると、これらも確認なしで有効にできます（ガイドの[例](guide.ja.md#ツールを許可する)では `ask` に置いています）。
- 上限と見え方は、モックのプリセットと同じです。1 回につき最長 5 分（これらの種類に `times` はありません）、このコンピュータでだけ、`--mcp-http` からは決して使えず、読み直しや再起動のあとは無効、時計は 2 つ。
- 試していないこと：プリセットが有効・無効になる前に開いていた接続（使い回される HTTP/1、HTTP/2）を、アプリがどう扱うか。使い続けるかもしれないので、切り替えがすぐには効かなかったり、終わりを過ぎて続いたりすることがあります。コードを読んだもの：ルールはリクエストの始まりで当てるので、`map_remote` や `resolve` のプリセットが有効な間に始まった WebSocket、ストリーム、長いアップロードは、プリセットが無効になったあとも、5 分を過ぎても、その送り先のままです。

## ルール（`--rules`）

ルールはあなたのもので、mitmproxy の起動時にファイルから読みます。ルールを変えるツールはありません。`run --rules-reload` のときは、ファイルが変わるたびに読み直すので、そのファイルに書き込めるもの（あなたのユーザーとして動くプロセスすべて。ファイルを扱えるエージェントも含みます）が、`run` が動いている間に、デバイスのリクエストの行き先を変えられるようになります。これがなければ、ファイルを読むのは mitmproxy の起動時だけです（`run` の起動時と、mitmproxy が終了したあと reqcove が起動し直すとき）。
`modify_headers` が受け付けるのは、HTTP のトークンであるヘッダー名と、改行や NUL のない値です（あると、通信上で別のヘッダーが始まってしまいます）。値のファイルが、あとのフローのために読み直されたときに改行や NUL を含むようになっていたら、そのフローのヘッダーからその値を落とします。`resolve` の名前はホスト名だけなので、その中のものが制御文字としてログに届くことはありません（テスト）。
`map_remote` と `resolve` は、mitmproxy に、このコンピュータから、ルールが言う先へ接続させます。このコンピュータと LAN も含みます。Exit Node がそれらのアドレスを拒否するのは、デバイス自身の接続についてのことです。ルールは、その送り先を、中継しているデバイスの上で、ルールのホストへリクエストを送るすべてのアプリ（Web ページも含みます）に開きます。`resolve` は IPv4 アドレスだけを受け付け、名前解決が必要な名前は決して受け付けません。`0.0.0.0/8`、リンクローカル、マルチキャスト、予約済みの範囲、Tailscale の 100.100.100.100、クラウドのメタデータのアドレス 169.254.169.254 と 100.100.100.200 を拒否します。`map_remote` は、与えられたものを何でも受け付けます。ポートのない `resolve` のルールは、リクエストのポート（アプリのもの、または `map_remote` の URL のもの）を使います。`resolve` の送り先への TLS は、ルールの名前で、mitmproxy 自身の CA の一覧（certifi。mitmproxy のコードを読んだもの）を使って検証するので、リクエストは、その名前の証明書を持つサーバーにだけ進みます（試しました：別の名前の信頼された証明書を持つサーバーには 502 が返ります）。平文の HTTP は検証しません。`resolve` の名前には、それぞれ別のアドレスが必要です。mitmproxy は接続をアドレス単位で使い回すので、アドレスを共有する名前は、1 つの名前の検証を共有してしまいます。そのため断ります。`resolve` の送り先のアドレスへの `map_remote` は、双方向で、その接続を共有します。一方のリクエストが、他方のために作られ検証された接続に乗ることがあり、失敗した接続は、アプリの接続が続く限り、両方を失敗させます。
ルールが失敗したリクエスト（たとえば、`map_remote` が不正なポートを作った場合）は、元のまま送らずに 502 で応答します（テスト）。置き換えがまったく成り立たない `map_remote` は、起動時に `run` を止めます。
他人が作ったルールファイルはコードです。あなたのアプリのリクエストを、Cookie やトークンも含めて、どこへでも送れます。
`reqcove mock add` は、あなたの代わりにモックをルールファイルに書きます。入力と出力がターミナルのときだけ動きます。頼まれていないエージェントが実行するのを防ぐ助けで、保証ではありません（コマンドを実行できるエージェントは、ターミナルを用意することも、ファイルを自分で編集することもできます）。ルールを書くのは、あなたのままです。Skill は、エージェントにこれを決して実行しないよう伝えます。`run` にファイルを先に確かめさせるために、状態ディレクトリから `run` の SOCKS5 のパスワード（0600、あなたのユーザー）を読みます。`run` は、指し示されたファイルを確かめるだけで、取り込みはしません（テスト）。
`mock` はサイトの名前で応答します。アプリも、WebView のページも、それをサイト自身の応答として受け取ります（その中のスクリプトはそのオリジンで動き、リダイレクトには従います）。使えるのは `--allow-hosts` のホストだけで（それ以外は断ります）、ヘッダーの値は `modify_headers` のものと同じように確かめます。記録には、フローがモックされたことが、ルールの番号とステータスと一緒に残ります。その中身は決して残りません。モックが応答するかもしれないリクエストは、ボディが届くまで全体を保持します（operation がボディの中にあるためです）。長さが分かっているときは 1 MiB までです。長さのない GET は、HTTP/2 ではそれ以上を運べ、`map_local` と同じく全体を保持します。ルールを書く MCP ツールはありません。モックは、ユーザーが書いたファイルから来ます。`--mcp-http` からは、エージェントがそのファイルに届く方法はまったくありません。
`list_rules` と `explain_rules`（読み取り専用。v0.7 から）は、それぞれのルールを種類と番号で、そのプリセットと一緒に示し、ほかに示すのは、ルールから導いたものだけです。モックのメソッド、URL、operation、ステータス、遅延、fault、`map_remote` の送り先のスキームとホスト（または「path only」、ルールがそれを書き出していないときは「not shown」）、`modify_headers` のヘッダー名と向き、`resolve` の名前とアドレスです。フィルター、正規表現、ヘッダーの値、ボディ、ファイルのパスは決して示しません（目印の文字列を使った E2E テスト。`map_local` のルールは番号だけを示します）。`explain_rules` は、自分で作ったリクエストに、リクエストが通る経路そのもののコードを通します。そのリクエストは決して送りません。プリセットの状態はコピーを使うので、どのプリセットの回数も使わず、どれも有効にも無効にもしません（テスト）。プリセットのツールと同じく、`run` のローカルのソケットと `reqcove mcp` にだけあり、`--mcp-http` からは決して使えません。送り先は、デバイスのリクエストがどこへ送られうるかを示すからです。

## 上流プロキシ（`--upstream-proxy`）

このとき、復号した HTTP(S) のリクエストはそのプロキシを通って進み、Reqcove の mitmproxy は自分ではサーバーに接続しません（connection strategy は lazy。テストがサーバーの接続を数えます）。許可したホストへの、TLS の上のほかのプロトコルは、これまでどおりサーバーへ直接向かいます（コードを読んだもの。レビューで見ました）。変わることは次のとおりです。

- プロキシには、リクエストとレスポンスがマスクなしで見えます。たとえば Burp は、それをプロジェクトに、ディスクに保存します。プロキシ自身の MCP サーバーや拡張機能は、Reqcove のツールが出さないものと、リクエストを送る能力を、エージェントに与えます。
- 本物のサーバーの証明書を検証するのは、プロキシの仕事です。プロキシの CA（`--upstream-ca`、または起動時に取得した Burp のもの）があるとき、Reqcove はその CA だけを信頼するので、検証する相手はプロキシで、サーバーではありません。Burp の CA は、プロキシ自身のリスナーから平文の HTTP で取得します（`http://127.0.0.1:PORT/cert`。名前解決をしないので、ほかのサーバーは応答できません）。取得するのはプロキシがこのコンピュータにあるときだけで、受け取るのは「PortSwigger CA」という名前の CA だけです（テスト。Burp がそこで応答することは curl で確かめました）。Burp は、デフォルトでは検証しませんでした（試しました。レビュー）。
- プロキシがどこに接続するかは、プロキシが決めます。Reqcove は、Exit Node が許可したアドレスをプロキシに渡しますが、Burp は SNI の名前で、このコンピュータで名前解決し直して接続します（試しました。レビュー）。このコンピュータの LAN に解決される名前は、Exit Node の拒否を越えて、そこに届きます。iPhone が訪れたサイトは、プロキシの名前解決に対してだけ、自分の名前をそう解決させることができます（DNS リバインディング：コードを読んだもので、試していません）。そのため、`--allow-hosts` は狭くしておいてください。`'*'` のときは `run` が警告します。この理由で、`--upstream-proxy` と一緒の `resolve` のルールは断ります。
- CONNECT の行（IP アドレスとポート）と平文の HTTP は、暗号化されずにプロキシに届きます。プロキシは、このコンピュータか tailnet の上に置いてください。
- このフラグは起動時に読みます。これを変えるツールはありません。

## ページ（`--ui`）

`--ui` は、ノードの 80 番ポートで、記録の読み取り専用のページを提供します。中身は MCP ツールが返すものと同じで、同じようにマスクされています。読めるのは次のとおりです（どれもテストがあります）。

- tailnet にあるあなた自身のデバイス（reqcove のノードと同じユーザーでログインしていて、タグなし）と `--device` のデバイスだけです。接続が開いたときと、リクエストのたびに確かめます。それ以外には何も返しません。
- あなた自身のデバイスからは、すべてのデバイスのフローが、デバイスの名前と一緒に見えます。別のユーザーの `--device` のデバイスからは、一覧でも ID の指定でも、そのデバイス自身のフローだけが見え、件数と次の手順もそのデバイス自身のものだけです（ほかのデバイスのものも、その名前も見えません）。
- トークンを持つブラウザだけです。`run` が表示するリンクは、トークンを HttpOnly、SameSite=Strict の Cookie として設定し、400 日間保持します。同じ iPhone のほかのアプリはこのポートに届きますが、トークンがなければページを読めません。トークンは状態ディレクトリの `ui-token`（0600）に保存され、起動のたびに同じです。そのため、リンク、ブックマーク、Cookie は、そのファイルを削除して起動し直すまで使えます。そのあとは 403 になります。ページに届くのは、あなた自身のデバイスと `--device` のデバイスです。漏れたリンクは、それらからしか使えません。
- `Host` でノード（その MagicDNS 名か tailnet アドレス）を名指ししたリクエストだけです。iPhone が訪れたサイトが、自分の名前をノードに向けて、このページを自分のものとして読むことはできません（DNS リバインディング）。
- GET と HEAD だけです。リクエストが Remote Proxy を通って来たときも同じです。検索フォームはページ自身に送られ（CSP の `form-action 'self'`）、Clear はフローを一覧から隠すだけで（URL の `since`）、何も削除しません。ページのスクリプトは、自分の `/app.js` だけです（Content-Security-Policy は、ほかのスクリプトも、インラインのものも許しません）。このスクリプトは 1 秒に 1 回 `/flows.json` に一覧を求め、DOM の呼び出しと `textContent` だけで入れるので、サイトがヘッダーやボディに書き込んだものは、テキストのままです（テストが、node の代用の DOM の上でこれを実行します）。キャッシュはされません（`no-store`）。ページはそれでも Safari を通ります。Safari の履歴には、見たフローのページの URL、トークン付きの最初のリンク（デバイスがなければ役に立ちません。`ui-token` を削除するまで有効です）、検索の URL が、検索した語と一緒に残ることがあります（`--no-redact` のときは、シークレットの値を検索すると、その値がそこに残ります）。32 段より深く入れ子になった JSON のボディは、インデントせずにそのまま表示します（深い入れ子のインデントには、深さの 2 乗で増えるメモリが要ります）。

トークンは、ログイン用の URL と同じく、`run` のターミナルと `reqcove links` にだけ出ます。ログの行や MCP ツールには決して出ません。

## mitmweb（`--web`）

mitmweb は 127.0.0.1 で待ち受けます。パスワードは状態ディレクトリの `web-token`（0600。そのファイルを削除して起動し直すまで、起動のたびに同じ）に保存し、0600 のファイルで渡します。コマンドラインでは決して渡しません。パスワード付きのリンク（`?token=`）をブラウザがノードを通して開くと、mitmweb がそれを受け付けたあとで、パスワードを除いた同じ URL へのリダイレクトで応答します（mitmweb の代役を使ったテスト）。そのため、パスワードはアドレスバーに残りません。Safari の履歴が最初の URL を残すかどうかは、確かめていません。ターミナルでは、`run` はトークン付きのリンクを表示します（スクロールバックに残り、トークンのファイルを削除するまで有効です）。ターミナルでないところでは、何も表示しません。`reqcove links` は、状態ディレクトリの `links`（0600）から、もう一度表示します。mitmweb の Cookie は、mitmweb の再起動を越えては使えません（起動のたびに作る鍵で署名するためです。mitmweb のコードを読んだもの）。そのため、再起動のあとはリンクがもう一度必要です。ノードは、tailnet にあるあなた自身のデバイスのために、自分の 8081 番ポートも mitmweb へ中継します（同じユーザーで、タグなし。別のユーザーの `--device` のデバイスも、ほかの誰も対象外です。接続が開いたときとリクエストのたびに、`Host` のノードの名前かアドレスで確かめます）。それでもパスワードが守っています。そこで得られるものは、このコンピュータで得られるものと同じです。パスワードがあれば mitmweb のオプションを変えられ（スクリプトも含みます）、それはこのコンピュータでコードを実行することになります。パスワード付きのリンクは、`run` のターミナルと `reqcove links` だけが表示します。Remote Proxy を使うスマートフォンも、同じ方法で届きます（ノードの 8081 番ポートへのリクエストと WebSocket のトンネルは、あなた自身のデバイスに限り、mitmweb へ送られます）。すでに開いている WebSocket は、そのデバイスがあなたのものと数えられなくなっても、開いたままです。Exit Node を使っている iPhone から試しました。mitmweb は通信を**マスクなしで**表示し、パスワードを持つ人は誰でも、そのページからリクエストを編集してリプレイし、オプションを変えられます。ボディは 1 つ 2 MB まで（mitmproxy はストリームするボディを保持しないので、Reqcove が渡します）、全体をマスクなしで表示し、新しい 10,000 件のフローと 256 MB のボディを保持します。この上限が数えるのは終わったフローです。まだ続いているフローは終わったときに数え、それまで保持するボディ（向きごとに 2 MB まで）は上限の外です（コードを読んだもの）。mitmproxy が復号したフローをすべて表示します。許可した接続に相乗りした、`--allow-hosts` の外のホストへのリクエスト（HTTP/2 の接続の再利用）も含みます。リクエストごとの確認は、それらを Reqcove の記録に入れないだけです。

オプションで変わること（コードを読んだもので、試していません）：mitmproxy の動作だけで、reqcove が mitmproxy を起動し直すまでです。Reqcove の記録は、`--allow-hosts` の範囲とマスクを保ちます。Reqcove が、届いた時点で両方を確かめ直すためです。Capture タブで SOCKS プロキシをオフにすると、デバイスの HTTP(S) が止まります（Reqcove は、それを通して HTTP(S) を mitmproxy に渡しています）。そこで別のモードをオンにすると、127.0.0.1（reqcove が設定する listen host）で待ち受け、Reqcove のデバイス名と、このコンピュータや LAN の拒否を迂回します。

## HTTP 経由の MCP（`--mcp-http`）

ノードは、MCP ツールを自分の 8090 番ポートの `/mcp` で、tailnet にあるあなた自身のデバイスにだけ提供します（reqcove のノードと同じユーザーで、どちらもタグなし。接続が開いたときとリクエストのたびに確かめます）。`Host` でノードの名前かアドレスを指定し、`Authorization: Bearer` と、状態ディレクトリの `mcp-token`（0600。定数時間で比較します）にあるトークンを付けたものに限ります。別のオリジンのブラウザのページからのリクエストは拒否します。トークンは、`run` のターミナルと `reqcove links` だけが表示します（`-t` を付けて動かしたコンテナでは、`docker logs` に残ります）。ログの行、`reqcove status`、ツールには決して出ません。エージェントがそれらを実行するかもしれないからです。個人の tailnet では、Tailscale の OAuth apps で入ったエージェントのデバイス（Grok Bot）は、あなたのほかのコンピュータと同じく、あなた自身のデバイスの 1 つに数えられます。それらを区別するのはトークンです。そのとき、ツールが答えるものはすべて、そのデバイスとそのモデルの提供元（Grok Bot なら xAI のクラウド）に届きます。エージェントは、あなたが `mcp-token` を削除して `run` を再起動するまで、トークンを持ち続けます。
ツールは `reqcove mcp` のものと同じですが、プリセットのツール、`list_rules` と `explain_rules`、マーカーのツール（`add_marker`、`list_markers`）はありません。`--mcp-http` の専用のサーバーが、それらを持たないためです（テスト）。返すのは、同じマスク済みの記録です。
`run` は、HTTP での各ツール呼び出しを、呼んだデバイスとツールの名前（引数は出しません）と一緒にログに出し、トークンがないか間違っているリクエストもそれぞれログに出します。
各デバイスが呼べるのは、1 秒におよそ 10 回（同時には 30）です。それを超えると、しばらくの間 `429 Too Many Requests` が返り、1 分に 1 回ログに出ます（テスト）。1 台のデバイスの暴走したエージェントが、ほかのデバイスの分まで `run` をふさぐことはありません。呼び出しは、呼び出し元が切断すると終わります（テスト）。
確かめたのは、テスト（本物の tailnet で、別のユーザーのデバイスが拒否されること。トークン、`Host`、オリジンの確認）、この Mac から tailnet 越し、そして Grok Bot です。

## ローカルプロキシ（`--local-proxy`）

このコンピュータ自身のアプリ（iOS シミュレーター）のための、127.0.0.1:8082 の HTTP プロキシで、パスワードはありません。このコンピュータのどのプロセスも、どのユーザーのものでも使え、それが `--allow-hosts` のホストへ送るものは、`local` というデバイスとして記録されます。アプリは、このプロキシがないときと同じように、このコンピュータ自身の名前解決で、LAN、VPN、tailnet に届きます。IPv6 は拒否します。このコンピュータ自身（ループバック、自身のアドレス）やリンクローカルアドレスに行き着く名前も、このコンピュータの `/etc/hosts` にある場合を除いて拒否します（テスト）。そうしないと、ここのブラウザのページが、自分の名前をそこへ向けることで、プロキシを通してこのコンピュータのサービスに届いてしまいます（DNS リバインディング）。ページは、それでも自分の名前を LAN、VPN、tailnet のアドレスに向けることができ、プロキシはそれを通します（VPN の中の名前が使え続けるようにするためです）。直接つなぐブラウザも同じ問題に向き合いますが、プロキシを通すとブラウザにはアドレスが見えないので、プライベートネットワーク向けのブラウザ自身の保護（Chrome の Private Network Access）が働きません。`--local-proxy` は、必要な間だけオンにしてください。このコンピュータ、LAN、tailnet はシステムのプロキシの例外に入っているので、アプリは、reqcove がないときと同じく直接届きます。Apple のホストは復号しません。macOS では、`run` は動いている間、システムの Web プロキシをこのプロキシに向けます。元の設定は状態ディレクトリ（0600）に保存し、止まるとき（SIGHUP でも）、次の起動時、または `reqcove cleanup` で元に戻します。まだ戻していない設定を上書きして保存することは決してなく、cleanup は、それを持っている間は状態を削除しません。reqcove がいきなり kill されると、システムのプロキシを使うここのアプリは、設定を戻すまで接続できません。Reqcove が、このコンピュータに自分の CA を信頼させることは決してありません。`run` がコマンドを表示します（TLS だけ、このユーザーだけ）。信頼させると、`<state>/mitmproxy/` にある CA の秘密鍵は、デバイスだけでなく、このコンピュータに対しても任意の HTTPS サイトになりすませます。状態ディレクトリと、そのコピーやバックアップは人に見せないようにし、終わったら信頼を外してください（`reqcove status` と `cleanup` が、フィンガープリントを使った方法を表示します）。本物の `networksetup`（設定し、Ctrl-C で元に戻す）と、iOS 27 のシミュレーターで試しました。

## LAN モード（`--lan`）

`run --lan` は tailnet のノードを起動しません。HTTP プロキシが、このコンピュータのアドレスの 1 つ、つまり LAN のインターフェイス 1 つのアドレス（0.0.0.0 でも、VPN のトンネルでも決してありません）の、`--proxy-port` で待ち受けます。パスワードはありません。誰が使えるかは、ここで、アドレスごとに決めます。

- そのインターフェイスのネットワークの外からの接続は、受け付けた時点で閉じます。許可されていないアドレスからの接続も同じです。何も記録せず、新しいアドレスはそれぞれ 1 回ログに出します。これは、見たアドレスの一覧（10,000 件）がいっぱいになって空にされるまでのことで、そのあとはもう 1 回ログに出し、run はもう一度質問します（テスト）。維持された接続では、リクエストのたびに確かめ直すので、`reqcove lan deny` は 2 秒以内に新しいリクエストを拒否します。すでに開いている HTTPS のトンネルは、閉じるまで、またはどちらの向きにも 15 分間バイトが流れなくなるまで続きます。1 つのアドレスが同時に開けるトンネルは 256 本までです（どちらも、小さな値にしたテスト）。
- 許可したアドレスは、`<state>/lan-allowed`（0600。それぞれを許可した日時付き）に保存します。変わるのは、`reqcove lan allow|deny` か、run が自分のターミナルで出す質問を通してだけです。`lan` コマンドは、`reqcove links` と同じく、標準入力と標準出力がターミナルでなければ断ります。エージェントのシェルは、たいていどちらも持っていません（助けであって、保証ではありません。スクリプトはターミナルを用意できます）。この一覧を変える MCP ツールはありません。質問は、run がターミナルのフォアグラウンドのジョブである間だけ行い、それより前に入力されたものは先に捨てるので、前に押した Enter や `y` は答えになりません（差し替え用の継ぎ目を通したテスト。ターミナルの呼び出しそのものはテストしていません）。
- アドレスはデバイスではありません。あとで許可されたアドレスを持ったものも、許可されます。このネットワークでも、同じプレフィックスを持つ別のネットワークでもです（カフェの 192.168.1.0/24 と、あなたの家の 192.168.1.0/24）。準備完了の表示、`reqcove status`、`reqcove lan list` が一覧を表示します。
- `--lan` は `--config` のファイルでは断るので、`brew services` と `reqcove service install`（インストールのときにもそのファイルを断ります）が、開いたプロキシを動かし続けることは決してありません。

許可したアドレスが、このコンピュータを通して届く先（テスト）：80 番と 443 番ポートだけ（ほかは、名前解決の前に拒否します）で、公開のアドレスに、あなたのアドレスから届きます。プライベートな範囲（10/8、172.16/12、192.168/16、100.64/10）は、このコンピュータの VPN の先のものも含めて、`--allow-hosts` に完全な名前（`*` なし）で書いたものにだけ届きます。完全な名前でも決して届かないもの：このコンピュータ（ループバック、自身のアドレス）、リンクローカルアドレス、プロキシのあるネットワーク、公開のアドレス空間から番号を振った、このコンピュータのほかのネットワーク、特別な用途の範囲、IPv6。名前は、このコンピュータのリゾルバで解決し、`/etc/hosts` が先です。`map_remote` と `resolve` の送り先には、これらの確認の外で、mitmproxy が接続します。許可したホストをこのコンピュータのサーバーへ送るルールは、LAN のクライアントのリクエストにも応えます。

`http://mitm.it` の CA は平文の HTTP で届くので、LAN のほかの誰かが差し替えられます。準備完了の表示は、代わりに AirDrop で送るための CA のファイルの名前を示し、iOS がプロファイルの「詳細」に表示するのと同じ形で、その SHA-256 を表示します（iOS 27.3 で確かめました、2026-11-14：一致しました）。LAN モードは信頼できるネットワークで使い、終わったら止めてください。自宅の Wi-Fi の iPhone で試しました（iOS 27.3、2026-11-14）：許可するまで拒否され、そのあと記録され、`reqcove lan deny` のあとはまた拒否されました。

## このコンピュータのほかのプロセス

mitmproxy の SOCKS5 のポートは 127.0.0.1 にあり、起動のたびに作るパスワードで守られています（0600 のファイルに保存し、プロセスの引数には決して入れません）。それを知っているのは reqcove だけなので、ほかのローカルのプロセスは、プロキシを使うことも、デバイスになりすますこともできません。reqcove は、`run` ごとに 1 回、自分でそのポートを bind し、待ち受けているソケットを、起動する mitmdump それぞれに渡します。mitmproxy（12.3.1）にはそのためのオプションがないので、reqcove のランチャー（`mitm.py`。別の `--mitmproxy-spec` のときにも使います）が、mitmproxy に、自分で bind する代わりにそのソケットで待ち受けさせます。mitmdump が死ぬと、reqcove は、ポートを持ったまま起動し直します（`ps` で見えます）。そのため、その間も、最初の mitmdump の前も、ほかのプロセスがそのポートの 127.0.0.1 を取ることはできません。その間に作られた接続は、ソケットのキューで次の mitmdump を待ちます。デバイスの接続は、そのアドオンが hello を言うまで待ちます（最長 15 秒で、そのあとは失敗します）。mitmproxy は `proxyauth=any` で動き、パスワードを確かめるのは reqcove のアドオンだけなので、そこで待っている接続を、アドオンが読み込まれる前に読んではなりません。ランチャーは、mitmproxy に、受け付けをせずにそのソケットの上でサーバーを作らせ、アドオンは、読み込まれたとき、hello の直前に受け付けを始めます。本物の mitmproxy（uvx 経由、macOS）でテストしました。mitmdump が落ちている間にキューに入った 2 つの接続は、間違ったパスワードを一度に全部送ったものも、1 手ずつ送ったものも拒否され、それらが求めたものは何も中継も記録もされません。ランチャーにすぐ受け付けさせ、アドオンの読み込みを（手で）1.5 秒遅らせると、どちらも受け付けられ、テストは失敗します。その遅れがなければ、mitmproxy（12.3.1）はたまたま、最初の接続を読む前にアドオンを読み込み、やはり拒否しました。
テスト：mitmdump が落ちている間と、reqcove がそれをあきらめたあとは、ポートの bind が失敗し、Stop がポートを解放します（単体テスト。ここでは macOS で実行し、CI は Linux でも実行します）。本物の mitmproxy（ロックからと、uvx 経由、macOS）では、再起動している間も同じで、そのとき送ったリクエストは、次の mitmdump が中継して記録します。ランチャーの変更が効かなかった場合（別の方法で bind する mitmproxy）は、mitmproxy 自身の bind が、持たれているポートで失敗し、hello の前に終了して、決して準備完了になりません。mitmproxy 12.3.1 で、変更を遅すぎる時点で行って試しました（address already in use）。
macOS で、同じユーザーとして試しました。そのポートの 127.0.0.1 の bind は、SO_REUSEADDR と SO_REUSEPORT を付けても失敗します。そのポートの 0.0.0.0 の bind は SO_REUSEADDR で成功しますが、127.0.0.1 への接続は、これまでどおり、より具体的なソケット、つまり reqcove のソケットに届きます。別のユーザーでは試していません。両方のカーネルのドキュメントによれば（ここでは確かめていません）、2 つ目のソケットがそのアドレスを得るのは、両方が SO_REUSEPORT を設定したときだけで（Linux では、同じユーザーのときだけ）、reqcove のソケットは決して設定しません。対象外：あなた自身のユーザーのプロセス（どのみちパスワードのファイルを読めます）と、root。

状態ディレクトリは、それ自体を確かめます。その上のディレクトリは確かめません。状態ディレクトリ（と `--state`）は、あなただけが書き込めるディレクトリの下に置いてください。親ディレクトリで項目の名前を変えられる人は、状態ディレクトリを自分のものに差し替えられます。

## mitmproxy 自身のコード

mitmproxy とその依存パッケージ（44 個）は、reqcove に組み込まれたロックファイル（`internal/capture/mitm.py.lock`）から来ます。`run` は、それと小さなランチャーを状態ディレクトリに書き、`uv run --locked --script` で mitmproxy を起動します。これは、ロックが名指しするファイルだけをインストールし、それぞれのハッシュを確かめます（試しました：1 つのパッケージのハッシュを変えたロックは、キャッシュが空のときも、いっぱいのときも拒否されました）。素の `uvx` は、ハッシュを与えられても確かめません（試しました）。これは、別の `--mitmproxy-spec` のときと、ファイル名が `uvx` でない `--uvx`（ラッパー。その `uv` がどれか分かりません）のときに使い、決まった日付より前のリリースから取ります（`--exclude-newer`）。CI は、ロックがランチャーと合っていることを確かめ、既知の脆弱性について監査します（pip-audit）。最初の監査は tornado 6.5.10 に 3 件を見つけました。tornado は mitmweb のサーバーで、mitmproxy 12.3.1 はそのバージョンを上限にしています。ロックはそれを上書きし、6.6.1 に固定しています。6.6 がその 3 件を直し、6.6 自身には CVE-2026-126347 があります（Reqcove の `--web` のテストは 6.6.1 で通ります。mitmproxy 自身のテストは実行していません）。

## Exit Node の DNS

Exit Node は、それを使うデバイスに、DNS over HTTPS（Tailscale の PeerAPI）で応答します。試したところ、`--device` に入っていないこのコンピュータにも応答しました。Exit Node を使える tailnet のほかのデバイスは、それを通して名前を解決できます。問い合わせ先は、あなたのデバイスと同じ上流で、デフォルトでは `1.1.1.1` です。`--dns system` や、`--dns` に LAN のリゾルバを指定したときは、それはあなたのルーターや会社のリゾルバで、それだけが知っている名前も引けます。（Tailscale のコードを読んだもの：tailnet のポリシーが Exit Node の使用を許すピアなら、どれにでも応答します。）Reqcove は DNS を記録しません。

このコンピュータから上流までの DNS は、Exit Node でも Remote Proxy でも同じく、暗号化されていない平文の DNS で、答えを DNSSEC で検証しません（コードを読んだもの）。そのため、このコンピュータがつながっているネットワーク（その Wi-Fi、ISP）には、デバイスが引く名前が見え、その経路上にいる人は偽の答えを返せます。経路の外からは難しくなります。問い合わせごとにランダムな ID と専用のランダムなポートがあり、ほかのアドレスからの答えは捨てます。偽の答えで得られるものはわずかです（コードを読んだもので、試していません）。HTTPS は、それでもその名前の証明書を示さなければなりません（復号するホストでは mitmproxy が、それ以外ではスマートフォン自身が検証します）。このコンピュータ、その LAN、ループバックを指す答えは、そこへのどの接続とも同じく拒否します（テスト済み）。平文の HTTP は、どのネットワークでもそうであるように、別の場所へ送られることがあります。名前を隠すには、ローカルの DNS-over-HTTPS のリレーを `--dns 127.0.0.1:PORT` として使えるかもしれません。これは試していません。

## デバイスから届く範囲

公開の IPv4 アドレスです。Reqcove は、Exit Node でも Remote Proxy でも、このコンピュータ自身のアドレス（すべてのインターフェイスのもの）と、それらのインターフェイスがつながっているネットワーク（そのため、公開のアドレスを使う LAN や、隣のサーバーがいるクラウドサーバーのサブネットも拒否します）、ループバック、プライベートとリンクローカルの範囲、tailnet の範囲、マルチキャストとそのほかの特別な用途の範囲、そして IPv6 のすべてを拒否します。ルートを通してだけ届く公開のネットワーク（ルーターの先にあり、インターフェイスのサブネットではないもの）は拒否しません（コードを読んだもの）。ping（ICMP echo）も同じ規則に従います。`--device` にないデバイスからのものや、拒否するアドレスへのものは捨てます（テストが、その両方から 127.0.0.1 へ ping を送ります）。一覧にあるデバイスから公開のアドレスへの ping には、このコンピュータから ping を送ることで応答します（コードを読んだもの）。

デバイスの UDP のフローが続いている間（最後のパケットから 2 分、DNS では 30 秒）、それを通して応答できるのは、送り先のアドレスとポートだけです。ほかの誰かから、このコンピュータのそのポートに届いたデータグラムは捨てます（テストが、このコンピュータから 1 つ送ります）。

これで防げないもの：

- **あなたのネットワークの公開アドレス**。これは、このコンピュータのインターフェイスのアドレスではありません。そこへ接続するデバイスは、ルーターが転送するもの（ポートフォワーディング）や、クラウドサーバーではこのコンピュータに届くかもしれません。テストしていません。

## ログイン用の URL

ノードがログインしていない間、`reqcove run` はログイン用の URL を表示します。それを最初に開いた人が、このノードを自分の tailnet に入れることになるので、表示するのは `run` のターミナルだけです。`status` ツールは、そしてそれを通してエージェントとそのモデルの提供元は、どこで見られるかを伝えますが、URL そのものは運びません。

- `run` のログの行は、それを運びません。`--ui`、`--web`、`--mcp-http` のトークンも同じです。`run` がログに出すすべての行（と、終了時のエラー）は 1 つのフィルターを通ります。フィルターは、トークンと、コントロールサーバーのログイン用 URL の形をした URL（Tailscale の `/a/<hex>`、Headscale の `/register/…` と `/register?key=…`）を置き換え、`run` がログイン用の URL を見たあとは、その URL 自体も置き換えます。`--verbose` のときは、tsnet 自身の行もこの対象です。tsnet は、`run` が URL を知る前にそれを出力します（テストが、テスト用のコントロールサーバーからそれらを読みます）。フィルターが知っているのは、それらの形だけです。ログイン用の URL が別の形をしたコントロールサーバーでは、`run` の最初のポーリング以降（3 秒以内）にマスクされます。
- ターミナルでないところ（サービス、`-t` なしの `docker logs`、エージェントのシェル）では、`run` は URL もリンクも表示せず、`reqcove links` が表示するということだけを表示します。
- `login-url`（ログイン待ちの間）と `links`（トークン付きのもの。`run` の準備ができてから）は、状態ディレクトリに 0600 で保存し、`run` が起動するときと止まるときに削除します（クラッシュのあとは、次の起動まで残ります。`reqcove links` は、`run` が動いているかを確かめません）。0600 が締め出すのはほかのユーザーで、あなたとして動くプログラムではありません。シェルを持つエージェントは、同じディレクトリにあるノードの鍵、トークン、CA の鍵と同じように、それらを読めます。tsnet も、自分の行を、ログイン用の URL も含めて、そこのバッファのファイル（`tsnet/tailscaled.log*.txt`、0600）に保存します。`--verbose` がなくても同じです（コードを読んだもの）。
- `reqcove links` は、出力先がターミナルでないときは断ります。エージェントが実行するのを防ぐ助けで、保証ではありません（プログラムはターミナルを用意できます）。Claude Code の `!` では何も得られません（2026-11-13 に試しました）。Skill とサーバーの instructions は、エージェントにこれを決して実行しないよう伝えます。
- mitmweb のサーバーは、失敗したリクエストの URL を、`?token=` も含めて `mitmproxy.log` に出します。アドオンが、その前にそこでトークンをマスクします（mitmweb の E2E テストで確かめました）。

## Tailscale へのログ

Reqcove のノードは、Tailscale にログを送りません。データプレーンの監査ログを必須にしている tailnet には対応していません（`reqcove status` がそう伝えます）。Reqcove がログをオンにすることは決してありません。
