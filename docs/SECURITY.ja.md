# Reqcove のセキュリティモデル

[English](SECURITY.md)

Reqcove はスマートフォンの HTTPS を復号し、読んだものを AI エージェントに渡します。このページでは、Reqcove が何を守り、何を信頼し、何をしようとしていないかを説明します。対象は v1.0 です。

このページには Reqcove を信頼するかどうかを決めるのに必要なことだけを書いています。詳細はほかの 2 つのページにあります。マスクが形式ごとに何を見つけるかと、記録が残らない接続は、[masking.ja.md](masking.ja.md) にまとめています。オプションごとの詳細は[ガイド](guide.ja.md)の各オプションの節にある「セキュリティの詳細」に、そのほかの詳細はガイドの[セキュリティ](guide.ja.md#セキュリティ)の節にあります。

試していない点と、コードから判断した点には、その場所にそう書いています。テストや実機で確かめたことは、各節の最後の「確認状況」に書いています。確認状況はこのページか、ガイドの詳細にあります。試した環境は、ほかの記載がなければ mitmproxy 12.3.1、iOS 27.3 の iPhone、macOS です。

このページで使う言葉を 2 つ説明します。**状態ディレクトリ**は `~/.reqcove` か、`--state` で指定したディレクトリです。**あなた自身のデバイス**は Reqcove のノードと同じユーザーで tailnet に入っていて、どちらにもタグが付いていないデバイスです。Reqcove はこれを、接続が開くときとリクエストのたびに確かめます。

## 脆弱性の報告

公開の issue ではなく、このリポジトリの GitHub のプライベート脆弱性レポート（private vulnerability reporting）を使ってください。

## スマートフォンから出ていくものとその行き先

### 記録するもの

- 記録するのは、`--allow-hosts` にあって `--pass-hosts` にないホストへのリクエストだけです。これを 2 つの確認で守ります。mitmproxy はほかの接続を復号せずに通し、Reqcove はリクエストごとに Host をもう一度確かめます。
- Apple のホストへの接続は常に復号せずに通します。
- HTTP/2 で接続が再利用されると、許可したホストへの接続が、ほかのホストへのリクエストを運ぶことがあります。そのリクエストは接続と一緒に復号されます。記録はしませんが、`--web` には表示され、`--upstream-proxy` に転送されることがあります。
- 一覧にないホストへのリクエストと TLS の失敗は、数えるだけで記録しません。ただし `reqcove capture allow-all` がオンの間（下）は、すべてのホストを記録します。`reqcove capture discover` がオンの間（下）は、そのホストの**名前**も回数と一緒に残します。運んだものは残しません。
- `--pass-hosts` のホストと、mitmproxy が raw TCP として運ぶ接続は、接続の記録だけを残します。中身は残しません（[詳細](masking.ja.md#中身なしで記録する接続)）。
- 記録がまったく残らない接続もあります（[拾えないもの](#拾えないもの)）。
- Reqcove が見分けられるシークレットは届いた時点でマスクするので、どのツールも返せません（[マスク](#マスク)）。
- ボディを返すのは、ツールがボディを求められたとき（`get_flow` と `search_flows` の `bodies`）と、ボディを比べる `diff_flows` だけです。
- 記録はメモリにあります。上限はフロー 10,000 件とテキスト 64 MiB で、`reqcove run` が止まると消えます。Reqcove 自身はフローをディスクに書きません（[上限](masking.ja.md#記録が保持するもの)）。
- `reqcove har > FILE` は、あなたが指定した先に記録を書きます。中身はツールが返すものと同じようにマスクされています。ファイルのモードはシェルの設定に従うので、ほかのユーザーが読めることがよくあります。これに対して、状態ディレクトリのモードは 0700 です。
- Reqcove は DNS を記録しません。

### エージェントが読んだものの行き先

- ツールが返すものはすべて、エージェントのモデルの提供元に送られます。それを踏まえて `--allow-hosts` を選んでください。`--allow-hosts '*'` はほかのアプリやサイトの通信も送ることになるので、Reqcove は起動時に警告します。`reqcove capture allow-all` も、しばらくの間そうなります。その答えが警告します。
- `status` と `list_devices` のツールは通信のほかに、ノードの MagicDNS 名（tailnet の名前を含みます）、ノードの tailnet アドレス、デバイスのマシン名も返します。あなたのログイン名は返しません（コードから判断したものです）。
- 送られたものは提供元に残ります。提供元は、受け取ったものを規約が定める期間だけ保持します。
- エージェントの側にも残ります。エージェントは、自分が動くコンピュータに会話を保存します。Claude Code はセッションごとに、ツールの結果も含めて `~/.claude/projects/` の下のファイルに書きます。ほかのエージェントは見ていません。
- これらの写しは Reqcove のものではありません。`run` を止めると Reqcove の記録は消えますが、写しは消えません。`reqcove cleanup` も写しには触れません。
- マスクが見つけられなかったシークレットと、`--no-redact` で読んだものは、そこで読める状態のまま残ります。エージェントがそれをもとに書いたもの（要約、ファイル、コミット）にも残ります。

確認状況：この Mac の Claude Code 2.1 で見ました（2026-11-14）。

### Exit Node の DNS

- **Exit Node を使える tailnet のほかのデバイスも、Exit Node を通して名前を解決できます。** tailnet のポリシーが Exit Node の利用を認めたデバイスなら、どれでも解決できます（Tailscale のコードから判断したものです）。`--dns system` のときや、`--dns` に LAN のリゾルバを指定したときは、ルーターや会社のリゾルバしか知らない名前も引けます。
- **このコンピュータから上流までの DNS は、暗号化されていない平文です。** 応答を DNSSEC で検証することもしません（コードから判断したものです）。そのため、このコンピュータがつながっているネットワーク（Wi-Fi や ISP）には、デバイスが引く名前が見えます。その経路上にいる人は偽の応答を返せます。
- **偽の応答で得られるものは多くありません**（コードから判断したもので、試していません）。HTTPS では、向けた先のサーバーがその名前の証明書を示す必要があります。このコンピュータ、その LAN、ループバックを指す応答は拒否します。平文の HTTP は、どのネットワークでもそうであるように、別の場所へ送られることがあります。

[詳細](guide.ja.md#security-dns)

### Tailscale へのログ

Reqcove のノードは Tailscale にログを送りません。データプレーンの監査ログを必須にしている tailnet には対応していません（`reqcove status` がそう伝えます）。Reqcove がログを有効にすることはありません。

## 保存するものと読める人

鍵とトークンは状態ディレクトリにあります。状態ディレクトリのモードは 0700、中のファイルは 0600 です。つまり、読み書きできるのはあなたの OS ユーザーと、そのユーザーとして動くプロセスだけです。記録そのものはメモリにだけあります。サービスのファイルと Homebrew のログは、状態ディレクトリの外にあります（[`reqcove cleanup` のあとに残るもの](#reqcove-cleanup-のあとに残るもの)）。

| 状態ディレクトリにあるもの | 中身 |
|---|---|
| `mitmproxy/mitmproxy-ca.pem`、`mitmproxy/mitmproxy-ca.p12` | CA とその秘密鍵 |
| `tsnet/` | ノードの鍵と、tsnet 自身のログの行 |
| `ui-token`、`web-token`、`mcp-token` | `--ui`、`--web`、`--mcp-http` のトークン |
| `login-url`、`links` | ログイン待ちの間のログイン用の URL と、`run` の準備ができたあとのトークン付きのリンク |
| `lan-allowed` | LAN モードで許可したアドレス |
| `mitmproxy.log` | mitmproxy のエラーの行だけ |
| `ca-copies`（`~/.reqcove` の中） | CA のコピーを持つ、ほかの状態ディレクトリの一覧 |
| そのほか | mitmproxy のロックファイルとランチャー、SOCKS5 のパスワード、4 つのソケット。`--local-proxy` のときは、元に戻すためのシステムのプロキシ設定 |

Reqcove が確かめるのは状態ディレクトリそのもので、その上のディレクトリは確かめません。状態ディレクトリは、`--state` で指定するものも含めて、あなただけが書き込めるディレクトリの下に置いてください。親ディレクトリで項目の名前を変えられる人は、状態ディレクトリを自分のものに差し替えられます。

### CA の秘密鍵

- `~/.reqcove/mitmproxy/mitmproxy-ca.pem` と、その隣の `mitmproxy-ca.p12`（パスフレーズのない PKCS#12 ファイル）には、あなたの iPhone が信頼する CA の秘密鍵が入っています。この鍵を持つ人はその iPhone に対してどの HTTPS サイトにもなりすませます。
- この CA は使える名前を制限していません（mitmproxy のコードから判断したものです）。CA を信頼したデバイスは、`--allow-hosts` のホストだけでなく、すべての HTTPS サイトについて CA を信頼します。`--allow-hosts` は Reqcove が復号する範囲で、鍵が署名できる範囲ではありません。
- CA は最初の起動時に作られ、有効期間は 10 年です（mitmproxy 12.3.1 が CA に付ける期間で、コードから判断したものです）。期限は `run` と `reqcove status` が表示します。
- 信頼はデバイスからプロファイルを削除するまで続きます。`run` を止めても、`reqcove cleanup` を実行しても、状態ディレクトリを削除しても、信頼は消えません。
- このディレクトリは自分だけのものにしておいてください。Reqcove を使うのをやめるときは、先に iPhone からプロファイルを削除し、それからディレクトリを削除します（手順は `reqcove cleanup` が表示します）。
- ディレクトリを別のコンピュータにコピーすると、鍵もコピーされます。
- `--state` で指定したディレクトリに CA がないときは、そのディレクトリが起動時に `~/.reqcove` の CA のコピーを、鍵も含めて受け取ります。上の「ディレクトリを削除します」は、コピーを受け取ったディレクトリもすべて削除するという意味です。すべてを止めるには、iPhone からプロファイルを削除します。
- バックアップにも鍵が入ります（コードから判断したもので、バックアップの中身は見ていません）。このディレクトリをバックアップから外すか、バックアップも鍵のある場所の 1 つとして扱ってください。

[詳細](guide.ja.md#security-ca-copies)

確認状況：E2E テストが確かめるのは、CA の有効期間が 9 年を超えることだけです。

### ログイン用の URL

ノードがログインしていない間、`reqcove run` はログイン用の URL を表示します。その URL を最初に開いた人の tailnet に、このノードが入ります。Reqcove は `--ui`、`--web`、`--mcp-http` のトークンを含むリンクも、ログイン用の URL と同じように扱います。

- ログイン用の URL とリンクを表示するのは、`run` のターミナルと `reqcove links` だけです。ログの行と MCP ツールには出しません。`status` ツールは、ログイン用の URL がどこで見られるかを伝えるだけで、URL そのものは返しません。そのため、エージェントにも、モデルの提供元にも URL は渡りません。
- `reqcove links` は、出力先がターミナルでないときは断ります。プログラムはターミナルを用意できるので、これはエージェントが実行するのを防ぐ助けにはなっても、保証にはなりません。
- 状態ディレクトリの中では、URL とリンクは 0600 のファイルにあり、あなたのユーザーだけが読み書きできます。0600 が防ぐのはほかのユーザーで、あなたとして動くプログラムではありません。シェルを使えるエージェントは、これらのファイルを読めます。同じディレクトリにあるノードの鍵、トークン、CA の鍵も読めます。

[詳細](guide.ja.md#security-login-url)

### ログ

状態ディレクトリの `mitmproxy.log` に入るのは、mitmproxy のエラーの行だけです。`run` 自身の出力がリダイレクト先やサービスのログのようなファイルのときは、`run` は起動時、最初の行を書く前にそのファイルを 0600 にします。この出力にはトークンもログイン用の URL も入りません。入るのは、`run` がデバイスについてログに出すものです。[詳細](guide.ja.md#security-logs)

### `reqcove cleanup` のあとに残るもの

`reqcove cleanup` は手順を表示するだけで、自分では何も行いません。例外は 1 つで、途中で落ちた `run` が `--local-proxy` に向けたままにしたシステムの Web プロキシは、元に戻します。`--delete-state` を付けると、状態ディレクトリ（ノードの鍵、CA とその鍵、トークン、`lan-allowed`、そこにあるログ）も削除します。ただし、`run` がそのディレクトリを使っているとき、元に戻すプロキシの設定がまだそこにあるとき、そのディレクトリが Reqcove のものでないときは削除しません（コードから判断したものです）。

次のものは、あなたが取り除くまで残ります。それぞれの取り除き方はガイドの[詳細](guide.ja.md#security-cleanup)にあります。

- 各デバイスの CA のプロファイルと、このコンピュータやシミュレーターでの CA の信頼
- tailnet のノード
- ほかの状態ディレクトリ
- サービス
- Skill と、エージェントの MCP サーバーの登録
- Reqcove の外に出たもの（HAR ファイル、エージェントの会話の記録、バックアップ、uv のキャッシュ）

### コンテナで動かす場合

サイトが送ってきたものを開く mitmproxy は、コンテナの中で動きます。mitmproxy に欠陥があっても、届くのはコンテナ（記録と、volume にある CA の鍵）までで、ユーザーのほかのファイルには届きません。イメージにはシェルもパッケージ管理もなく、root ではない専用のユーザーで動きます。その代わり、Docker デーモンのソケットを使える人は、CA の鍵を含めて volume を読めます。コンテナにターミナルを付けたとき（`docker run -t`）は、コンテナを削除するまで、`docker logs` にログイン用の URL、リンク、`--mcp-http` のトークンが残ります。

動かし方は [container.ja.md](container.ja.md) にあります。[詳細](guide.ja.md#security-container)

## 使える人

- **あなたの OS ユーザーを信頼します。** 状態ディレクトリと、その中の MCP ソケットを使えるのは、そのユーザーだけです。そのユーザーとして動くプロセスはどれも、記録と CA の秘密鍵を読めます。Reqcove が守るのは OS ユーザーの境界までで、同じユーザーのプロセスからは記録も鍵も守りません。
- **指定したデバイスは Exit Node を使ってよい相手としてだけ信頼します。** tailnet のほかのデバイスからの通信は、Exit Node でも Remote Proxy でも拒否します。
- **デバイス名は、各デバイスが自分で名乗るものです。** そのため、`--device` にデバイス名を書けるのは、あなた自身のユーザーのデバイスだけです。そのデバイスにも Reqcove のノードにもタグが付いていないことも条件です（タグ付きのノードは、タグを付けた人のユーザー ID を持ち続けます）。ほかのデバイスはマシン名、IP、StableID で指定してください。
- **LAN モード（`--lan`）では、許可したアドレスをプロキシを使ってよい相手として信頼します。** パスワードはありません。信頼するのはアドレスで、デバイスではありません（[LAN モード](#lan-モード--lan)）。

### デバイスから届く範囲

Exit Node と Remote Proxy を通してデバイスから届くのは、公開の IPv4 アドレスです。Reqcove は次のものを拒否します。

- このコンピュータ自身のアドレス（すべてのインターフェイスのもの）と、そのインターフェイスがつながっているネットワーク。そのため、公開アドレスを使う LAN や、クラウドサーバーのサブネットにいる隣のサーバーも拒否します。
- ループバック、プライベートとリンクローカルの範囲、tailnet の範囲、マルチキャスト、そのほかの特殊用途の範囲。
- IPv6 のすべて。

**拾えないもの：あなたのネットワークの公開アドレス。** これは、このコンピュータのインターフェイスのアドレスではありません。デバイスがそのアドレスに接続すると、ルーターがポートフォワーディングで転送する先に届くかもしれません。クラウドサーバーではこのコンピュータに届くかもしれません。テストしていません。

経路、ping、UDP については、ガイドの[詳細](guide.ja.md#security-reach)にあります。

### ほかのユーザーと共有するコンピュータ

Reqcove が信頼するのはあなたの OS ユーザーで、同じコンピュータのほかのユーザーではありません。ほかのユーザーはファイルのモードで締め出します。状態ディレクトリは 0700、中のファイルは 0600 で、そこにある 4 つのソケットも同じです。そのため、ほかのユーザーは記録を読むことも、ツールを呼ぶことも、鍵を取ることもできません（それぞれを作るコードから判断したもので、2 人目のユーザーでは試していません）。それでも、ほかのユーザーには次のことができます。

- `ps` で `run` と mitmproxy のコマンドラインを見ること。デバイス名とホストが出ます。`--mask-names` や `--mask-values` を `@FILE` ではなくコマンドラインに書いたときは、それも出ます（コードから判断したものです）。SOCKS5 のパスワード、トークン、mitmweb のパスワードは出ません。
- `--local-proxy` を通してリクエストを送ること。このポートはどのユーザーのリクエストも受け付けます。
- ノードのポートに接続すること。これは、このコンピュータ自体があなたとして tailnet に入っているときです。`--ui`、`--web`、`--mcp-http` からほかのユーザーを締め出しているのは、トークンです（コードから判断したものです）。
- 状態ディレクトリの外に書いたものを読むこと。HAR ファイルのモードはシェルの設定に従うので、たいていほかのユーザーも読めます。

root と、あなたのユーザーになれる人は対象外です。[詳細](guide.ja.md#security-shared-computer)

### このコンピュータのほかのプロセス

mitmproxy の SOCKS5 のポートは 127.0.0.1 にあり、パスワードで守ります。パスワードは起動のたびに作り、0600 のファイルに保存します。プロセスの引数には入れません。パスワードを知っているのは Reqcove だけなので、ほかのローカルのプロセスはプロキシを使うことも、デバイスになりすますこともできません。Reqcove は `run` の間ずっと、mitmproxy を起動し直す間も含めて、このポートを自分で持ち続けます。パスワードの確認が読み込まれる前に接続を読むことはありません。

あなた自身のユーザーのプロセス（どのみちパスワードのファイルを読めます）と root は対象外です。別のユーザーでは試していません。ポートの持ち方と試したことは、ガイドの[詳細](guide.ja.md#security-other-processes)にあります。

`reqcove capture`（add、remove、set、stop、start、save、allow-all、discover）は、`run` が記録するホストを変えます。使うのは状態ディレクトリの `ctl.sock`（0600、テストで確認）で、MCP ツールのソケットではありません。記録するものを変えるツールはありません。このコマンドは、入力と出力が端末のときだけ動きます。スキルとサーバーの指示は、エージェントにこれを実行しないよう伝えます。端末の確認は間違いを防ぐためのもので、境界ではありません。あなたのユーザーのプロセス（コマンドを実行できるエージェントも含みます）は、端末を与えることも、`ctl.sock` に直接書くこともでき、記録するホストを増やせます。`allow-all` なら、最長 24 時間、すべてのホストです。`run` は届いた要求を自分で確かめ、`"*"`（時間を限った `allow-all --for` は別です）と LAN モードでの変更を拒否します（テストで確認）。変更のたびに、`run` のログの 1 行、source が `cli` のマーカー、`status` の `scope_change` が残ります（E2E テストで確認）。そのため、あなたがしていない変更があれば分かります。

v1.1 からの `reqcove reload` も、同じ道を通り、同じ確認と痕跡があります。config、そのホストのファイル、`--rules` のファイルを読み直し、そのホストとルールを適用します。そのため、これらのファイルに書き込めて、このコマンドを実行できるもの（または `ctl.sock` に書けるもの）は、`--rules-reload` がなくても、`run` が動いている間に、記録するものとリクエストの行き先を変えられます。適用するのはホストとルールだけです。`--no-redact`、`--web` などほかの設定は、再起動するまで変わりません（ほかのフラグがすべて再起動の対象として挙がることは単体テストで確かめました。どれも適用しないことは、コードから判断したものです）。

`reqcove capture stop` は、記録と一緒に `--rules` ファイルも止めます。止めている間は mock、map_local、map_remote、modify_headers、resolve のどのルールも効かず、プリセットも含みます（オフにし、`activate_preset` は拒否します）。そのため、アプリのリクエストは送ったとおりに本物のサーバーへ届きます。mock や map_remote で本番から遠ざけていたテストのリクエストも、そのときは本番に届きます。`stop` の答えはこのことを警告し、`status` は `"recording": "stopped"` を返します（E2E テストで確認：モックしていた URL が、新しい接続でも、止める前に復号した接続でもサーバーに届くこと、プリセットをオンにできないこと）。その間 mitmproxy が復号するのは mitm.it だけで、空のリスト（すべてを復号します）にはしません。止める前に復号した接続は、閉じるまで復号されたままで、記録はしません（E2E テストで確認）。その上の途中のボディも、それ以上コピーしません（単体テストで確認）。`--web` の mitmweb は、その接続の上のリクエストをまだ一覧に出します（マスクなし、ボディはなし。コードから判断したものです）。

`reqcove capture allow-all --for D` は、しばらくの間（最長 24 時間）**すべて**を記録します。`--allow-hosts '*'` と同じです。デバイスのすべてのアプリとサイトの通信で、Apple のホストと `--pass-hosts` のホストだけは別です（E2E テストで確認）。エージェントとそのモデルの提供元が読め、`--upstream-proxy` がオンならそこへ流れ、`--web` がオンなら表示されます（コードから判断したものです）。証明書をピン留めするアプリは、その間失敗します。答えはこのことを警告し、`status` は `"recording": "allow-all"` と `allow_all_until` を返します。
- **時間を限ります：** このコンピュータの時計か、`run` 自身の経過時間の、早いほうで終わります。そのためスリープで延びることはありません。終わるときは安全側に倒れます。先にほかのホストの記録をやめ、それから mitmproxy に伝えます。mitmproxy が答えなければ、allow-all なしで再起動します（単体テストで、どちらの時計でも、その間の `capture stop` でも確認。E2E テストでは、終わる直前に mitmproxy を強制終了し、次に起動したものがほかのホストを復号しないことを確認）。`run` の再起動を越えて続くことはなく、ファイルにも書きません。`capture save` が書くのは許可したホストで、`"*"` は書きません。実際のスリープでは試していません。
- **終わったあとも残ります：** その間の記録は、押し出されるか `run` が止まるまでメモリに残ります（メンテナーの判断です）。そのため、終わったあともエージェントはほかのアプリの通信を読めます。`status` の `records_outside_scope` がその数を数えます。ほかの記録と同じく、`run` を再起動すると消えます。
- **ルール**が効くのは、許可したホストだけです。ホストを名指ししない `modify_headers` ルール（トークンなど）も、ほかのホストには送りません（E2E テストで確認）。
- その間に復号した接続は、終わったあとも閉じるまで復号されたままで、記録はしません（E2E テストで確認）。


`reqcove capture discover --for D`（最長 24 時間）は、しばらくの間、記録しているホストの外でデバイスが接続するホストの**名前**と回数を残します（TLS 接続の SNI と、復号しても記録しない接続の上のリクエストの Host）。中身、URL のパス、時刻は残しません。つまりオンの間、「数えるだけで記録しない」が当てはまるのは、そのホストが運ぶものだけで、名前には当てはまりません。

- **このコンピュータだけ：** 名前が届くのは `reqcove status` と、このコンピュータのエージェント（`status`、`summarize`）だけです。`--mcp-http` と `--ui` のページには届きません（E2E テストで `--mcp-http` と `--ui` が読むものに出ないことを、単体テストで 2 つのサーバーを確認）。エージェントは、通信から来るほかの名前と同じく、これを指示ではなくデータとして読みます。ほかのホストの欄と同じくマスクし、Apple のホストと mitm.it は除きます。ホストを足すコマンドは、普通のホスト名のときだけ Reqcove が組み立てます。
- **時間を限ります。** allow-all と同じで（どちらの時計でも終わり、スリープしても延びません）、終わったあとは、mitmproxy が答えるかどうかにかかわらず、新しい名前を取りません（単体テストで確認）。見えた名前は、`run` が再起動するか、もう一度始めるまでメモリに残ります。ファイルには書きません。上限は 1,000 件です。
- **すべては拾えません：** 名前のない接続、ECH の接続（外側の名前だけ）、スコープの外のホストへの TLS でない接続は見えません（コードから判断したもので、試していません）。オンにできるのは、`reqcove capture` と同じものです（上）。
## マスク

Reqcove が見分けられるシークレットは、届いた時点でマスクします。そのため、どのツールもシークレットを返せません。`--no-redact` を付けると、マスクをしなくなります。

- 名前で見分けます。ヘッダー、クエリパラメータ、ボディのフィールドは、名前がシークレットを表していれば（`token`、`password`、`apiKey` など）、値をマスクします。Cookie の値は名前に関係なくマスクします。
- 形で見分けます。`Bearer`、`Basic`、`Token` の認証情報、JWT、よく知られた接頭辞を持つキーは、どこにあってもマスクします。
- 形式ごとに読みます。JSON、フォーム、テキストの行、GraphQL、XML、HTML と JavaScript、`multipart/form-data`、gRPC、WebSocket のメッセージを、それぞれの形式として読み、シークレットの名前を探します。protobuf（gRPC の protobuf のメッセージも含みます）を名前で読むのは、スキーマ（`--proto`）を渡したときだけです。スキーマがなければ構造だけを表示し、文字列の中身は表示しません。このときは名前でマスクしません。
- 自分の規則でも見分けます。`--mask-names` と `--mask-values` で、名前とパターンを足せます。

対象の語、形、形式ごとの読み方と、それぞれでマスクされずに残るものは、[masking.ja.md](masking.ja.md) にあります。主な抜けは次のとおりです。

- シークレットだと分からない名前の下にあるシークレット（`{"data": "…"}`）。どの形式でも同じです。`--mask-names` や `--mask-values` で足せます。
- メールアドレスや名前などの個人データ。デバッグに必要なので、マスクしません。
- マスクが読まない形式の中のシークレット（`multipart/mixed`、base64 の `SAMLResponse` フォームフィールド）と、名前ではなく位置で渡されるシークレット。
- マスクが見られなかったボディ（テキストでないもの、デコードできなかったもの）。マスクが有効な間は渡しも検索もしません。`--no-redact` を付けると返します。
- マスクが見つけられなかったシークレットは、エージェントとモデルの提供元に残ります（[上記](#エージェントが読んだものの行き先)）。

## 拾えないもの

次の接続は何も残しません。記録もされず、数えられもしません。条件と確かめ方は [masking.ja.md](masking.ja.md#記録が残らない接続) にあります。

- mitmproxy が自分で素通しする接続。Apple のホスト、`--allow-hosts` にないホスト、mitmproxy がアドレスでしか知らない接続です。アドレスでしか知らない接続は、`--allow-hosts` にそのアドレスを書いたときは別です。mitmproxy がアドレスでしか知らないのは、次の 2 種類です。
  - SNI のない TLS。
  - 80 番か 443 番ポートの平文の TCP のうち、最初のバイト列が mitmproxy の読み方では許可したホストを示さないもの。TLS なしの HTTP/2 がその一例です。
- 許可したホストへの HTTP/2 のリクエストのうち、アプリが一覧にない別の名前のために開いた接続に相乗りしたもの。証明書を共有する名前をまとめて許可してください（`*.example.com`）。
- Encrypted Client Hello を使う TLS。プロバイダーの公開名を許可したときは別です。
- 許可したホストへの接続のうち、HTTP/1 の最初のリクエストが `Host` で Apple のホストを指定したもの。接続全体が復号されたまま中継されます。
- アドレスだけで許可したホストへの raw TCP のうち、クライアントが SNI でホストの名前を示したもの。記録は名前で照合するので、`list_passthrough` に出ません。
- TLS のハンドシェイクを終えたあとで Reqcove の証明書を拒否して閉じるクライアントと、リクエストを送らずに閉じるクライアント。証明書を自分で確かめるピンニングのアプリがこれに当たります。ハンドシェイクの途中で拒否するアプリは、一覧に出ます。

## 露出を広げるオプション

オプションごとに、何が見えるようになるか、誰に見えるか、主な限界、あなたがすることを書きます。動作の詳細と確かめたことは、ガイドの各オプションの節にある「セキュリティの詳細」に書いています。

次の 3 つのオプションはノードのポートを開きます。

| オプション | ポート | 届くデバイス | 守るもの |
|---|---|---|---|
| `--ui` | 80 | あなた自身のデバイスと、`--device` のデバイス | トークン（`ui-token`）。Cookie として設定します |
| `--web` | 8081（mitmweb に中継） | あなた自身のデバイス | mitmweb のパスワード（`web-token`） |
| `--mcp-http` | 8090 の `/mcp` | あなた自身のデバイス | トークン（`mcp-token`）。`Authorization: Bearer` で送ります |

どのポートも `Host` でノード（その MagicDNS 名か tailnet アドレス）を指定したリクエストにだけ応答します。トークンは状態ディレクトリの 0600 のファイルに保存し、ログイン用の URL と同じく、`run` のターミナルと `reqcove links` にだけ出ます（[ログイン用の URL](#ログイン用の-url)）。

### mitmweb（`--web`）

mitmweb は通信を**マスクなし**で表示します。mitmproxy が復号したすべてのフローが、ボディも含めて見えます。パスワードを持つ人は誰でも、そのページからリクエストを編集してリプレイでき、オプション（スクリプトを含みます）を変えられます。オプションを変えると、このコンピュータでコードが動きます。mitmweb に接続できるのは、このコンピュータと、ノードを通したあなた自身のデバイスだけです。パスワードは起動し直しても変わりません。変えるには、`web-token` を削除して起動し直します。[詳細](guide.ja.md#security-web)

### ページ（`--ui`）

`--ui` は記録の読み取り専用のページを提供します。中身は MCP ツールが返すものと同じようにマスクされています。ページを読めるのは、あなた自身のデバイスと `--device` のデバイスのうち、トークンを持つブラウザだけです。別のユーザーの `--device` のデバイスに見えるのは、自分のフローだけです。トークンは起動し直しても変わらないので、リンクは `ui-token` を削除して起動し直すまで使えます。Safari の履歴には、表示したページの URL と検索の URL が残ることがあります。[詳細](guide.ja.md#security-ui)

### HTTP 経由の MCP（`--mcp-http`）

ノードはトークンを送ってきたあなた自身のデバイスに MCP ツールを提供します。個人の tailnet では、Grok Bot のように Tailscale の OAuth アプリを通して参加したエージェントのデバイスも、あなた自身のデバイスの 1 つになります。ツールの答えはそのデバイスと、そのモデルの提供元（Grok Bot なら xAI のクラウド）に届きます。返すのはマスクされた同じ記録です。プリセット、ルール、マーカーのツールはありません。エージェントは、あなたが `mcp-token` を削除して `run` を再起動するまで、トークンを持ち続けます。[詳細](guide.ja.md#security-mcp-http)

### ローカルプロキシ（`--local-proxy`）

iOS シミュレーターのような、このコンピュータ自身のアプリのための127.0.0.1:8082 の HTTP プロキシです。パスワードはありません。このコンピュータのプロセスはどのユーザーのものでも、このプロキシを使えます。プロキシが `--allow-hosts` のホストへ送るものは、`local` というデバイスとして記録します。このコンピュータのブラウザで開いたページは、DNS リバインディングで自分のドメイン名を LAN、VPN、tailnet のアドレスに向け、プロキシを通してそのアドレスに届くことができます。`--local-proxy` は、必要な間だけ有効にしてください。Reqcove がこのコンピュータに CA を信頼させることはありません。あなたがこのコンピュータで CA を信頼すると、CA の秘密鍵でこのコンピュータに対してもどの HTTPS サイトにもなりすませるようになります。終わったら信頼を外してください。[詳細](guide.ja.md#security-local-proxy)

### LAN モード（`--lan`）

`run --lan` は tailnet のノードを起動しません。HTTP プロキシがこのコンピュータの LAN のアドレスの 1 つで待ち受けます。パスワードはありません。誰が使えるかはアドレスで決めます。アドレスはデバイスではないので、許可したアドレスをあとで持った人も許可されます。このネットワークでも、同じプレフィックスを持つ別のネットワークでも同じです。許可したアドレスは 80 番と 443 番ポートで公開のアドレスに届きます。プライベートなアドレスに届くのは、`--allow-hosts` に完全な名前で書いたものだけです。このコンピュータと、プロキシのあるネットワークには届きません。LAN モードは信頼できるネットワークで使い、終わったら止めてください。[詳細](guide.ja.md#security-lan)

### 上流プロキシ（`--upstream-proxy`）

このオプションを付けると、復号した HTTP(S) のリクエストは上流プロキシを経由して送られます。プロキシには、リクエストとレスポンスがマスクなしで見えます（たとえば Burp は、それをプロジェクトとしてディスクに保存します）。本物のサーバーの証明書を検証するのも、プロキシの仕事になります。どこに接続するかも、プロキシが決めます。Burp は名前をこのコンピュータでもう一度引くので、このコンピュータの LAN の中に解決される名前は、Exit Node の拒否をすり抜けて LAN に届きます。`--allow-hosts` は狭くしておき、プロキシはこのコンピュータか tailnet に置いてください。[詳細](guide.ja.md#security-upstream-proxy)

### ルール（`--rules`）

ルールはあなたのもので、`run` の起動時にファイルから読みます。ルールを書いたり変えたりする MCP ツールはありません。他人が作ったルールファイルは、他人が作ったプログラムと同じです。あなたのアプリのリクエストを、Cookie やトークンも含めて、どこへでも送れます。`map_remote` と `resolve` はこのコンピュータから接続します。接続先にはこのコンピュータと LAN も含まれます。`mock` はサイトの名前で応答します。`--rules-reload` を付けると、ファイルに書き込めるもの（ファイルを扱えるエージェントも含みます）は、`run` が動いている間に、デバイスのリクエストの行き先を変えられます。付けなくても、ファイルに書き込めて `reqcove reload`（v1.1 から、[上](#このコンピュータのほかのプロセス)）を実行できるものは同じことができます。reqcove が mitmproxy を起動し直すときは、最後に読み込めたルールを非公開のコピー（0600。トークンも入ります。`run` が止まるときに消します）から渡します。そのルールが読み込めなくなったら、ルールなしで続けずに `run` が止まります。[詳細](guide.ja.md#security-rules)

### モックのプリセット

ルールファイルで `preset: NAME` を付けたモックは、エージェントが `activate_preset` で有効にするまで何もしません。プリセットを書いた時点で、エージェントがそれを有効にしてよいと、あなたが同意したことになります。エージェントが有効にできるのは、あなたが書いたものだけです。有効にできるのは 1 回につき最長 5 分で、有効にし直す回数に上限はありません。サイトが記録に書き込んだ文が、そうするようエージェントを誘導しようとすることがあります。読み取りのツールは名前で個別に許可してください。`"mcp__reqcove"` をまとめて許可したクライアントは、確認なしでプリセットを有効にします。[詳細](guide.ja.md#security-mock-presets)

### map_remote、modify_headers、resolve のプリセット

これらの種類のプリセットは有効な間、デバイスのリクエストの行き先や中身を変えます。`map_remote` のプリセットは一致したリクエストを、アプリの Cookie、トークン、ログインのボディと一緒に、あなたが書いた送り先へ送ります。エージェントは送り先を選べません。選べるのは、いつ有効にするかだけです。考えておくべき危険は古くなった送り先です。今は別の人が持っている、古いトンネルやステージングの名前がこれに当たります。プリセットは 5 分で無効になりますが、有効な間にアプリが送り先で受け取ったものは、無効になったあともアプリが持ち続けるかもしれません。[詳細](guide.ja.md#security-presets)

### フラグのファイル（`--config`）

`run --config FILE`（`brew services` と `reqcove service install` のためのもの）は、`run` のフラグをファイルから読みます。つまり、そのファイルに書き込めるものが、次の起動のフラグを決めます。v1.1 から、引数をまったく付けない `reqcove run` も `~/.config/reqcove/config`（なければ Homebrew の `etc/reqcove/config`）を同じ確認をして読みます。ファイルはあなたのもので、あなただけが読めるものでなければなりません。次の 5 つのフラグはファイルに書いても受け付けないので、コマンドラインで指定してください。`--no-redact`、`--web`、`--allow-hosts '*'`、`--rules-reload`、`--lan` です。v1.1 から、`reqcove setup` はホストをその隣のファイル（`hosts`、0600）に書き、フラグのファイルは `--allow-hosts=@FILE` でそれを読みます。そのファイルに書き込めるものも、次の起動で何を記録するかを決めます。`run` はこのファイルの持ち主もパーミッションも確かめません（コードから判断したものです）。`reqcove capture save` は、あなたの普通のファイルであるときだけ書きます。[詳細](guide.ja.md#security-config)

## プロンプトインジェクション

記録の中身は、ほかの人が書いたものです。レスポンスのボディ、レスポンスのヘッダー、ステータスの理由の文、リダイレクト先、エラーメッセージは、リモートのサイトが書きます。そこには、エージェントを誘導するための文が入っているかもしれません。アプリは自分の User-Agent、TLS の名前、送る JSON のキーを選びます。tailnet のピアは自分のデバイス名を選びます。

- Reqcove のツールは読むだけですが、例外が 1 つあります。エージェントは、あなたがプリセットにしたルールを有効にできます（[モックのプリセット](#モックのプリセット)、[ほかの種類のプリセット](#map_remotemodify_headersresolve-のプリセット)）。ルールを書いたり変えたりするツールはありません。プリセットがなければ、エージェントが何を呼んでも通信は変わりません。
- エージェントはほかのツールも持っているかもしれません。シェル、ファイルの書き込み、ネットワーク、ほかの MCP サーバーです。サイトが記録に書き込んだ文は、それらを使うようエージェントを誘導しようとすることがあります（Cookie をどこかへ送る、ファイルを編集する）。Reqcove の側からはこれを止められません。止められるのはエージェント自身の設定です。
- Reqcove を読むエージェントには、作業に必要なものだけを与えてください。Reqcove を読んであなたに答えるだけのエージェントが、いちばん安全な形です。Claude Code では Reqcove の読み取りのツールを名前で許可し（`activate_preset` は入れません）、シェルのコマンドやネットワークのツールを一緒に許可しないでください。Codex ではサンドボックスと承認を残してください。
- サイト、アプリ、tailnet が書いたものを返すツールは、どれも説明の中で、それがデータで指示ではないと伝えています。すべてのクライアントに送られるサーバーの instructions も、同じことを伝えています。モデルがこれを守るかどうかは、テストでは示せません。
- 記録からは証明できないこともあります。フローのホストは、アプリが選ぶリクエストの Host です。マーカーの `source` が示すのは経路で、誰が置いたかの証明にはなりません。

[詳細](guide.ja.md#security-agent)

## mitmproxy 自身のコード

mitmproxy とその依存パッケージ（44 個）は、Reqcove に組み込まれたロックファイルから来ます。`run` は `uv run --locked --script` で mitmproxy を起動します。このコマンドはロックに書かれたファイルだけをインストールし、それぞれのハッシュを確かめます。CI は、ロックに既知の脆弱性がないかを監査します（pip-audit）。

- 素の `uvx` はハッシュを与えられても確かめません。素の `uvx` を使うのは、別の `--mitmproxy-spec` を指定したときと、`--uvx` のファイル名が `uvx` でないときです。
- ロックはバージョンを 1 つ上書きしています。mitmproxy 12.3.1 は mitmweb のサーバーである tornado を 6.5.10 までに制限しています。監査は 6.5.10 に 3 つの脆弱性を見つけました。6.6 でその 3 つは直りましたが、6.6 自体には CVE-2026-126347 があるので、ロックは 6.6.1 に固定しています。この組み合わせで mitmproxy 自身のテストは実行していません。

[詳細](guide.ja.md#security-mitmproxy-code)

## あなたの責任

次のことは、Reqcove ではなくあなたが行います。

- **同意を得る。** ほかの人のデバイスを中継して記録するのは、その人の同意があるときだけにしてください（[下記](#ほかの人のデバイス)）。
- **CA を片付ける。** 使うのをやめるときは、各デバイスからプロファイルを削除してください。状態ディレクトリと、そのコピーやバックアップは、人に渡さないでください（[CA の秘密鍵](#ca-の秘密鍵)、[`reqcove cleanup` のあとに残るもの](#reqcove-cleanup-のあとに残るもの)）。
- **共有のコンピュータに気を付ける。** ほかのユーザーに見えるものと届くものがあります（[ほかのユーザーと共有するコンピュータ](#ほかのユーザーと共有するコンピュータ)）。
- **エージェントが読めるものとできることを絞る。** `--allow-hosts` を狭くし、エージェントには作業に必要なツールだけを与えてください（[プロンプトインジェクション](#プロンプトインジェクション)）。

### ほかの人のデバイス

`--device` にはあなたのものではないデバイスも指定できます。LAN モードは、あなたが許可したアドレスなら何でも中継します。

- デバイスを中継して記録するのは、それを使う人の同意があるときだけにしてください。
- 許可したホストへのリクエストは、復号されて記録されます。エージェントがそこから読んだものは、モデルの提供元に送られます。
- そのデバイスはプロファイルを削除するまで、あなたが鍵を持つ CA をすべてのサイトについて信頼します（[CA の秘密鍵](#ca-の秘密鍵)）。
- Reqcove は誰にも尋ねず、同意があるかどうかも確かめません（コードから判断したものです）。
- 同意なしに人の通信を記録することは、あなたのいる場所の法律に反するかもしれません。
- あなた自身のデバイスの通信にも、チャットのメッセージのように、ほかの人の言葉が入っています。個人データはマスクしません。
