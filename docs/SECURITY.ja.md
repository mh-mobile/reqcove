# Reqcove のセキュリティモデル

[English](SECURITY.md)

Reqcove はスマートフォンの HTTPS を復号し、読んだものを AI エージェントに渡します。このページでは、Reqcove が何を守り、何を信頼し、何をしようとしていないかを説明します。対象は v1.0 です。形式ごとにマスクが何を見つけるかと、記録が残らない接続は、[masking.ja.md](masking.ja.md) にまとめています。

試していない点と、コードから判断した点には、その場所にそう書いています。テストや実機で確かめたことは、各節の最後の「確認状況」に書いています。試した環境は、ほかの記載がなければ mitmproxy 12.3.1、iOS 27.3 の iPhone、macOS です。

このページで使う言葉を 2 つ説明します。**状態ディレクトリ**は `~/.reqcove` か、`--state` で指定したディレクトリです。**あなた自身のデバイス**は、Reqcove のノードと同じユーザーで tailnet に入っていて、どちらにもタグが付いていないデバイスです。Reqcove はこれを、接続が開くときとリクエストのたびに確かめます。

## 脆弱性の報告

公開の issue ではなく、このリポジトリの GitHub のプライベート脆弱性レポート（private vulnerability reporting）を使ってください。

## スマートフォンから出ていくものとその行き先

### 記録するもの

- 記録するのは、`--allow-hosts` にあって `--pass-hosts` にないホストへのリクエストだけです。これを 2 つの確認で守ります。mitmproxy はほかの接続を復号せずに通し、Reqcove はリクエストごとに Host をもう一度確かめます。
- Apple のホストへの接続は、常に復号せずに通します。
- 許可したホストへの接続が、ほかのホストへのリクエストを運ぶことがあります（HTTP/2 の接続の再利用）。そのリクエストは接続と一緒に復号されます。記録はしませんが、`--web` には表示され、`--upstream-proxy` に転送されることがあります。
- 一覧にないホストへのリクエストと TLS の失敗は、数えるだけで記録しません。
- `--pass-hosts` のホストと、mitmproxy が raw TCP として運ぶ接続は、接続の記録だけを残します。中身は残しません（[詳細](masking.ja.md#中身なしで記録する接続)）。
- 記録がまったく残らない接続もあります（[拾えないもの](#拾えないもの)）。
- シークレットは届いた時点でマスクします（[マスク](#マスク)）。
- ボディを返すのは、ツールがボディを求められたとき（`get_flow` と `search_flows` の `bodies`）と、ボディを比べる `diff_flows` だけです。
- 記録はメモリにあります。上限はフロー 10,000 件とテキスト 64 MiB で、`reqcove run` が止まると消えます。Reqcove 自身はフローをディスクに書きません（[上限](masking.ja.md#記録が保持するもの)）。
- `reqcove har > FILE` は、あなたが指定した先に記録を書きます。中身はツールが返すものと同じようにマスクされています。ファイルのモードはシェルの設定に従うので、ほかのユーザーが読めることがよくあります。状態ディレクトリのモードは 0700 です。
- Reqcove は DNS を記録しません。

### エージェントが読んだものの行き先

- ツールが返すものはすべて、エージェントのモデルの提供元に送られます。それを踏まえて `--allow-hosts` を選んでください。`--allow-hosts '*'` はほかのアプリやサイトの通信も送ることになるので、Reqcove は起動時に警告します。
- `status` と `list_devices` のツールは、通信のほかに、ノードの MagicDNS 名（tailnet の名前を含みます）、ノードの tailnet アドレス、デバイスのマシン名も返します。あなたのログイン名は返しません（コードから判断したもので、試していません）。
- 送られたものは提供元に残ります。提供元は、受け取ったものを規約が定める期間だけ保持します。
- エージェントの側にも残ります。エージェントは、自分が動くコンピュータに会話を保存します。Claude Code は、セッションごとに、ツールの結果も含めて `~/.claude/projects/` の下のファイルに書きます。ほかのエージェントは見ていません。
- これらの写しは Reqcove のものではありません。`run` を止めると Reqcove の記録は消えますが、写しは消えません。`reqcove cleanup` も写しには触れません。
- マスクが見つけられなかったシークレットと、`--no-redact` で読んだものは、そこで読める状態のまま残ります。エージェントがそれをもとに書いたもの（要約、ファイル、コミット）にも残ります。

確認状況：この Mac の Claude Code 2.1 で見ました（2026-11-14）。

### Exit Node の DNS

- Exit Node はそれを使うデバイスに DNS over HTTPS（Tailscale の PeerAPI）で応答します。Exit Node を使える tailnet のほかのデバイスも、Exit Node を通して名前を解決できます（Tailscale のコードから判断したもので、tailnet のポリシーが Exit Node の利用を認めたピアには、どれにでも応答します）。
- そのデバイスが問い合わせる上流は、あなたのデバイスと同じです。デフォルトでは `1.1.1.1` です。`--dns system` のときや、`--dns` に LAN のリゾルバを指定したときは、上流はルーターや会社のリゾルバになり、そのリゾルバしか知らない名前も引けます。
- このコンピュータから上流までの DNS は、Exit Node でも Remote Proxy でも、暗号化されていない平文です。応答を DNSSEC で検証することもしません（コードから判断したもので、試していません）。そのため、このコンピュータがつながっているネットワーク（Wi-Fi や ISP）には、デバイスが引く名前が見えます。その経路上にいる人は偽の応答を返せます。
- 経路の外からは偽の応答を返すのは難しくなっています。問い合わせごとにランダムな ID とランダムなポートを使い、ほかのアドレスからの応答は捨てるからです。
- 偽の応答で得られるものは多くありません（コードから判断したもので、試していません）。HTTPS では、その名前の証明書を示す必要があります。復号するホストでは mitmproxy が、ほかのホストではスマートフォン自身が証明書を確かめます。このコンピュータ、その LAN、ループバックを指す応答は、そこへのほかの接続と同じく拒否します。平文の HTTP はどのネットワークでもそうであるように、別の場所へ送られることがあります。
- 名前を隠すにはローカルの DNS over HTTPS の中継を `--dns 127.0.0.1:PORT` として使う方法が考えられます。これは試していません。

確認状況：テスト（このコンピュータ、その LAN、ループバックを指す応答を拒否すること）。`--device` に入っていないこのコンピュータに Exit Node が応答することは、試して確かめました。

### Tailscale へのログ

Reqcove のノードは、Tailscale にログを送りません。データプレーンの監査ログを必須にしている tailnet には対応していません（`reqcove status` がそう伝えます）。Reqcove がログを有効にすることはありません。

## 保存するものと読める人

Reqcove がディスクに保存するものは、状態ディレクトリにあります。状態ディレクトリのモードは 0700、中のファイルは 0600 です。つまり、読み書きできるのはあなたの OS ユーザーと、そのユーザーとして動くプロセスだけです。記録そのものはメモリにだけあります。

| 状態ディレクトリにあるもの | 中身 |
|---|---|
| `mitmproxy/mitmproxy-ca.pem`、`mitmproxy/mitmproxy-ca.p12` | CA とその秘密鍵 |
| `tsnet/` | ノードの鍵と、tsnet 自身のログの行 |
| `ui-token`、`web-token`、`mcp-token` | `--ui`、`--web`、`--mcp-http` のトークン |
| `login-url`、`links` | ログイン待ちの間のログイン用の URL と、`run` の準備ができたあとのトークン付きのリンク |
| `lan-allowed` | LAN モードで許可したアドレス |
| `mitmproxy.log` | mitmproxy のエラーの行だけ |
| `ca-copies`（`~/.reqcove` の中） | CA のコピーを持つ、ほかの状態ディレクトリの一覧 |
| そのほか | mitmproxy のロックファイルとランチャー、SOCKS5 のパスワード、3 つのソケット。`--local-proxy` のときは、元に戻すためのシステムのプロキシ設定 |

Reqcove が確かめるのは状態ディレクトリそのもので、その上のディレクトリは確かめません。状態ディレクトリ（と `--state`）は、あなただけが書き込めるディレクトリの下に置いてください。親ディレクトリで項目の名前を変えられる人は、状態ディレクトリを自分のものに差し替えられます。

### CA の秘密鍵

- `~/.reqcove/mitmproxy/mitmproxy-ca.pem` と、その隣の `mitmproxy-ca.p12`（パスフレーズのない PKCS#12 ファイル）には、あなたの iPhone が信頼する CA の秘密鍵が入っています。これを持つ人はその iPhone に対してどの HTTPS サイトにもなりすませます。
- この CA は使える名前を制限していません（mitmproxy のコードから判断したもので、試していません）。CA を信頼したデバイスは、`--allow-hosts` のホストだけでなく、すべての HTTPS サイトについて CA を信頼します。`--allow-hosts` は Reqcove が復号する範囲で、鍵が署名できる範囲ではありません。
- CA は最初の起動時に作られ、有効期間は 10 年です（mitmproxy 12.3.1 が CA に付ける期間で、コードから判断したものです）。期限は `run` と `reqcove status` が表示します。
- 信頼はデバイスからプロファイルを削除するまで続きます。`run` を止めても、`reqcove cleanup` を実行しても、状態ディレクトリを削除しても、信頼は消えません。
- このディレクトリは自分だけのものにしておいてください。Reqcove を使うのをやめるときは、先に iPhone からプロファイルを削除し、それからディレクトリを削除します（手順は `reqcove cleanup` が表示します）。
- ディレクトリを別のコンピュータにコピーすると、鍵もコピーされます。

ほかの状態ディレクトリにあるコピーには、次の点があります。

- CA のない `--state` のディレクトリは、起動時に `~/.reqcove` の CA のコピーを受け取ります（1 台のコンピュータで複数の Exit Node を動かしても、iPhone のプロファイルは 1 つで済みます）。コピーするのは鍵の入った `mitmproxy-ca.pem` と証明書のファイルです。`mitmproxy-ca.p12` と mitmweb のパスワードはコピーしません。コピーした先は `run` がログに出します。
- 鍵はそのディレクトリのそれぞれに入ります。どのディレクトリも 0700 で、ファイルは 0600 です。1 つを削除しても、ほかのディレクトリに鍵が残ります。上の「ディレクトリを削除します」は、そのすべてを削除するという意味です。すべてを止めるにはiPhone からプロファイルを削除します。
- コピーの一覧は `~/.reqcove/ca-copies` にあります。`~/.reqcove` に対する `cleanup` は、まだ CA を持っているディレクトリを挙げます。コピーに対する `cleanup` は、プロファイルが両方に使われていることを伝えます。
- どのコマンドも、`~` で始まる `--state` を断ります。`--state=~/x` はシェルが展開しないので、鍵が `./~/x` に置かれ、`cleanup` が本物のディレクトリを「ない」と報告してしまうからです。

バックアップには、次の点があります。

- バックアップにも鍵が入ります。Reqcove は状態ディレクトリの中のものにバックアップ対象外の印を付けません（コードから判断したもので、バックアップの中身は見ていません）。Time Machine や、ホームを対象にするほかのバックアップや同期のツールは、CA の鍵、ノードの鍵（`tsnet/`）、トークンをコピーし、`cleanup --delete-state` のあとも持ち続けます。
- このディレクトリをバックアップから外すか、バックアップも鍵のある場所の 1 つとして扱ってください。
- 復元でモードが広がることがあります。`run` は起動時に、ディレクトリを 0700 に、トークンのファイルを 0600 に戻します。ほかのファイルは戻しません（コードから判断したもので、試していません）。

確認状況：テスト（コピーのディレクトリが 0700、ファイルが 0600 であること。E2E テストが確かめるのは、CA の有効期間が 9 年を超えることだけです）。

### ログイン用の URL

ノードがログインしていない間、`reqcove run` はログイン用の URL を表示します。それを最初に開いた人が、このノードを自分の tailnet に入れることになります。`--ui`、`--web`、`--mcp-http` のトークンを含むリンクも、同じように扱います。

- 表示するのはターミナルだけです。 ログイン用の URL とリンクは、`run` のターミナルと `reqcove links` にだけ出ます。ログの行と MCP ツールには出しません。`status` ツールは、ログイン用の URL がどこで見られるかを伝えるだけで、URL そのものは返しません。そのため、エージェントにも、モデルの提供元にも URL は渡りません。
- **ターミナルでないところ**（サービス、`-t` なしの `docker logs`、エージェントのシェル）では、`run` は URL もリンクも表示しません。`reqcove links` で表示できることだけを伝えます。
- `reqcove links` は、出力先がターミナルでないときは断ります。 これはエージェントが実行するのを防ぐ助けで、保証ではありません（プログラムはターミナルを用意できます）。Skill とサーバーの instructions は、エージェントに、これを実行しないよう伝えています。
- `run` がログに出す行と、終了時のエラーは、すべて 1 つのフィルターを通ります。 フィルターは、トークン、`run` がすでに見たログイン用の URL、コントロールサーバーのログイン用の URL の形をした URL（Tailscale の `/a/<hex>`、Headscale の `/register/…` と `/register?key=…`）を置き換えます。`--verbose` のときは、tsnet 自身の行も対象です。tsnet は、`run` が URL を知る前に URL を出力するからです。
- フィルターが知っている形はこれだけです。 ほかの形のログイン用の URL は、`run` の最初のポーリング（3 秒以内）からマスクします。
- **`login-url` と `links`** は 0600 のファイルで、`run` の起動時と終了時に削除します。クラッシュしたあとは次の起動まで残ります。`reqcove links` は、`run` が動いているかどうかを確かめないからです。
- tsnet は自分の行をバッファのファイルに保存します。 ログイン用の URL もそこに入ります（`tsnet/tailscaled.log*.txt`、0600）。`--verbose` を付けないときも同じです（コードから判断したもので、試していません）。
- 0600 が防ぐのはほかのユーザーで、あなたとして動くプログラムではありません。 シェルを使えるエージェントは、これらのファイルを読めます。同じディレクトリにあるノードの鍵、トークン、CA の鍵も読めます。
- mitmweb のサーバーは、失敗したリクエストの URL を `mitmproxy.log` に書きます。 URL には `?token=` も含まれますが、アドオンが先にトークンをマスクします。

確認状況：テスト（テスト用のコントロールサーバーから tsnet の行を読むテストと、mitmweb の E2E テストでの `mitmproxy.log` の確認）。Claude Code の `!` で `reqcove links` を実行しても何も出ないことを試しました（2026-11-13）。

### ログ

- `mitmproxy.log` に入るのは、mitmproxy のエラーの行だけです。
- `run` 自身の出力がファイルのときは、`run` が起動時に、最初の行を書く前にそのファイルを 0600 にします。リダイレクト先のファイルも、brew services の `$(brew --prefix)/var/log/reqcove.log`（launchd は 0644 で作ります）も対象です。
- `reqcove setup` は、サービスを最初に起動する前に brew のログを 0600 にします。`reqcove service install` も、自分の `service.log` を同じように 0600 にします。brew services では試していません。
- この出力にはトークンもログイン用の URL も入りません。入るのは、`run` がデバイスについてログに出すものです。

確認状況：テスト（失敗したリクエストや不正な形のリクエストで送ったシークレットが `mitmproxy.log` に届かないこと。`run` が出力を 0600 にすること。サービスのログを作ること）。

### `reqcove cleanup` のあとに残るもの

`reqcove cleanup` は手順を表示するだけで、自分では何も行いません。例外は 1 つで、途中で落ちた `run` が `--local-proxy` に向けたままにしたシステムの Web プロキシは、元に戻します。`--delete-state` を付けると、状態ディレクトリ（ノードの鍵、CA とその鍵、トークン、`lan-allowed`、そこにあるログ）も削除します。ただし、`run` がそのディレクトリを使っている間、元に戻すプロキシの設定がまだそこにある間、Reqcove のものでないディレクトリは削除しません（コードから判断したものです）。

次のものは、あなたが取り除くまで残ります。

- **各デバイスの CA のプロファイルと、このコンピュータやシミュレーターでの CA の信頼。** cleanup は、iPhone、シミュレーター、Mac のキーチェーンについて方法を表示しますが、どれも自分では行いません。ほかの場所に足した信頼（Linux の証明書ストア、ブラウザ独自のストア、Android）は、cleanup には分かりません。
- **tailnet のノード**（管理コンソールの Machines）と、スマートフォンで選んだ Exit Node や Wi-Fi プロキシ。
- **ほかの状態ディレクトリ**（`--state`）。クリーンアップはディレクトリごとに行います。`~/.reqcove` に対する cleanup が挙げるのは、その CA のコピーを持つディレクトリだけです。
- **サービス。** cleanup はサービスに触れません。`reqcove service uninstall` はサービスを止めてそのファイルを削除しますが、フラグのファイル（`~/.config/reqcove/config`）は残します。`brew services stop reqcove` は Homebrew のサービスを止めますが、そのフラグのファイルとログ（`$(brew --prefix)/var/log/reqcove.log`）は残ります。サービスを残しておくと、次のログインで `run` が起動し、状態ディレクトリと新しい CA を作り直します。
- **Skill**（`reqcove init --uninstall` で削除します）と、エージェントの MCP サーバーの登録。
- **Reqcove の外に出たもの。** HAR ファイル、エージェントの会話の記録（[上記](#エージェントが読んだものの行き先)）、バックアップ、uv のキャッシュにある mitmproxy と Python です。

確認状況：テスト（削除を断る場合、プロキシを元に戻すこと、CA のコピーを持つディレクトリを挙げること）。

### コンテナで動かす場合

動かし方は [container.ja.md](container.ja.md) にあります。

- サイトが送ってきたものを開く mitmproxy は、コンテナの中で動きます。mitmproxy に欠陥があっても、届くのはコンテナ（記録と、volume にある CA の鍵）までで、ユーザーのほかのファイルには届きません。
- イメージにはシェルもパッケージ管理もなく、root ではない専用のユーザーで動きます。
- その代わり、Docker デーモンのソケットを使える人は、CA の鍵を含めて volume を読めます。
- コンテナにターミナルを付けたとき（`docker run -t`）は、コンテナを削除するまで、`docker logs` にログイン用の URL、`--ui`/`--web` のリンク、`--mcp-http` のトークンが残ります。ターミナルを付けなければ、`run` はそれらの代わりに `reqcove links` を案内します。
- `reqcove mcp` は `--log-driver none` で動かすので、ツールの答えはログに残りません。

確認状況：`scripts/container-smoke.sh`（状態ディレクトリの持ち主とモード。ネットワークは不要です）。攻撃を試して確かめたものではありません。

## 使える人

- あなたの OS ユーザーを信頼します。 状態ディレクトリと、その中の MCP ソケットを使えるのは、そのユーザーだけです。そのユーザーとして動くプロセスはどれも、記録と CA の秘密鍵を読めます。Reqcove はそれより強いことは約束しません。
- 指定したデバイスはExit Node を使うことについてだけ信頼します。 tailnet のほかのデバイスからの通信は、Exit Node でも Remote Proxy でも拒否します。
- デバイス名は、各デバイスが自分で名乗るものです。 そのため、`--device` にデバイス名を書けるのは、あなた自身のユーザーのデバイスだけです。そのデバイスにも Reqcove のノードにもタグが付いていないことも条件です（タグ付きのノードは、タグを付けた人のユーザー ID を持ち続けます）。ほかのデバイスは、マシン名、IP、StableID で指定してください。
- LAN モード（`--lan`）では、許可したアドレスを、プロキシを使うことについて信頼します。 パスワードはありません。信頼するのはアドレスで、デバイスではありません（[LAN モード](#lan-モード--lan)）。

### デバイスから届く範囲

Exit Node と Remote Proxy を通してデバイスから届くのは、公開の IPv4 アドレスです。Reqcove は次のものを拒否します。

- このコンピュータ自身のアドレス（すべてのインターフェイスのもの）と、そのインターフェイスがつながっているネットワーク。そのため、公開アドレスを使う LAN や、クラウドサーバーのサブネットにいる隣のサーバーも拒否します。
- ループバック、プライベートとリンクローカルの範囲、tailnet の範囲、マルチキャスト、そのほかの特殊用途の範囲。
- IPv6 のすべて。

ほかに次の点があります。

- 経路を通してだけ届く公開のネットワーク（ルーターの先にあって、インターフェイスのサブネットではないもの）は拒否しません（コードから判断したもので、試していません）。
- ping（ICMP echo）にも同じ規則を使います。`--device` にないデバイスからの ping と、拒否するアドレスへの ping は捨てます。一覧にあるデバイスから公開アドレスへの ping には、このコンピュータから ping を打って応答します（コードから判断したもので、試していません）。
- デバイスの UDP のフローが続いている間（最後のパケットから 2 分、DNS では 30 秒）、そのフローを通して応答できるのは、送り先のアドレスとポートだけです。ほかから、このコンピュータのそのポートに届いたデータグラムは捨てます。
- **拾えないもの：あなたのネットワークの公開アドレス。** これは、このコンピュータのインターフェイスのアドレスではありません。そこへ接続したデバイスは、ルーターが転送する先（ポートフォワーディング）や、クラウドサーバーではこのコンピュータに届くかもしれません。テストしていません。

確認状況：テスト（`--device` にないデバイスと、一覧にあるデバイスの両方から 127.0.0.1 へ ping を送るテスト。このコンピュータからデータグラムを 1 つ送るテスト）。

### ほかのユーザーと共有するコンピュータ

Reqcove が信頼するのはあなたの OS ユーザーで、同じコンピュータのほかのユーザーではありません。ほかのユーザーはファイルのモードで締め出します。状態ディレクトリは 0700、中のファイルは 0600 で、そこにある 3 つのソケット（MCP ツールのものと、mitmproxy の 2 つ）も同じです。そのため、ほかのユーザーは、記録を読むことも、ツールを呼ぶことも、鍵を取ることもできません（それぞれを作るコードから判断したもので、2 人目のユーザーでは試していません）。それでも、ほかのユーザーに見えるものと届くものがあります。

- **`ps`。** `run` と mitmproxy のコマンドラインが見えます。そこには、デバイス名、`--allow-hosts` と `--pass-hosts` のホスト、ルールファイルと状態ディレクトリのパス、上流プロキシのアドレスが出ます。`--mask-names` や `--mask-values` を `@FILE` ではなくコマンドラインに書いたときは、それも出ます（コードから判断したもので、試していません）。SOCKS5 のパスワード、トークン、mitmweb のパスワードは出ません。これらは 0600 のファイルで渡すからです。
- **`--local-proxy`。** このポートは、どのユーザーのリクエストも受け付け、許可したホストへのものを `local` として記録します（[下記](#ローカルプロキシ--local-proxy)）。mitmproxy の SOCKS5 のポートと mitmweb のポートも 127.0.0.1 にありますが、パスワードで守られています（[下記](#このコンピュータのほかのプロセス)）。
- **ノードのポート。** このコンピュータ自体が、あなたとして tailnet に入っているときの話です。ノードが見分けるのはデバイスで、このコンピュータのユーザーではありません。そのため、ほかのユーザーのプログラムは、あなた自身のデバイスの 1 つとして `--ui`、`--web`、`--mcp-http` に届きます。このコンピュータが `--device` に入っていれば、Exit Node と Remote Proxy にも届きます。最初の 3 つからほかのユーザーを締め出しているのは、トークンです（コードから判断したもので、2 人目のユーザーでは試していません）。
- **状態ディレクトリの外に書いたもの。** HAR ファイルのモードはシェルの設定に従うので、たいていほかのユーザーも読めます。`/tmp` は全員が使う場所です。`(umask 077; reqcove har > FILE)` とすれば、新しいファイルは 0600 になります（zsh で試しました）。サービスのファイル（LaunchAgent、systemd のユニット）は 0644 です。そこに入るのはパスで、トークンは入りません（コードから判断したもので、試していません）。

対象外：root と、あなたのユーザーになれる人。

### このコンピュータのほかのプロセス

- mitmproxy の SOCKS5 のポートは、パスワードで守ります。 ポートは 127.0.0.1 にあります。パスワードは起動のたびに作り、0600 のファイルに保存します。プロセスの引数には入れません。パスワードを知っているのは Reqcove だけなので、ほかのローカルのプロセスは、プロキシを使うことも、デバイスになりすますこともできません。
- ポートは、`run` の間ずっと Reqcove が持ち続けます。 Reqcove は自分でポートを bind します。bind は `run` ごとに 1 回です。待ち受けているソケットは、起動する mitmdump のそれぞれに渡します。mitmproxy（12.3.1）にはそのためのオプションがないので、Reqcove のランチャー（`mitm.py`。別の `--mitmproxy-spec` でも使います）が、mitmproxy に自分で bind させず、渡したソケットで待ち受けさせます。mitmdump が落ちると、Reqcove はポートを持ったまま mitmdump を起動し直します（`ps` で見えます）。そのため、その合間にも、最初の mitmdump の前にも、ほかのプロセスがそのポートの 127.0.0.1 を取ることはできません。
- その間に来た接続はソケットのキューで次の mitmdump を待ちます。 デバイスの接続は、アドオンが hello を送るまで待ちます（最長 15 秒で、それを過ぎると失敗します）。
- キューにある接続を、パスワードの確認が読み込まれる前に読むことはありません。 mitmproxy は `proxyauth=any` で動き、パスワードを確かめるのは Reqcove のアドオンだけです。そこで、ランチャーは mitmproxy に、accept をしないままソケットの上にサーバーを作らせます。アドオンは、読み込まれたとき、hello の直前に accept を始めます。
- **ランチャーの変更が当たらなかったとき**（mitmproxy が別の方法で bind するとき）は、mitmproxy 自身の bind が、Reqcove の持つポートで失敗します。mitmproxy は hello の前に終了し、準備完了にはなりません。
- 別のユーザーでは試していません。 macOS と Linux のカーネルの文書によると（ここでは確かめていません）、2 つ目のソケットがそのアドレスを取れるのは、両方のソケットが SO_REUSEPORT を設定したときだけです（Linux では同じユーザーのときだけ）。Reqcove のソケットは SO_REUSEPORT を設定しません。
- **対象外：** あなた自身のユーザーのプロセス（どのみちパスワードのファイルを読めます）と root。

確認状況：macOS で、本物の mitmproxy を使ったテスト（ロックからの起動と uvx 経由の両方）。mitmdump が落ちている間にキューに入った接続は、誤ったパスワードを一度に送っても 1 段ずつ送っても拒否され、何も中継も記録もされません。mitmdump の再起動中はポートを bind できず、その間に送ったリクエストは次の mitmdump が記録します。単体テスト（CI の Linux でも実行）では、mitmdump が落ちている間と Reqcove が再起動をあきらめたあとはポートを bind できず、Stop でポートが空くことを確かめています。macOS で同じユーザーとして手で試したこと：そのポートの 127.0.0.1 への bind は、SO_REUSEADDR と SO_REUSEPORT を付けても失敗します。0.0.0.0 への bind は SO_REUSEADDR で成功しますが、127.0.0.1 への接続は、より具体的な Reqcove のソケットに届きます。ランチャーがすぐに accept し、アドオンの読み込みを 1.5 秒遅らせると、キューの接続のテストは失敗します（遅らせないときは、mitmproxy がたまたま先にアドオンを読み込みました）。ランチャーの変更を遅すぎる時点で当てると、「address already in use」で終了します。

## マスク

Reqcove が見分けられるシークレットは、届いた時点でマスクします。そのため、どのツールもシークレットを返せません。`--no-redact` を付けると、マスクをしなくなります。

- 名前で見分けます。 ヘッダー、クエリパラメータ、ボディのフィールドは、名前がシークレットを表していれば（`token`、`password`、`apiKey` など）、値をマスクします。Cookie の値は名前に関係なくマスクします。
- 形で見分けます。 `Bearer`、`Basic`、`Token` の認証情報、JWT、よく知られた接頭辞を持つキーは、どこにあってもマスクします。
- 形式ごとに読みます。 JSON、フォーム、テキストの行、GraphQL、XML、HTML と JavaScript、`multipart/form-data`、protobuf、gRPC、WebSocket のメッセージを、それぞれの形式として読み、シークレットの名前を探します。
- あなたの規則を足せます。 `--mask-names` と `--mask-values` で、名前とパターンを足せます。

対象の語、形、形式ごとの読み方と、それぞれでマスクされずに残るものは、[masking.ja.md](masking.ja.md) にあります。主な抜けは次のとおりです。

- シークレットだと分からない名前の下にあるシークレット（`{"data": "…"}`）。どの形式でも同じです。`--mask-names` や `--mask-values` で足せます。
- メールアドレスや名前などの個人データ。デバッグに必要なので、マスクしません。
- マスクが読まない形式の中のシークレット（`multipart/mixed`、base64 の `SAMLResponse` フォームフィールド）と、名前ではなく位置で渡されるシークレット。
- マスクが見られなかったボディ（テキストでないもの、デコードできなかったもの）。マスクが有効な間は渡しも検索もしません。`--no-redact` を付けると返します。
- マスクが見つけられなかったシークレットは、エージェントとモデルの提供元に残ります（[上記](#エージェントが読んだものの行き先)）。

## 拾えないもの

次の接続は何も残しません。記録もされず、数えられもしません。条件と確かめ方は [masking.ja.md](masking.ja.md#記録が残らない接続) にあります。

- mitmproxy が自分で素通しする接続。Apple のホスト、`--allow-hosts` にないホスト、mitmproxy がアドレスでしか知らない接続です。
- SNI のない TLS。`--allow-hosts` にそのアドレスを書いたときは別です。
- 80 番か 443 番ポートの平文の TCP のうち、最初のバイト列が、mitmproxy の読み方では許可したホストを示さないもの。TLS なしの HTTP/2 がその一例です。
- 許可したホストへの HTTP/2 のリクエストのうち、アプリが一覧にない兄弟の名前のために開いた接続に相乗りしたもの。証明書を共有する名前をまとめて許可してください（`*.example.com`）。
- Encrypted Client Hello を使う TLS。プロバイダーの公開名を許可したときは別です。
- 許可したホストへの接続のうち、HTTP/1 の最初のリクエストが `Host` で Apple のホストを指定したもの。接続全体が、復号されたまま中継されます。
- アドレスで許可され、SNI には別の名前がある接続のうち、mitmproxy が raw TCP として運ぶもの。
- TLS のハンドシェイクを終えたあとで Reqcove の証明書を拒否して閉じるクライアントと、リクエストを送らずに閉じるクライアント。証明書を自分で確かめるピンニングのアプリがこれに当たります。ハンドシェイクの途中で拒否するアプリは、一覧に出ます。

## 露出を広げるオプション

次の 3 つのオプションは、ノードのポートを開きます。

| オプション | ポート | 届くデバイス | 守るもの |
|---|---|---|---|
| `--ui` | 80 | あなた自身のデバイスと、`--device` のデバイス | トークン（`ui-token`）。Cookie として設定します |
| `--web` | 8081（mitmweb に中継） | あなた自身のデバイス | mitmweb のパスワード（`web-token`） |
| `--mcp-http` | 8090 の `/mcp` | あなた自身のデバイス | トークン（`mcp-token`）。`Authorization: Bearer` で送ります |

どのポートも、`Host` でノード（その MagicDNS 名か tailnet アドレス）を指定したリクエストにだけ応答します。トークンは状態ディレクトリにある 0600 のファイルで、`run` のターミナルと `reqcove links` にだけ出ます（[ログイン用の URL](#ログイン用の-url)）。

### mitmweb（`--web`）

mitmweb は通信を**マスクなし**で表示します。パスワードを持つ人は誰でも、そのページからリクエストを編集してリプレイでき、オプション（スクリプトを含みます）を変えられます。オプションを変えると、このコンピュータでコードが動きます。

- mitmweb は 127.0.0.1 で待ち受けます。パスワードは、`web-token` を削除して起動し直すまで、起動のたびに同じです。パスワードは 0600 のファイルで渡し、コマンドラインでは渡しません。
- ノードは、あなた自身のデバイスのために、自分の 8081 番ポートを mitmweb に中継します。別のユーザーの `--device` のデバイスにも、ほかの誰にも中継しません。中継してもパスワードは必要で、できることはこのコンピュータで mitmweb を開いたときと同じです。
- Remote Proxy を使うスマートフォンも、同じように mitmweb に届きます。ノードの 8081 番ポートへのリクエストと WebSocket のトンネルを mitmweb に送ります（あなた自身のデバイスだけです）。すでに開いている WebSocket は、デバイスがあなたのものと見なされなくなっても、開いたままです。
- ターミナルでは、`run` がトークン付きのリンクを表示します。リンクはスクロールバックに残り、トークンのファイルを削除するまで有効です。ターミナルでないところでは表示しません。`reqcove links` は、`links` から読んでもう一度表示します。
- ブラウザがノードを通してパスワード付きのリンク（`?token=`）を開くと、mitmweb がそれを受け付けたあとで、パスワードを除いた同じ URL へのリダイレクトで応答します。そのため、パスワードはアドレスバーに残りません。Safari の履歴が最初の URL を保持するかどうかは確かめていません。
- mitmweb の Cookie は、mitmweb の再起動をまたいで使えません。mitmweb は起動のたびに作る鍵で Cookie に署名するからです（mitmweb のコードから判断したもので、試していません）。再起動のあとは、もう一度リンクが必要です。
- mitmweb は、mitmproxy が復号したすべてのフローを表示します。許可した接続に相乗りした、`--allow-hosts` にないホストへのリクエスト（HTTP/2 の接続の再利用）も含みます。リクエストごとの確認はそれらを Reqcove の記録から外すだけです。
- ボディは、それぞれ 2 MB まで、全体をマスクなしで表示します（mitmproxy はストリームするボディを保持しないので、Reqcove が渡します）。保持するのは新しい順に 10,000 件のフローと 256 MB のボディです。この上限が数えるのは終わったフローです。進行中のフローは終わってから数えます。その間に保持しているボディ（片方向につき 2 MB まで）は、上限の外です（コードから判断したもので、試していません）。

mitmweb のオプションで変わることは、次のとおりです（コードから判断したもので、試していません）。

- 変わるのは mitmproxy の動作だけで、Reqcove が mitmproxy を起動し直すまで続きます。Reqcove の記録は、`--allow-hosts` の範囲に絞られ、マスクされたままです。Reqcove が、届いた時点でどちらももう一度確かめるからです。
- Capture タブで SOCKS プロキシを切ると、デバイスの HTTP(S) が止まります。Reqcove はSOCKS プロキシを通してデバイスの通信を mitmproxy に渡しているからです。
- そこで別のモードを有効にすると、そのモードは 127.0.0.1（Reqcove が設定する待ち受けホスト）で待ち受けます。このモードにはReqcove のデバイス名の確認も、このコンピュータと LAN の拒否も働きません。

確認状況：mitmweb の代役を使ったテスト（リダイレクト）。Exit Node を使う iPhone から試しました。

### ページ（`--ui`）

`--ui` は記録の読み取り専用のページを提供します。中身は MCP ツールが返すものと同じで、同じようにマスクされています。読めるのは次のとおりです。

- あなた自身のデバイスと、`--device` のデバイスだけです。 ほかのデバイスには何も返しません。
- 別のユーザーの `--device` のデバイスに見えるのは、自分のフローだけです。 一覧でも ID の指定でも同じです。件数と次の手順も、自分の分だけが見えます。ほかのデバイスのフローも名前も見えません。あなた自身のデバイスからは、すべてのデバイスのフローが、デバイスの名前と一緒に見えます。
- トークンを持つブラウザだけです。 `run` が表示するリンクは、トークンを HttpOnly、SameSite=Strict の Cookie として設定します。Cookie の有効期間は 400 日です。同じ iPhone のほかのアプリは、ポートには届きますが、トークンがなければページを読めません。リンクが漏れても、使えるのは上のデバイスからだけです。
- トークンは起動のたびに同じです。 そのため、リンク、ブックマーク、Cookie は、`ui-token` を削除して起動し直すまで使えます。削除したあとは 403 になります。
- `Host` でノードの名前を指定したリクエストだけです。 iPhone が開いたサイトが、自分の名前をノードに向けて、ページを自分のものとして読むこと（DNS リバインディング）はできません。
- GET と HEAD だけです。 リクエストが Remote Proxy を通ってきたときも同じです。検索フォームの送り先はページ自身で（CSP の `form-action 'self'`）、Clear は一覧からフローを隠すだけです（URL に `since` を付けます）。何も削除しません。
- スクリプトはページ自身の `/app.js` だけです。 Content-Security-Policy は、ほかのスクリプトもインラインのスクリプトも許しません。`/app.js` は 1 秒ごとに `/flows.json` で一覧を取得し、DOM の呼び出しと `textContent` だけで一覧に入れます。そのため、サイトがヘッダーやボディに書いたものは、テキストのまま表示されます。`/app.js` はキャッシュされません（`no-store`）。

これらの確認が及ばないものもあります。

- ページは Safari を通ります。Safari の履歴には、表示したフローのページの URL、トークン付きの最初のリンク、検索の URL と検索した語が残ることがあります。最初のリンクは、デバイスがなければ使えず、`ui-token` を削除するまで有効です。`--no-redact` のときにシークレットの値で検索すると、その値が履歴に残ります。
- 32 段より深くネストした JSON のボディは、字下げせず、そのまま表示します。深いネストを字下げすると、深さの 2 乗に比例してメモリを使うからです。

確認状況：テスト（読めるデバイスやブラウザについての各項目。node の代役の DOM で `/app.js` を動かすテスト）。

### HTTP 経由の MCP（`--mcp-http`）

ノードはMCP ツールをあなた自身のデバイスに提供します。トークンは定数時間で比較します。別のオリジンのブラウザのページからのリクエストは拒否します。

- あなたのデバイスどうしを見分けるのは、トークンです。 個人の tailnet では、Tailscale の OAuth アプリを通して参加したエージェントのデバイス（Grok Bot）も、あなたのほかのコンピュータも、あなた自身のデバイスの 1 つになります。
- **ツールの答えは、そのデバイスと、そのモデルの提供元に届きます**（Grok Bot なら xAI のクラウドです）。エージェントは、あなたが `mcp-token` を削除して `run` を再起動するまで、トークンを持ち続けます。
- トークンは、ログの行、`reqcove status`、ツールには出しません。 エージェントがそれらを実行することがあるからです。`-t` を付けて動かしたコンテナでは、`docker logs` にトークンが残ります。
- ツールは `reqcove mcp` より少なくなります。 `--mcp-http` 専用のサーバーには、プリセットのツール、`list_rules`、`explain_rules`、マーカーのツール（`add_marker`、`list_markers`）がありません。ほかのツールは同じで、マスクされた同じ記録を返します。
- `capture_stats` と `status` は、`resolve` のルールと上流プロキシのアドレスを返しません。 ただし、`rules_error` は返します。`--rules-reload` での変更が `resolve` の行で失敗すると、エラーに、その行のホストとアドレスが出ることがあります。エラーを引用する `status` の `next_steps` も同じです（コードから判断したもので、試していません）。
- `run` はHTTP でのツール呼び出しをログに出します。 出すのは、呼んだデバイスとツールの名前で、引数は出しません。トークンがないリクエストと、トークンが誤っているリクエストもログに出します。
- **各デバイスが呼べるのは、1 秒におよそ 10 回です**（同時には 30）。それを超えると、その間は `429 Too Many Requests` を返し、1 分に 1 回ログに出します。1 台のデバイスでエージェントが暴走しても、ほかのデバイスのために `run` が動き続けます。呼び出しは、呼び出し元が切断すると終わります。

確認状況：テスト（本物の tailnet で、別のユーザーのデバイスが拒否されること。トークン、`Host`、オリジンの確認。サーバーにないツール。`capture_stats` と `status` が返さないもの。429。呼び出し元の切断で呼び出しが終わること）。この Mac から tailnet 越しに試し、Grok Bot でも試しました。

### ローカルプロキシ（`--local-proxy`）

このコンピュータ自身のアプリ（iOS シミュレーター）のための、127.0.0.1:8082 の HTTP プロキシです。パスワードはありません。

- このコンピュータのプロセスは、どのユーザーのものでも、このプロキシを使えます。プロキシが `--allow-hosts` のホストへ送るものは、`local` というデバイスとして記録します。
- アプリは、このプロキシがないときと同じように、このコンピュータ自身の名前解決で、LAN、VPN、tailnet に届きます。このコンピュータ、LAN、tailnet は、システムのプロキシの例外に入っているので、アプリはそこへ直接届きます。
- IPv6 は拒否します。このコンピュータ自身（ループバック、自身のアドレス）やリンクローカルアドレスに行き着く名前も拒否します。ただし、このコンピュータの `/etc/hosts` にその名前があるときは通します。拒否しなければ、このコンピュータのブラウザで開いたページが、自分の名前をそこに向けて、プロキシを通してこのコンピュータのサービスに届いてしまいます（DNS リバインディング）。
- ページが自分の名前を LAN、VPN、tailnet のアドレスに向けることは、なおできます。プロキシはそれを通します（VPN の中の名前を使い続けられるようにするためです）。プロキシを使わないブラウザでも同じことは起きます。ただし、プロキシを通すとブラウザにはアドレスが見えないので、ブラウザ自身のプライベートネットワーク向けの保護（Chrome の Private Network Access）が働きません。`--local-proxy` は、必要な間だけ有効にしてください。
- Apple のホストは復号しません。
- macOS では、`run` が動いている間、システムの Web プロキシをこのプロキシに向けます。元の設定は状態ディレクトリ（0600）に保存し、`run` の停止時（SIGHUP でも）、次の起動時、`reqcove cleanup` のどれかで元に戻します。まだ戻していない設定を上書きして保存することはありません。cleanup も、設定を保存している間は状態ディレクトリを削除しません。Reqcove が強制終了されると、システムのプロキシを使うアプリは、設定を戻すまで接続できません。
- Reqcove が、このコンピュータに CA を信頼させることはありません。そのためのコマンドは `run` が表示します（TLS だけ、このユーザーだけが対象です）。信頼させると、`<state>/mitmproxy/` にある CA の秘密鍵で、デバイスだけでなくこのコンピュータに対しても、どの HTTPS サイトにもなりすませるようになります。状態ディレクトリと、そのコピーやバックアップを人に渡さず、終わったら信頼を外してください（外し方は `reqcove status` と `cleanup` が、フィンガープリントを添えて表示します）。

確認状況：テスト（このコンピュータやリンクローカルアドレスに行き着く名前を拒否すること）。本物の `networksetup`（設定と、Ctrl-C での復元）と iOS 27 のシミュレーターで試しました。

### LAN モード（`--lan`）

`run --lan` は tailnet のノードを起動しません。HTTP プロキシが、このコンピュータのアドレスの 1 つ、つまり LAN のインターフェイス 1 つのアドレスで、`--proxy-port` のポートで待ち受けます（0.0.0.0 でも、VPN のトンネルでも待ち受けません）。パスワードはありません。誰が使えるかはアドレスで決めます。LAN モードは信頼できるネットワークで使い、終わったら止めてください。

- アドレスはデバイスではありません。 許可したアドレスをあとで持った人も、許可されます。このネットワークでも、同じプレフィックスを持つ別のネットワークでも同じです（カフェの 192.168.1.0/24 と自宅の 192.168.1.0/24）。許可した一覧は、準備完了の表示、`reqcove status`、`reqcove lan list` で見られます。
- ほかのアドレスは拒否します。 そのインターフェイスのネットワークの外からの接続は、受け付けた時点で閉じます。許可していないアドレスからの接続も同じです。何も記録せず、新しいアドレスごとに 1 回ログに出します。見たアドレスの一覧（10,000 件）がいっぱいになると、一覧を空にします。そのあとは同じアドレスをもう 1 回ログに出し、`run` がもう一度尋ねます。
- 拒否に変えると、新しいリクエストは 2 秒以内に断ります。 維持している接続でも、リクエストごとにもう一度確かめるからです。すでに開いている HTTPS のトンネルは、閉じるまで続きます。どちらの向きにも 15 分バイトが流れなければ、そこで閉じます。1 つのアドレスが同時に開けるトンネルは、256 本までです。
- **許可したアドレス**は、`<state>/lan-allowed` に保存します（0600。許可した日時も入ります）。一覧を変えられるのは、`reqcove lan allow|deny` と、`run` が自分のターミナルで出す質問だけです。一覧を変える MCP ツールはありません。
- `lan` コマンドは、標準入力と標準出力がターミナルでなければ断ります。 `reqcove links` と同じです。エージェントのシェルはたいていどちらも持っていません。これは助けで、保証ではありません（スクリプトはターミナルを用意できます）。
- **`run` の質問**は、`run` がターミナルのフォアグラウンドのジョブである間だけ出します。質問の前に入力されたものは先に捨てるので、前に押した Enter や `y` は答えになりません。
- `--lan` は `--config` のファイルでは断ります。 そのため、`brew services` と `reqcove service install`（インストール時にもそのファイルを断ります）が、開いたプロキシを動かし続けることはありません。

許可したアドレスがこのコンピュータを通して届く先は、次のとおりです。

| 行き先 | 届くかどうか |
|---|---|
| 80 番と 443 番以外のポート | 届きません。名前解決の前に拒否します |
| 公開のアドレス | 届きます。あなたのアドレスから出ていきます |
| プライベートな範囲（10/8、172.16/12、192.168/16、100.64/10）。このコンピュータの VPN の先も含みます | `--allow-hosts` に完全な名前（`*` なし）で書いたものにだけ届きます |
| このコンピュータ（ループバック、自身のアドレス）、リンクローカルアドレス、プロキシのあるネットワーク、公開のアドレス空間から番号を振った、このコンピュータのほかのネットワーク、特殊用途の範囲、IPv6 | 完全な名前を書いても届きません |

- 名前はこのコンピュータのリゾルバで引きます。`/etc/hosts` が先です。
- `map_remote` と `resolve` の送り先には mitmproxy が接続するので、上の確認の外です。許可したホストをこのコンピュータのサーバーに送るルールは、LAN のクライアントのリクエストにも働きます。
- `http://mitm.it` の CA は平文の HTTP で届くので、LAN のほかの誰かが差し替えられます。準備完了の表示は代わりに AirDrop で送れるように CA のファイルの名前を示し、その SHA-256 を、iOS がプロファイルの「詳細」（More Details）に表示するのと同じ形で表示します。

確認状況：テスト（拒否する接続とアドレスのログ。拒否への変更、使われていないトンネル、256 本のトンネルは、小さい値で確かめました。許可したアドレスが届く先。`run` の質問はターミナルの呼び出しを差し替えて確かめたもので、ターミナルの呼び出しそのものはテストしていません）。自宅の Wi-Fi の iPhone で試しました（2026-11-14）。許可するまで拒否され、そのあと記録され、`reqcove lan deny` のあとはまた拒否されました。SHA-256 は iOS の表示と一致しました。

### 上流プロキシ（`--upstream-proxy`）

このオプションを付けると、復号した HTTP(S) のリクエストは上流プロキシを通って進みます。Reqcove の mitmproxy は、自分ではサーバーに接続しません（connection strategy は lazy です）。許可したホストへの TLS 上のほかのプロトコルは、それでもサーバーへ直接進みます（コードから判断したもので、試していません）。このフラグは起動時に読みます。これを変えるツールはありません。

- プロキシには、リクエストとレスポンスがマスクなしで見えます。 たとえば Burp は、それをプロジェクトとしてディスクに保存します。Burp 自身の MCP サーバーや拡張は、Reqcove のツールが渡さないものと、リクエストを送る手段をエージェントに与えます。
- 本物のサーバーの証明書を検証するのは、プロキシの仕事です。 プロキシの CA（`--upstream-ca` で指定したもの、または起動時に取得した Burp のもの）があるとき、Reqcove が信頼するのはその CA だけです。つまり、Reqcove が検証するのはプロキシで、サーバーではありません。試したところ、Burp はデフォルトではサーバーの証明書を検証しませんでした。
- Burp の CA は平文の HTTP で取得します。 取得元はプロキシ自身のリスナー（`http://127.0.0.1:PORT/cert`）です。名前を引かないので、ほかのサーバーは応答できません。取得するのはプロキシがこのコンピュータにあるときだけで、受け入れるのは「PortSwigger CA」という名前の CA だけです。
- プロキシがどこに接続するかは、プロキシが決めます。 Reqcove は、Exit Node が許可したアドレスをプロキシに渡します。しかし Burp はSNI の名前をこのコンピュータでもう一度引いて接続します。そのため、このコンピュータの LAN の中に解決される名前は、Exit Node の拒否をすり抜けて LAN に届きます。
- `--allow-hosts` は狭くしておいてください。 iPhone が開いたサイトは、自分の名前を、プロキシの名前解決のときだけ LAN に向けられます（DNS リバインディング。コードから判断したもので、試していません）。`--allow-hosts` が `'*'` のとき、`run` は警告します。`resolve` のルールを `--upstream-proxy` と一緒に使うと断るのも、このためです。
- CONNECT の行（IP アドレスとポート）と平文の HTTP は暗号化されずにプロキシに届きます。 プロキシはこのコンピュータか tailnet に置いてください。

確認状況：テスト（サーバーへの接続を数えるテスト。「PortSwigger CA」という名前の CA だけを受け入れること）。Burp で試しました。Burp は `/cert` で応答し（curl で確かめました）、デフォルトではサーバーの証明書を検証せず、SNI の名前で接続しました。

### ルール（`--rules`）

ルールはあなたのもので、mitmproxy の起動時にファイルから読みます。ルールを書いたり変えたりする MCP ツールはありません。`--mcp-http` 経由のエージェントには、ファイルに届く手段がありません。他人が作ったルールファイルはコードです。あなたのアプリのリクエストを、Cookie やトークンも含めて、どこへでも送れます。

- `run --rules-reload` は、ファイルが変わるたびに読み直します。 そのため、ファイルに書き込めるもの（あなたのユーザーとして動くプロセスなら何でも。ファイルを扱えるエージェントも含みます）は、`run` が動いている間に、デバイスのリクエストの行き先を変えられます。付けなければ、ファイルを読むのは mitmproxy の起動時だけです（`run` と一緒に起動するときと、mitmproxy が終了して Reqcove が起動し直すとき）。
- `reqcove mock add` は、あなたの代わりにモックをルールファイルに書きます。 動くのは、入力と出力がターミナルのときだけです。これは、頼まれていないエージェントが実行するのを防ぐ助けで、保証ではありません（コマンドを実行できるエージェントは、ターミナルを用意することも、ファイルを直接編集することもできます）。ルールを書くのはあなたです。Skill は、エージェントに、このコマンドを実行しないよう伝えています。先に `run` にファイルを確かめさせるために、このコマンドは状態ディレクトリ（0600、あなたのユーザー）から `run` の SOCKS5 のパスワードを読みます。`run` は指定されたファイルを確かめるだけで、取り込みません。
- **ルールが失敗したリクエスト**（たとえば、`map_remote` が不正なポートを作ったとき）には元のまま送らずに 502 で応答します。置き換えがまったく成り立たない `map_remote` があると、`run` は起動時に止まります。
- **`modify_headers`** が受け付けるのは、HTTP のトークンであるヘッダー名と、改行も NUL も含まない値です（含むと、送信時に別のヘッダーが始まってしまいます）。値のファイルをあとのフローのために読み直したとき、改行や NUL が入っていれば、その値をそのフローのヘッダーから外します。
- **`resolve` の名前**はホスト名だけです。そのため、名前に含まれるものが制御文字としてログに出ることはありません。

**ルールが付けるヘッダーは、リクエストが指定したホストにだけ届きます。** リクエストの Host はアプリが書くもので、mitmproxy は、Host に何が書いてあっても、アプリが接続した先へ接続します。一方、ルール（`~d`）は Host を読みます。そのため、ルールが付けるヘッダー（`modify_headers`。プリセットも含みます）は、リクエストが指定したホストにだけ届きます。レスポンスに付けるヘッダーは、そのホストのレスポンスにだけ付きます。`map_remote` や `resolve` がリクエストを別の先へ送らないとき、ルールが働くのは、次のどれかが成り立つときだけです。

- アプリが接続したアドレスが、アプリの送った Host そのものである（Host は、どのルールよりも前に読みます）。
- HTTPS で、その Host が、mitmproxy がサーバーの証明書を照合する TLS の名前である。その名前の証明書を持たないサーバーには、リクエストが届きません。`--upstream-proxy` を通すときは、この条件は使いません。そのとき mitmproxy が検証するのはプロキシの証明書で、サーバーの証明書を検証するのはプロキシだからです。
- このコンピュータで Host を引いたアドレスの中に、アプリが接続したアドレスがある。

どれも成り立たなければ、リクエストはアプリが送ったまま進み、レスポンスもサーバーが送ったまま戻ります。その rewrites には、ルールを当てなかったことが出ます（条件は `explain_rules` が示します）。細かい点は次のとおりです。

- ルールが Host を変えても、こうしたリクエストにルールは働きません。 ルール自身が書いた Host で、ルール自身を通してしまうからです（Host に対してトークンを付けるルールと、Host を接続先のアドレスに書き換えるルールの組み合わせ）。リクエストの行き先を変えるのは、`map_remote` と `resolve` の役目です。
- **パスだけを変えてホストを変えない `map_remote`** は、ほかの `map_remote` と同じようにリクエストを送り直します。このとき mitmproxy は、そのホストの名前をこのコンピュータで解決して接続します。アプリが接続したアドレスには接続しません。そのため、ヘッダーのルールが働きます。
- **名前は IDNA の ASCII 形で比べます**（HTTP/2 の `:authority` はデコードされて届き、SNI はデコードされずに届きます）。İ、ı、ſ、K を含む Host（そのままでも、`xn--` 形でも）にはルールは働きません。大文字と小文字を区別しない `~d` が、それを別の ASCII の名前に一致させてしまうからです（`mysıte.com` を `mysite.com` に）。
- 名前解決には上限があります。 名前ごとに専用のスレッドで引き、1 つの名前につき同時に 1 回、同時に引く名前は 16 個までで、答えは 30 秒保持します。リゾルバが止まっても、イベントループの executor は空いたままで、プロセスも終了できます。Host の名前解決に 3 秒を超えてかかったリクエストと、16 個の名前を引いている最中に来たリクエストは、ルールなしで進みます。
- **このコンピュータの名前解決は、デバイスのものと食い違うことがあります**（Exit Node は `--dns` に問い合わせます。デフォルトは 1.1.1.1 です。CDN はリゾルバによって違う答えを返すことがあります）。そのときリクエストはルールなしで進みます。その名前の `resolve` ルールがあれば避けられます（コードから判断したもので、CDN では試していません）。ただし、`--upstream-proxy` は `resolve` を受け付けないので、上流プロキシを通すときは、ルールなしのままです。
- こうしたリクエストを、代わりに Host の先へ送ることはしていません。 そうすると mitmproxy が自分で名前を引くことになり、このコンピュータと LAN に対する Exit Node の拒否をすり抜けるからです（mitmproxy のコードから判断したもので、試していません）。

**`map_remote` と `resolve` は、このコンピュータから接続します。** 接続先はルールが指定した場所で、このコンピュータと LAN も含みます。Exit Node がそれらのアドレスを拒否するのは、デバイス自身の接続についてです。ルールがあると、中継しているデバイスのアプリは、そのルールのホストへリクエストを送るだけで、ルールの送り先に届きます（Web ページも含みます）。

- `resolve` が受け付けるのは IPv4 アドレスだけで、引く必要のある名前は受け付けません。`0.0.0.0/8`、リンクローカル、マルチキャスト、予約済みの範囲、Tailscale の 100.100.100.100、クラウドのメタデータのアドレス 169.254.169.254 と 100.100.100.200 は断ります。`map_remote` は、与えられたものを何でも受け付けます。
- ポートのない `resolve` ルールは、リクエストのポート（アプリのもの、または `map_remote` の URL のもの）を使います。
- `resolve` の送り先への TLS は、ルールの名前に対して検証します。使うのは mitmproxy 自身の CA の一覧です（certifi。mitmproxy のコードから判断したものです）。そのため、リクエストが進むのは、その名前の証明書を持つサーバーだけです。平文の HTTP は検証しません。
- `resolve` の名前には、それぞれ別のアドレスが必要です。mitmproxy は接続をアドレスごとに使い回すので、アドレスを共有する名前は、1 つの名前の検証を共有してしまいます。そのため、アドレスの共有は断ります。
- `resolve` の送り先のアドレスへの `map_remote` は、その接続を双方向に共有します。一方のリクエストが、もう一方のために作られて検証された接続に相乗りすることがあります。接続が失敗すると、アプリの接続が続く間、両方が失敗します。

**`mock` は、サイトの名前で応答します。** アプリも、WebView のページも、それをサイト自身の応答として受け取ります。応答の中のスクリプトはそのオリジンで動き、リダイレクトにも従います。

- `mock` を使えるのは `--allow-hosts` のホストだけです（ほかは断ります）。ヘッダーの値は、`modify_headers` と同じように確かめます。
- 記録には、フローがモックされたことと、ルールの番号とステータスが出ます。モックの中身は出ません。
- モックが応答するかもしれないリクエストは、ボディが届き終わるまで全体を保持します（operationがボディに入っているからです）。長さを示しているリクエストでは、1 MiB までです。
- 長さを示さない GET を保持するのは、ボディがない間だけです。HTTP/2 では、ボディを送ってきた GET に、ボディの最初のバイトで 502 を返し、ボディは保持しません。これは `map_local` と同じです。空の DATA フレームでストリームが終わる GET には、応答します。そのバイトかストリームの終わりを待つ間、ボディは保持せず、サーバーにも接続しません（コードから判断したもので、試していません）。
- 12.3.1 以外の mitmproxy（別の `--mitmproxy-spec`）ではヘッダーと同時に終わらないストリームに、すぐ 502 を返します（コードから判断したもので、試していません）。

**`list_rules` と `explain_rules` は読み取り専用です。** 各ルールを、種類、番号、プリセットと一緒に示します。示すのはルールから導いたものだけです。

- モックでは、メソッド、URL、operation、ステータス、遅延、fault。`map_remote` では、送り先のスキームとホスト（「path only」か、ルールがそれを書いていないときは「not shown」）。`modify_headers` では、ヘッダー名と向き。`resolve` では、名前とアドレス。`map_local` のルールは番号だけです。
- フィルター、正規表現、ヘッダーの値、ボディ、ファイルのパスは示しません。
- `explain_rules` は、自分で作ったリクエストに対して、リクエストの経路と同じコードを動かします。そのリクエストは送りません。プリセットの状態はコピーを使うので、プリセットの回数を使わず、プリセットを有効にも無効にもしません。
- プリセットのツールと同じく、この 2 つは `run` のローカルのソケットと `reqcove mcp` でだけ使えます。`--mcp-http` では使えません。送り先から、デバイスのリクエストをどこへ送れるかが分かるからです。

確認状況：テスト（ヘッダーの名前と値。`resolve` の名前。失敗したルールへの 502。`run` がファイルを取り込まずに確かめること。`explain_rules` がプリセットの回数を使わないこと。2 つのツールが示すものは、目印の文字列を使った E2E テスト）。本物の mitmproxy でのテスト：別のホストの Host を付けて接続された代役のサーバーには、ルールの値が届きません（平文の HTTP でも、自分の名前の有効な証明書を持つ HTTPS でも、Host をそのアドレスに書き換えるルールがあっても）。アプリにも、そのサーバーからレスポンスのルールの値は届きません。その名前の証明書を持たないサーバーには、リクエストが届きません。Host のアドレスへのリクエストと、`resolve` ルールが送ったリクエストには、双方向でルールが働きます。ネットワークを通さずに確かめたもの：IDNA と İ、ı、ſ、K（mitmproxy 自身が作ったフローで）。名前解決の上限（mitmproxy の Python で、答えが返らない名前解決を使って。動いている mitmdump では確かめていません）。パスだけを変える `map_remote`（mitmproxy の Python で）。Go の HTTP/2 クライアントでのテスト：502 と空の DATA フレーム（ストリームの終わりを mitmproxy がどう伝えるかは、mitmproxy のコードから判断したものです）。試したこと：`resolve` の送り先が、別の名前の信頼された証明書を持つとき、502 になります。

### モックのプリセット

`--rules` のファイルで `preset: NAME` を付けたモックは、エージェントが `activate_preset` で有効にするまで何もしません（`list_presets`、`deactivate_preset`）。`map_remote`、`modify_headers`、`resolve` のルールもプリセットにできます。こちらはリクエストを別の場所へ送れます（[下記](#map_remotemodify_headersresolve-のプリセット)）。

- プリセットを書くことが、エージェントが有効にしてよいという、あなたの同意です。 起動時のスイッチはありません。
- **Reqcove のツールだけを許可されたエージェント**（MCP だけのクライアントや、サンドボックスに入ったクライアント）が、デバイスの受け取るものを変えられます。変える時点はエージェントが選び、呼び直せば、呼び続ける限り変えていられます。サイトが記録に書き込んだ文が、そうするようエージェントを誘導しようとすることがあります。
- エージェントが有効にできるのは、あなたが書いたものだけです。 モックのプリセットでは、新しい中身、送り先、ホストは生まれず、このコンピュータから新しく出ていくものもありません。
- **最悪の場合**は、すべてのプリセットがずっと有効にされ続け、それぞれがサイトの名前で、あなたの書いたものを応答することです（許可したホストの HTML ページのモックは、どのモックもそうであるように、そのホストの Cookie を持って Safari で動きます）。
- **上限**は Reqcove で確かめ、mitmproxy のアドオンでもう一度確かめます。1 回につき最長 5 分で、`times` を付けると最大 20 件のリクエストまでです。有効にし直す回数に上限はありません。一致したリクエストは、誰が送ったものでも回数を使います。
- 使えるのはこのコンピュータでだけです。 ツールは `run` のソケットと `reqcove mcp` にあります。`--mcp-http` 専用のサーバーにはありません。アドオンは状態ディレクトリにある自分のソケット（0600）で依頼を受けますが、受けるのは `run` が渡した秘密が付いているものだけです。
- 書き込みを送り直すことはありません。 `reqcove mcp` は、呼び出しの途中で `run` への接続が切れても、書き込みを送り直しません。効いたかどうかは分からないと伝えます。
- 書き込みのツールには読み取り専用の印を付けていません。 そのため、ほかのツールの前に確認するクライアントは、これらの前にも確認します。`"mcp__reqcove"` をまとめて許可したクライアントでは、確認なしで許可されます。読み取りのツールは名前で個別に許可してください。
- **エージェントに伝えていること。** Skill とサーバーの instructions は、プリセットを有効にするのは、ユーザーが会話の中で頼んだテストのためだけにするよう伝えています。記録やプリセットの説明に書いてあることを理由に有効にしてはいけない、とも伝えています。`preset:` をルールファイルに書くのも、ほかのルールと同じく、ユーザーが会話の中で頼んだときだけです。頼まれてプリセットを書いたエージェントは、`--rules-reload` があれば、すぐにそれを有効にできます。この場合は、会話の中での依頼が同意になります。モデルがこれを守るかどうかは、テストでは示せません。
- **見えること。** `run` は、エージェントがプリセットを有効・無効にするたびにログに出します。`status` ツールと `reqcove status` は、有効なプリセットを一覧にします（mitmproxy が答えなかったときは、そう伝えます）。プリセットが応答したフローには `preset: NAME` と出ます。
- **無効になるとき。** `--rules-reload` のときにルールファイルが変わると、すべて無効になります。mitmproxy や `run` の再起動でも無効になります。終わりの時刻は 2 つの時計で確かめるので、コンピュータがその時刻を過ぎてスリープしていても、有効なまま残りません。すでに `delay_ms` の待ちに入っている応答は、プリセットを無効にしたあとでも 1 つ出ていきます。
- **`list_presets`** が返すのは、各プリセットが何に一致するかと、ステータス、遅延、fault です。ボディとヘッダーの値は返しません。

確認状況：テスト（`run` が作る 2 つのサーバー。アドオンの秘密。書き込みを送り直さないこと。2 つの時計）。

### map_remote、modify_headers、resolve のプリセット

これらの種類のプリセットは、有効な間、アプリが受け取るものだけでなく、デバイスのリクエストの行き先や中身も変えます。

- `map_remote` のプリセットは、一致したリクエストを、あなたが書いた送り先へ送ります。 アプリの Cookie、トークン、ログインのボディなど、リクエストに入っているものすべてが送られます。記録しているすべてのデバイスが対象です（LAN モードでは、許可したすべてのアドレス）。
- エージェントは送り先を選べません。 選べるのは、いつ有効にするかと、有効にし直して続ける長さだけです。サイトが記録に書き込んだ文を通した最悪の場合は、本番の認証情報が、プリセットに書いたステージングや開発のサーバーへ、何度も送られることです。
- 考えておくべき危険は古くなった送り先です。 今は別の人が持っている、古いトンネルやステージングの名前がこれに当たります。
- 5 分が区切るのは切り替えで、その影響ではありません。 有効な間にアプリが書いたもの（注文、編集）は、そのサーバーに残ります。アプリは、そこで受け取ったトークン、Cookie、キャッシュを持ち続け、無効になったあとで普段のサーバーに送るかもしれません。
- `resolve` はより安全な種類です。 名前の接続先を別の場所にしますが、Host、SNI、TLS の検証は、その名前のままです（コードから判断したものです）。HTTPS では接続先のサーバーにその名前の証明書が必要です。
- `modify_headers` のプリセットが変えるのは、リクエストだけです。 レスポンスに対するもの（`~s`）は、読み込みで断ります。ページの保護（CSP、HSTS）を外したり、Safari が表示するホストに Cookie を設定したりできてしまうからです。ヘッダーの値は表示しません。有効なプリセットは普通のルールのあとに当てるので、送られるのはプリセットのヘッダーです。
- **読み込みで断るもの。** 送り先を表示して確かめられるようにするためです。`map_remote` のプリセットのうち、置き換えが `http://` か `https://` とホストと `/` の形でないもの、ユーザーやパスワードを含むもの、ホストをリクエストから取るもの、リンクローカルアドレスへ行くものを断ります。このコンピュータと LAN のアドレス（`localhost`、`*.local`、プライベートアドレス）以外への平文の `http://` も断ります。
- **リクエストごとに確かめるもの。** 書き換えたあとの URL のスキーム、ホスト、ポートを、表示した送り先と照合します。正規表現が URL の途中に一致したリクエストには 502 を返し、別の場所へは送りません。
- **表示するもの。** 各プリセットの送り先（`map_remote`）やアドレス（`resolve`）を、`run` の準備完了の表示、ログ、`list_presets` に出します。有効なプリセットは `reqcove status` に出します。フィルター、正規表現、ヘッダーの値は出しません。プリセットが変えたフローには、`presets` にそのプリセットが出ます。Skill とサーバーの instructions は、そうしたフローの応答を普段のサーバーのものとして報告しないよう、エージェントに伝えています。
- `activate_preset` は、どの種類のプリセットも有効にできます。 読み取り専用の印はなく、そうしたツールの前に確認するクライアントは確認します。`"mcp__reqcove"` をまとめて許可したクライアントは、これも許可します。確認なしで許可すると、これらの種類も許可することになります（ガイドの[例](guide.ja.md#ツールを許可する)では `ask` に入れています）。
- 上限と見え方はモックのプリセットと同じです。 1 回につき最長 5 分で（これらの種類に `times` はありません）、このコンピュータでだけ使え、`--mcp-http` では使えません。読み直しや再起動で無効になり、2 つの時計で確かめます。
- **試していないこと。** プリセットが有効・無効になる前にアプリが開いていた接続（使い回される HTTP/1 や HTTP/2 の接続）を、アプリがどう扱うかは試していません。アプリは使い続けるかもしれません。その場合、切り替えがすぐには反映されなかったり、終わりの時刻を過ぎても続いたりすることがあります。
- **コードから判断したこと。** ルールはリクエストの始まりで当てます。そのため、`map_remote` や `resolve` のプリセットが有効な間に始まった WebSocket、ストリーム、長いアップロードは、プリセットが無効になったあとも、5 分を過ぎても、その送り先のままです。

確認状況：テスト（表示した送り先の外へ書き換えられた URL への 502。プリセットのヘッダーを普通のルールのあとに当てること）。平文の HTTP での E2E テスト（`resolve` が保つもの）。

### フラグのファイル（`--config`）

`run --config FILE`（`brew services` と `reqcove service install` のためのもの）は、`run` のフラグをファイルから読みます。つまり、そのファイルに書き込めるものが、次の起動のフラグを決めます。

- ファイルは、あなたのもので、あなただけが読めるものでなければなりません（そうでなければ断ります）。`--mask-values` のパターンが入ることがあるからです。
- エラーが示すのは行で、値は示しません。
- 次の 5 つのフラグはファイルでは断ります。コマンドラインで指定してください。`--no-redact`（マスクを外します）、`--web`（通信をマスクなしで表示します）、`--allow-hosts '*'`（すべてのサイトを記録します。`@FILE` 経由でも断ります）、`--rules-reload`（動作中に、ファイルがリクエストの行き先を変えられるようにします）、`--lan`（LAN に開いたプロキシを作ります）。
- `--upstream-proxy` や `--rules` など、ほかのフラグはファイルに書けます。

確認状況：テスト（断る場合）。

## プロンプトインジェクション

記録の中身は、ほかの人が書いたものです。レスポンスのボディ、レスポンスのヘッダー、ステータスの理由の文、リダイレクト先、エラーメッセージは、リモートのサイトが書きます。そこには、エージェントを誘導するための文が入っているかもしれません。アプリは、自分の User-Agent、TLS の名前、送る JSON のキーを選びます。tailnet のピアは、自分のデバイス名を選びます。

エージェントにできることは、次のとおりです。

- Reqcove のツールは読むだけですが、例外が 1 つあります。 エージェントは、あなたがプリセットにしたルールを、1 回につき最長 5 分、有効にできます（有効にし直す回数に上限はありません）。プリセットにできるのはモック（[モックのプリセット](#モックのプリセット)）と、`map_remote`、`modify_headers`、`resolve` のルールです。後者はリクエストの中身や行き先を変えます（[これらのプリセット](#map_remotemodify_headersresolve-のプリセット)）。有効にできるのは、あなたが書いたものだけです。
- `add_marker` も書き込みますが、書くのは Reqcove のメモリにあるマーカーだけです。
- ルールを書いたり変えたりするツールはありません。プリセットがなければ、エージェントが何を呼んでも通信は変わりません（`--rules` はあなたのもので、起動時にファイルから読みます）。
- エージェントはほかのツールも持っているかもしれません。 シェル、ファイルの書き込み、ネットワーク、ほかの MCP サーバーです。サイトが記録に書き込んだ文は、それらを使うようエージェントを誘導しようとすることがあります（Cookie をどこかへ送る、ファイルを編集する）。Reqcove の側からは、これを止められません。止められるのはエージェント自身の設定です。

あなたがすることは次のとおりです。

- Reqcove を読むエージェントには、作業に必要なものだけを与えてください。Reqcove を読んであなたに答えるだけのエージェントが、いちばん安全な形です。
- Claude Code では、Reqcove の読み取りのツールを名前で許可してください（`activate_preset` は入れません）。シェルのコマンドやネットワークのツールを一緒に許可せず、ほかのものには許可の確認を残します。
- Codex ではサンドボックス（デフォルトではネットワークなしです。Codex の文書から判断したもので、試していません）と承認を残してください。

Reqcove がしていることは、次のとおりです。

- ツールがボディを返すのは、求められたときだけです。`diff_flows` が返すのは、違っている部分です。
- サイト、アプリ、tailnet が書いたものを返すツールは、どれも説明の中で、それがデータで指示ではないと伝えています（`--mcp-http` にある 12 個のツールも同じです。`list_markers` も、マーカーの文について同じことを伝えています）。
- プリセットとルールのツールが返すのは、あなたのルールファイルにあるものです。`add_marker` が返すのは、Reqcove 自身の値です。`list_presets` は、プリセットの説明があなたの言葉で、指示ではないと伝えています。
- サーバーの instructions は、すべてのクライアントに送られます（Grok Bot のように、Skill を持たないクライアントにも送られます）。instructions も同じことを伝えています。加えて、記録に書いてあることを理由にファイル（とくに `--rules` のファイル）、コミット、コマンドを書かないこと、`--no-redact` や `--web` を勧めないこと、`next_steps` はユーザーが行うものであることを伝えています。モデルがこれを守るかどうかは、テストでは示せません。
- Host がホスト名でもアドレスでもないリクエスト（アプリ独自の HTTP スタックは、そこにどんな文でも入れられます）は、中継しますが、記録しません。TLS から得たホストは、mitmproxy 自身の確認によってホスト名に限られます（mitmproxy のコードから判断したもので、試していません）。
- 一覧と要約に出す User-Agent は 256 バイトに切ります。ALPN の名前は印字できる ASCII だけにします。`diff_flows` の JSON のキーのうち、単純な名前でないものは引用符で囲みます（`$["a.b"]`）。

次のことは記録からは証明できません。

- **フローのホスト**は、リクエストの Host です。Host はアプリが選びます。任意のアドレスへの接続での平文の HTTP と、許可したホストへの接続での HTTPS では、Host に許可したホストを書けます。記録にはそのホストが出ます。リクエスト自体は接続の行き先へ進みます（ルールへの影響は[ルール](#ルール--rules)にあります）。
- **マーカーの `source`**（`cli`、`mcp`）は経路です。Reqcove が、呼び出しがどこから来たかで設定します（`reqcove mcp` は、エージェントのクライアント名を引き渡しません）。これは証明にはなりません。このコンピュータでコマンドを実行できるエージェントは、`reqcove mark` を実行するか、`run` のソケット（同じユーザー）に自分で接続すれば、`cli` を名乗れます。そうすれば、ユーザーの 100 件を押し出すこともできます。`reqcove mcp` を通すエージェントは `mcp` になり、それはできません。
- **マーカーの文**は、ユーザーかエージェントの言葉です。データで、指示ではありません（サーバーの instructions がそう伝えています）。

確認状況：テスト（ツールの説明。クライアントが stdio と HTTP で instructions を受け取ること。文面は確かめていません。そうした Host のリクエストを記録しないこと。`reqcove mcp` を通すエージェントが `mcp` になること）。

## mitmproxy 自身のコード

- mitmproxy とその依存パッケージ（44 個）は、Reqcove に組み込まれたロックファイル（`internal/capture/mitm.py.lock`）から来ます。`run` はロックファイルと小さなランチャーを状態ディレクトリに書き、`uv run --locked --script` で mitmproxy を起動します。このコマンドはロックに書かれたファイルだけをインストールし、それぞれのハッシュを確かめます。
- 素の `uvx` はハッシュを与えられても確かめません。素の `uvx` を使うのは、別の `--mitmproxy-spec` のときと、`--uvx` のファイル名が `uvx` でないとき（ラッパー。その `uv` が何かは分かりません）です。このときは決まった日付より前のリリースを使います（`--exclude-newer`）。
- CI は、ロックがランチャーと合っていることを確かめ、既知の脆弱性がないかを監査します（pip-audit）。
- ロックはバージョンを 1 つ上書きしています。mitmproxy 12.3.1 は、mitmweb のサーバーである tornado を 6.5.10 までに制限しています。監査は6.5.10 に 3 つの脆弱性を見つけました。ロックは 6.6.1 に固定しています。6.6 がその 3 つを直し、6.6 自体には CVE-2026-126347 があるからです。この組み合わせで mitmproxy 自身のテストは実行していません。
- `--uvx` のラッパーを通すときも、デフォルトの mitmproxy にはロックの上書きを当てます。tornado はロックの日付の時点のもの（6.6.1）になります。ハッシュは確かめません。
- 別の `--mitmproxy-spec` では、上書きを当てず、その mitmproxy が求める tornado になります（コードから判断したものです）。mitmproxy 12.3.1 では 6.5.10 です。6.5.10 の脆弱性は mitmweb のサーバーにあり、`--web` がそのサーバーを動かします。

確認状況：試したこと（1 つのパッケージのハッシュを変えたロックは、キャッシュが空のときも、いっぱいのときも断られました。`uvx` はハッシュを与えても確かめませんでした。別の `--mitmproxy-spec` として指定した mitmproxy 12.3.1 では、tornado が 6.5.10 になりました）。2026-11-14 に uv 0.13.4 で試したこと：ラッパーを通すと、ほかのパッケージはロックのバージョンになり、`--web` のテストは通りました。Reqcove の `--web` のテストは、tornado 6.6.1 で通ります。

## あなたの責任

次のことは、Reqcove ではなくあなたが行います。

- **同意を得る。** ほかの人のデバイスを中継して記録するのは、その人の同意があるときだけにしてください（[下記](#ほかの人のデバイス)）。
- **CA を片付ける。** 使うのをやめるときは、各デバイスからプロファイルを削除してください。状態ディレクトリと、そのコピーやバックアップは、人に渡さないでください（[CA の秘密鍵](#ca-の秘密鍵)、[`reqcove cleanup` のあとに残るもの](#reqcove-cleanup-のあとに残るもの)）。
- **共有のコンピュータに気を付ける。** ほかのユーザーに見えるものと届くものがあります（[ほかのユーザーと共有するコンピュータ](#ほかのユーザーと共有するコンピュータ)）。
- **エージェントが読めるものとできることを絞る。** `--allow-hosts` を狭くし、エージェントには作業に必要なツールだけを与えてください（[プロンプトインジェクション](#プロンプトインジェクション)）。

### ほかの人のデバイス

`--device` には、あなたのものではないデバイスも指定できます。LAN モードは、あなたが許可したアドレスなら何でも中継します。

- デバイスを中継して記録するのは、それを使う人の同意があるときだけにしてください。
- 許可したホストへのリクエストは、復号されて記録されます。エージェントがそこから読んだものは、モデルの提供元に送られます。
- そのデバイスは、プロファイルを削除するまで、あなたが鍵を持つ CA を、すべてのサイトについて信頼します（[CA の秘密鍵](#ca-の秘密鍵)）。
- Reqcove は誰にも尋ねず、同意があるかどうかも確かめません（コードから判断したもので、試していません）。
- 同意なしに人の通信を記録することは、あなたのいる場所の法律に反するかもしれません。
- あなた自身のデバイスの通信にも、ほかの人の言葉が入っています（チャットのメッセージ）。個人データはマスクしません。
