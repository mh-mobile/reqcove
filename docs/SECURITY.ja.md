# Reqcove のセキュリティモデル

[English](SECURITY.md)

Reqcove はスマートフォンの HTTPS を復号し、読んだものを AI エージェントに渡します。このページでは、Reqcove が何を守り、何を信頼し、何をしようとしていないかを説明します。対象は v1.0 です。

このページには Reqcove を信頼するかどうかを決めるのに必要なことだけを書いています。詳細はほかの 2 つのページにあります。形式ごとにマスクが何を見つけるかと、記録が残らない接続は、[masking.ja.md](masking.ja.md) にまとめています。オプションごとの詳細は[ガイド](guide.ja.md)の各オプションの節にある「セキュリティの詳細」に、そのほかの詳細はガイドの[セキュリティ](guide.ja.md#セキュリティ)の節にあります。

試していない点と、コードから判断した点には、その場所にそう書いています。テストや実機で確かめたことは、各節の最後の「確認状況」に書いています。確認状況はこのページか、ガイドの詳細にあります。試した環境は、ほかの記載がなければ mitmproxy 12.3.1、iOS 27.3 の iPhone、macOS です。

このページで使う言葉を 2 つ説明します。**状態ディレクトリ**は `~/.reqcove` か、`--state` で指定したディレクトリです。**あなた自身のデバイス**は Reqcove のノードと同じユーザーで tailnet に入っていて、どちらにもタグが付いていないデバイスです。Reqcove はこれを、接続が開くときとリクエストのたびに確かめます。

## 脆弱性の報告

公開の issue ではなく、このリポジトリの GitHub のプライベート脆弱性レポート（private vulnerability reporting）を使ってください。

## スマートフォンから出ていくものとその行き先

### 記録するもの

- 記録するのは、`--allow-hosts` にあって `--pass-hosts` にないホストへのリクエストだけです。これを 2 つの確認で守ります。mitmproxy はほかの接続を復号せずに通し、Reqcove はリクエストごとに Host をもう一度確かめます。
- Apple のホストへの接続は常に復号せずに通します。
- 許可したホストへの接続が、ほかのホストへのリクエストを運ぶことがあります（HTTP/2 の接続の再利用）。そのリクエストは接続と一緒に復号されます。記録はしませんが、`--web` には表示され、`--upstream-proxy` に転送されることがあります。
- 一覧にないホストへのリクエストと TLS の失敗は、数えるだけで記録しません。
- `--pass-hosts` のホストと、mitmproxy が raw TCP として運ぶ接続は、接続の記録だけを残します。中身は残しません（[詳細](masking.ja.md#中身なしで記録する接続)）。
- 記録がまったく残らない接続もあります（[拾えないもの](#拾えないもの)）。
- シークレットは届いた時点でマスクします（[マスク](#マスク)）。
- ボディを返すのは、ツールがボディを求められたとき（`get_flow` と `search_flows` の `bodies`）と、ボディを比べる `diff_flows` だけです。
- 記録はメモリにあります。上限はフロー 10,000 件とテキスト 64 MiB で、`reqcove run` が止まると消えます。Reqcove 自身はフローをディスクに書きません（[上限](masking.ja.md#記録が保持するもの)）。
- `reqcove har > FILE` は、あなたが指定した先に記録を書きます。中身はツールが返すものと同じようにマスクされています。ファイルのモードはシェルの設定に従うので、ほかのユーザーが読めることがよくあります。状態ディレクトリのモードは 0700 です。
- Reqcove は DNS を記録しません。

### エージェントが読んだものの行き先

- ツールが返すものはすべて、エージェントのモデルの提供元に送られます。それを踏まえて `--allow-hosts` を選んでください。`--allow-hosts '*'` はほかのアプリやサイトの通信も送ることになるので、Reqcove は起動時に警告します。
- `status` と `list_devices` のツールは通信のほかに、ノードの MagicDNS 名（tailnet の名前を含みます）、ノードの tailnet アドレス、デバイスのマシン名も返します。あなたのログイン名は返しません（コードから判断したもので、試していません）。
- 送られたものは提供元に残ります。提供元は、受け取ったものを規約が定める期間だけ保持します。
- エージェントの側にも残ります。エージェントは、自分が動くコンピュータに会話を保存します。Claude Code はセッションごとに、ツールの結果も含めて `~/.claude/projects/` の下のファイルに書きます。ほかのエージェントは見ていません。
- これらの写しは Reqcove のものではありません。`run` を止めると Reqcove の記録は消えますが、写しは消えません。`reqcove cleanup` も写しには触れません。
- マスクが見つけられなかったシークレットと、`--no-redact` で読んだものは、そこで読める状態のまま残ります。エージェントがそれをもとに書いたもの（要約、ファイル、コミット）にも残ります。

確認状況：この Mac の Claude Code 2.1 で見ました（2026-11-14）。

### Exit Node の DNS

- Exit Node を使える tailnet のほかのデバイスも、Exit Node を通して名前を解決できます。tailnet のポリシーが Exit Node の利用を認めたデバイスなら、どれでも解決できます（Tailscale のコードから判断したものです）。`--dns system` のときや、`--dns` に LAN のリゾルバを指定したときは、ルーターや会社のリゾルバしか知らない名前も引けます。
- このコンピュータから上流までの DNS は、暗号化されていない平文です。応答を DNSSEC で検証することもしません（コードから判断したもので、試していません）。そのため、このコンピュータがつながっているネットワーク（Wi-Fi や ISP）には、デバイスが引く名前が見えます。その経路上にいる人は偽の応答を返せます。
- 偽の応答で得られるものは多くありません（コードから判断したもので、試していません）。HTTPS ではその名前の証明書を示す必要があります。このコンピュータ、その LAN、ループバックを指す応答は拒否します。平文の HTTP は、どのネットワークでもそうであるように、別の場所へ送られることがあります。

[詳細](guide.ja.md#security-dns)

### Tailscale へのログ

Reqcove のノードは Tailscale にログを送りません。データプレーンの監査ログを必須にしている tailnet には対応していません（`reqcove status` がそう伝えます）。Reqcove がログを有効にすることはありません。

## 保存するものと読める人

Reqcove がディスクに保存するものは、状態ディレクトリにあります。状態ディレクトリのモードは 0700、中のファイルは 0600 です。つまり、読み書きできるのはあなたの OS ユーザーと、そのユーザーとして動くプロセスだけです。記録そのものはメモリにだけあります。

| 状態ディレクトリにあるもの | 中身 |
|---|---|
| `mitmproxy/mitmproxy-ca.pem`、`mitmproxy/mitmproxy-ca.p12` | CA とその秘密鍵 |
| `tsnet/` | ノードの鍵と、tsnet 自身のログの行 |
| `ui-token`、`web-token`、`mcp-token` | `--ui`、`--web`、`--mcp-http` のトークン |
| `login-url`、`links` | ログイン待ちの間のログイン用の URL と、`run` の準備ができたあとのトークン付きのリンク |
| `lan-allowed` | LAN モードで許可したアドレス |
| `mitmproxy.log` | mitmproxy のエラーの行だけ |
| `ca-copies`（`~/.reqcove` の中） | CA のコピーを持つ、ほかの状態ディレクトリの一覧 |
| そのほか | mitmproxy のロックファイルとランチャー、SOCKS5 のパスワード、3 つのソケット。`--local-proxy` のときは、元に戻すためのシステムのプロキシ設定 |

Reqcove が確かめるのは状態ディレクトリそのもので、その上のディレクトリは確かめません。状態ディレクトリ（と `--state`）は、あなただけが書き込めるディレクトリの下に置いてください。親ディレクトリで項目の名前を変えられる人は、状態ディレクトリを自分のものに差し替えられます。

### CA の秘密鍵

- `~/.reqcove/mitmproxy/mitmproxy-ca.pem` と、その隣の `mitmproxy-ca.p12`（パスフレーズのない PKCS#12 ファイル）には、あなたの iPhone が信頼する CA の秘密鍵が入っています。これを持つ人はその iPhone に対してどの HTTPS サイトにもなりすませます。
- この CA は使える名前を制限していません（mitmproxy のコードから判断したもので、試していません）。CA を信頼したデバイスは、`--allow-hosts` のホストだけでなく、すべての HTTPS サイトについて CA を信頼します。`--allow-hosts` は Reqcove が復号する範囲で、鍵が署名できる範囲ではありません。
- CA は最初の起動時に作られ、有効期間は 10 年です（mitmproxy 12.3.1 が CA に付ける期間で、コードから判断したものです）。期限は `run` と `reqcove status` が表示します。
- 信頼はデバイスからプロファイルを削除するまで続きます。`run` を止めても、`reqcove cleanup` を実行しても、状態ディレクトリを削除しても、信頼は消えません。
- このディレクトリは自分だけのものにしておいてください。Reqcove を使うのをやめるときは、先に iPhone からプロファイルを削除し、それからディレクトリを削除します（手順は `reqcove cleanup` が表示します）。
- ディレクトリを別のコンピュータにコピーすると、鍵もコピーされます。
- CA のない `--state` のディレクトリは起動時に `~/.reqcove` の CA のコピーを、鍵も含めて受け取ります。上の「ディレクトリを削除します」は、コピーを受け取ったディレクトリもすべて削除するという意味です。すべてを止めるには、iPhone からプロファイルを削除します。
- バックアップにも鍵が入ります（コードから判断したもので、バックアップの中身は見ていません）。このディレクトリをバックアップから外すか、バックアップも鍵のある場所の 1 つとして扱ってください。

[詳細](guide.ja.md#security-ca-copies)

確認状況：E2E テストが確かめるのは、CA の有効期間が 9 年を超えることだけです。

### ログイン用の URL

ノードがログインしていない間、`reqcove run` はログイン用の URL を表示します。それを最初に開いた人がこのノードを自分の tailnet に入れることになります。`--ui`、`--web`、`--mcp-http` のトークンを含むリンクも、同じように扱います。

- ログイン用の URL とリンクを表示するのは、`run` のターミナルと `reqcove links` だけです。ログの行と MCP ツールには出しません。`status` ツールは、ログイン用の URL がどこで見られるかを伝えるだけで、URL そのものは返しません。そのため、エージェントにも、モデルの提供元にも URL は渡りません。
- `reqcove links` は、出力先がターミナルでないときは断ります。これはエージェントが実行するのを防ぐ助けで、保証ではありません（プログラムはターミナルを用意できます）。
- 状態ディレクトリでは、URL とリンクは 0600 のファイル（あなたのユーザーだけが読み書きできるファイル）にあります。0600 が防ぐのはほかのユーザーで、あなたとして動くプログラムではありません。シェルを使えるエージェントは、これらのファイルを読めます。同じディレクトリにあるノードの鍵、トークン、CA の鍵も読めます。

[詳細](guide.ja.md#security-login-url)

### ログ

`mitmproxy.log` に入るのは、mitmproxy のエラーの行だけです。`run` 自身の出力がファイルのとき（リダイレクト先や、サービスのログ）は、`run` が起動時に、最初の行を書く前にそのファイルを 0600 にします。この出力にはトークンもログイン用の URL も入りません。入るのは、`run` がデバイスについてログに出すものです。[詳細](guide.ja.md#security-logs)

### `reqcove cleanup` のあとに残るもの

`reqcove cleanup` は手順を表示するだけで、自分では何も行いません。例外は 1 つで、途中で落ちた `run` が `--local-proxy` に向けたままにしたシステムの Web プロキシは、元に戻します。`--delete-state` を付けると、状態ディレクトリ（ノードの鍵、CA とその鍵、トークン、`lan-allowed`、そこにあるログ）も削除します。ただし、`run` がそのディレクトリを使っている間、元に戻すプロキシの設定がまだそこにある間、Reqcove のものでないディレクトリは削除しません（コードから判断したものです）。

次のものは、あなたが取り除くまで残ります。それぞれの取り除き方はガイドの[詳細](guide.ja.md#security-cleanup)にあります。

- 各デバイスの CA のプロファイルと、このコンピュータやシミュレーターでの CA の信頼
- tailnet のノード
- ほかの状態ディレクトリ
- サービス
- Skill と、エージェントの MCP サーバーの登録
- Reqcove の外に出たもの（HAR ファイル、エージェントの会話の記録、バックアップ、uv のキャッシュ）

### コンテナで動かす場合

サイトが送ってきたものを開く mitmproxy は、コンテナの中で動きます。mitmproxy に欠陥があっても、届くのはコンテナ（記録と、volume にある CA の鍵）までで、ユーザーのほかのファイルには届きません。イメージにはシェルもパッケージ管理もなく、root ではない専用のユーザーで動きます。その代わり、Docker デーモンのソケットを使える人は、CA の鍵を含めて volume を読めます。コンテナにターミナルを付けたとき（`docker run -t`）は、コンテナを削除するまで、`docker logs` にログイン用の URL、リンク、`--mcp-http` のトークンが残ります。

動かし方は [container.ja.md](container.ja.md) にあります。[詳細](guide.ja.md#security-container)

## 使える人

- あなたの OS ユーザーを信頼します。状態ディレクトリと、その中の MCP ソケットを使えるのは、そのユーザーだけです。そのユーザーとして動くプロセスはどれも、記録と CA の秘密鍵を読めます。Reqcove はそれより強いことは約束しません。
- 指定したデバイスは Exit Node を使うことについてだけ信頼します。tailnet のほかのデバイスからの通信は、Exit Node でも Remote Proxy でも拒否します。
- デバイス名は、各デバイスが自分で名乗るものです。そのため、`--device` にデバイス名を書けるのは、あなた自身のユーザーのデバイスだけです。そのデバイスにも Reqcove のノードにもタグが付いていないことも条件です（タグ付きのノードは、タグを付けた人のユーザー ID を持ち続けます）。ほかのデバイスはマシン名、IP、StableID で指定してください。
- LAN モード（`--lan`）では許可したアドレスを、プロキシを使うことについて信頼します。パスワードはありません。信頼するのはアドレスで、デバイスではありません（[LAN モード](#lan-モード--lan)）。

### デバイスから届く範囲

Exit Node と Remote Proxy を通してデバイスから届くのは、公開の IPv4 アドレスです。Reqcove は次のものを拒否します。

- このコンピュータ自身のアドレス（すべてのインターフェイスのもの）と、そのインターフェイスがつながっているネットワーク。そのため、公開アドレスを使う LAN や、クラウドサーバーのサブネットにいる隣のサーバーも拒否します。
- ループバック、プライベートとリンクローカルの範囲、tailnet の範囲、マルチキャスト、そのほかの特殊用途の範囲。
- IPv6 のすべて。

**拾えないもの：あなたのネットワークの公開アドレス。** これは、このコンピュータのインターフェイスのアドレスではありません。そこへ接続したデバイスは、ルーターが転送する先（ポートフォワーディング）や、クラウドサーバーではこのコンピュータに届くかもしれません。テストしていません。

経路、ping、UDP については、ガイドの[詳細](guide.ja.md#security-reach)にあります。

### ほかのユーザーと共有するコンピュータ

Reqcove が信頼するのはあなたの OS ユーザーで、同じコンピュータのほかのユーザーではありません。ほかのユーザーはファイルのモードで締め出します。状態ディレクトリは 0700、中のファイルは 0600 で、そこにある 3 つのソケットも同じです。そのため、ほかのユーザーは記録を読むことも、ツールを呼ぶことも、鍵を取ることもできません（それぞれを作るコードから判断したもので、2 人目のユーザーでは試していません）。それでも、ほかのユーザーには次のことができます。

- `ps` で `run` と mitmproxy のコマンドラインを見ること。デバイス名とホストが出ます。`--mask-names` や `--mask-values` を `@FILE` ではなくコマンドラインに書いたときは、それも出ます。SOCKS5 のパスワード、トークン、mitmweb のパスワードは出ません。
- `--local-proxy` を通してリクエストを送ること。このポートはどのユーザーのリクエストも受け付けます。
- ノードのポートに届くこと。このコンピュータ自体があなたとして tailnet に入っているときの話です。`--ui`、`--web`、`--mcp-http` からほかのユーザーを締め出しているのは、トークンです（コードから判断したもので、試していません）。
- 状態ディレクトリの外に書いたものを読むこと。HAR ファイルのモードはシェルの設定に従うので、たいていほかのユーザーも読めます。

root と、あなたのユーザーになれる人は対象外です。[詳細](guide.ja.md#security-shared-computer)

### このコンピュータのほかのプロセス

mitmproxy の SOCKS5 のポートは 127.0.0.1 にあり、パスワードで守ります。パスワードは起動のたびに作り、0600 のファイルに保存します。プロセスの引数には入れません。パスワードを知っているのは Reqcove だけなので、ほかのローカルのプロセスはプロキシを使うことも、デバイスになりすますこともできません。ポートは、mitmproxy を起動し直す間も含めて、`run` の間ずっと Reqcove が持ち続けます。パスワードの確認が読み込まれる前に接続を読むことはありません。

あなた自身のユーザーのプロセス（どのみちパスワードのファイルを読めます）と root は対象外です。別のユーザーでは試していません。ポートの持ち方と試したことは、ガイドの[詳細](guide.ja.md#security-other-processes)にあります。

## マスク

Reqcove が見分けられるシークレットは、届いた時点でマスクします。そのため、どのツールもシークレットを返せません。`--no-redact` を付けると、マスクをしなくなります。

- 名前で見分けます。ヘッダー、クエリパラメータ、ボディのフィールドは、名前がシークレットを表していれば（`token`、`password`、`apiKey` など）、値をマスクします。Cookie の値は名前に関係なくマスクします。
- 形で見分けます。`Bearer`、`Basic`、`Token` の認証情報、JWT、よく知られた接頭辞を持つキーは、どこにあってもマスクします。
- 形式ごとに読みます。JSON、フォーム、テキストの行、GraphQL、XML、HTML と JavaScript、`multipart/form-data`、protobuf、gRPC、WebSocket のメッセージを、それぞれの形式として読み、シークレットの名前を探します。
- あなたの規則を足せます。`--mask-names` と `--mask-values` で、名前とパターンを足せます。

対象の語、形、形式ごとの読み方と、それぞれでマスクされずに残るものは、[masking.ja.md](masking.ja.md) にあります。主な抜けは次のとおりです。

- シークレットだと分からない名前の下にあるシークレット（`{"data": "…"}`）。どの形式でも同じです。`--mask-names` や `--mask-values` で足せます。
- メールアドレスや名前などの個人データ。デバッグに必要なので、マスクしません。
- マスクが読まない形式の中のシークレット（`multipart/mixed`、base64 の `SAMLResponse` フォームフィールド）と、名前ではなく位置で渡されるシークレット。
- マスクが見られなかったボディ（テキストでないもの、デコードできなかったもの）。マスクが有効な間は渡しも検索もしません。`--no-redact` を付けると返します。
- マスクが見つけられなかったシークレットは、エージェントとモデルの提供元に残ります（[上記](#エージェントが読んだものの行き先)）。

## 拾えないもの

次の接続は何も残しません。記録もされず、数えられもしません。条件と確かめ方は [masking.ja.md](masking.ja.md#記録が残らない接続) にあります。

- mitmproxy が自分で素通しする接続。Apple のホスト、`--allow-hosts` にないホスト、mitmproxy がアドレスでしか知らない接続です。
- SNI のない TLS。`--allow-hosts` にそのアドレスを書いたときは別です。
- 80 番か 443 番ポートの平文の TCP のうち、最初のバイト列が mitmproxy の読み方では許可したホストを示さないもの。TLS なしの HTTP/2 がその一例です。
- 許可したホストへの HTTP/2 のリクエストのうち、アプリが一覧にない兄弟の名前のために開いた接続に相乗りしたもの。証明書を共有する名前をまとめて許可してください（`*.example.com`）。
- Encrypted Client Hello を使う TLS。プロバイダーの公開名を許可したときは別です。
- 許可したホストへの接続のうち、HTTP/1 の最初のリクエストが `Host` で Apple のホストを指定したもの。接続全体が復号されたまま中継されます。
- アドレスで許可され、SNI には別の名前がある接続のうち、mitmproxy が raw TCP として運ぶもの。
- TLS のハンドシェイクを終えたあとで Reqcove の証明書を拒否して閉じるクライアントと、リクエストを送らずに閉じるクライアント。証明書を自分で確かめるピンニングのアプリがこれに当たります。ハンドシェイクの途中で拒否するアプリは、一覧に出ます。

## 露出を広げるオプション

オプションごとに、何が見えるようになるか、誰に見えるか、主な限界、あなたがすることを書きます。動作の詳細と確かめたことは、ガイドの各オプションの節にある「セキュリティの詳細」に書いています。

次の 3 つのオプションはノードのポートを開きます。

| オプション | ポート | 届くデバイス | 守るもの |
|---|---|---|---|
| `--ui` | 80 | あなた自身のデバイスと、`--device` のデバイス | トークン（`ui-token`）。Cookie として設定します |
| `--web` | 8081（mitmweb に中継） | あなた自身のデバイス | mitmweb のパスワード（`web-token`） |
| `--mcp-http` | 8090 の `/mcp` | あなた自身のデバイス | トークン（`mcp-token`）。`Authorization: Bearer` で送ります |

どのポートも `Host` でノード（その MagicDNS 名か tailnet アドレス）を指定したリクエストにだけ応答します。トークンは状態ディレクトリにある 0600 のファイルで、ログイン用の URL と同じく、`run` のターミナルと `reqcove links` にだけ出ます（[ログイン用の URL](#ログイン用の-url)）。

### mitmweb（`--web`）

mitmweb は通信を**マスクなし**で表示します。mitmproxy が復号したすべてのフローが、ボディも含めて見えます。パスワードを持つ人は誰でも、そのページからリクエストを編集してリプレイでき、オプション（スクリプトを含みます）を変えられます。オプションを変えると、このコンピュータでコードが動きます。mitmweb に届くのは、このコンピュータと、ノードを通したあなた自身のデバイスだけです。パスワードは起動のたびに同じです。変えるには、`web-token` を削除して起動し直します。[詳細](guide.ja.md#security-web)

### ページ（`--ui`）

`--ui` は記録の読み取り専用のページを提供します。中身は MCP ツールが返すものと同じようにマスクされています。ページを読めるのは、あなた自身のデバイスと `--device` のデバイスのうち、トークンを持つブラウザだけです。別のユーザーの `--device` のデバイスに見えるのは、自分のフローだけです。トークンは起動のたびに同じなので、リンクは `ui-token` を削除して起動し直すまで使えます。Safari の履歴には、表示したページの URL と検索の URL が残ることがあります。[詳細](guide.ja.md#security-ui)

### HTTP 経由の MCP（`--mcp-http`）

ノードはトークンを送ってきたあなた自身のデバイスに MCP ツールを提供します。個人の tailnet では、Tailscale の OAuth アプリを通して参加したエージェントのデバイス（Grok Bot）も、あなた自身のデバイスの 1 つになります。ツールの答えはそのデバイスと、そのモデルの提供元に届きます。返すのはマスクされた同じ記録です。プリセット、ルール、マーカーのツールはありません。エージェントは、あなたが `mcp-token` を削除して `run` を再起動するまで、トークンを持ち続けます。[詳細](guide.ja.md#security-mcp-http)

### ローカルプロキシ（`--local-proxy`）

このコンピュータ自身のアプリ（iOS シミュレーター）のための、127.0.0.1:8082 の HTTP プロキシです。パスワードはありません。このコンピュータのプロセスはどのユーザーのものでも、このプロキシを使えます。プロキシが `--allow-hosts` のホストへ送るものは、`local` というデバイスとして記録します。このコンピュータのブラウザで開いたページは、自分の名前を LAN、VPN、tailnet のアドレスに向けて、プロキシを通してそこに届くことができます（DNS リバインディング）。`--local-proxy` は、必要な間だけ有効にしてください。Reqcove が、このコンピュータに CA を信頼させることはありません。あなたが信頼させると、CA の秘密鍵で、このコンピュータに対してもどの HTTPS サイトにもなりすませるようになります。終わったら信頼を外してください。[詳細](guide.ja.md#security-local-proxy)

### LAN モード（`--lan`）

`run --lan` は tailnet のノードを起動しません。HTTP プロキシがこのコンピュータの LAN のアドレスの 1 つで待ち受けます。パスワードはありません。誰が使えるかはアドレスで決めます。アドレスはデバイスではないので、許可したアドレスをあとで持った人も許可されます。このネットワークでも、同じプレフィックスを持つ別のネットワークでも同じです。許可したアドレスは 80 番と 443 番ポートで公開のアドレスに届きます。プライベートなアドレスには `--allow-hosts` に完全な名前で書いたものにだけ届きます。このコンピュータと、プロキシのあるネットワークには届きません。LAN モードは信頼できるネットワークで使い、終わったら止めてください。[詳細](guide.ja.md#security-lan)

### 上流プロキシ（`--upstream-proxy`）

このオプションを付けると、復号した HTTP(S) のリクエストは上流プロキシを通って進みます。プロキシには、リクエストとレスポンスがマスクなしで見えます（たとえば Burp は、それをプロジェクトとしてディスクに保存します）。本物のサーバーの証明書を検証するのも、プロキシの仕事になります。どこに接続するかも、プロキシが決めます。Burp は名前をこのコンピュータでもう一度引くので、このコンピュータの LAN の中に解決される名前は、Exit Node の拒否をすり抜けて LAN に届きます。`--allow-hosts` は狭くしておき、プロキシはこのコンピュータか tailnet に置いてください。[詳細](guide.ja.md#security-upstream-proxy)

### ルール（`--rules`）

ルールはあなたのもので、mitmproxy の起動時にファイルから読みます。ルールを書いたり変えたりする MCP ツールはありません。他人が作ったルールファイルはコードです。あなたのアプリのリクエストを、Cookie やトークンも含めて、どこへでも送れます。`map_remote` と `resolve` はこのコンピュータから接続します。接続先にはこのコンピュータと LAN も含まれます。`mock` はサイトの名前で応答します。`--rules-reload` を付けると、ファイルに書き込めるもの（ファイルを扱えるエージェントも含みます）は、`run` が動いている間に、デバイスのリクエストの行き先を変えられます。[詳細](guide.ja.md#security-rules)

### モックのプリセット

ルールファイルで `preset: NAME` を付けたモックは、エージェントが `activate_preset` で有効にするまで何もしません。プリセットを書くことが、エージェントが有効にしてよいという、あなたの同意です。エージェントが有効にできるのは、あなたが書いたものだけです。有効にできるのは 1 回につき最長 5 分で、有効にし直す回数に上限はありません。サイトが記録に書き込んだ文が、そうするようエージェントを誘導しようとすることがあります。読み取りのツールは名前で個別に許可してください。`"mcp__reqcove"` をまとめて許可したクライアントは、確認なしでプリセットを有効にします。[詳細](guide.ja.md#security-mock-presets)

### map_remote、modify_headers、resolve のプリセット

これらの種類のプリセットは有効な間、デバイスのリクエストの行き先や中身を変えます。`map_remote` のプリセットは一致したリクエストを、アプリの Cookie、トークン、ログインのボディと一緒に、あなたが書いた送り先へ送ります。エージェントは送り先を選べません。選べるのは、いつ有効にするかだけです。考えておくべき危険は古くなった送り先です。今は別の人が持っている、古いトンネルやステージングの名前がこれに当たります。5 分が区切るのは切り替えで、その影響ではありません。アプリはそこで受け取ったものを持ち続けるかもしれません。[詳細](guide.ja.md#security-presets)

### フラグのファイル（`--config`）

`run --config FILE`（`brew services` と `reqcove service install` のためのもの）は、`run` のフラグをファイルから読みます。つまり、そのファイルに書き込めるものが、次の起動のフラグを決めます。ファイルはあなたのもので、あなただけが読めるものでなければなりません。次の 5 つのフラグはファイルでは断るので、コマンドラインで指定してください。`--no-redact`、`--web`、`--allow-hosts '*'`、`--rules-reload`、`--lan` です。[詳細](guide.ja.md#security-config)

## プロンプトインジェクション

記録の中身は、ほかの人が書いたものです。レスポンスのボディ、レスポンスのヘッダー、ステータスの理由の文、リダイレクト先、エラーメッセージは、リモートのサイトが書きます。そこには、エージェントを誘導するための文が入っているかもしれません。アプリは自分の User-Agent、TLS の名前、送る JSON のキーを選びます。tailnet のピアは自分のデバイス名を選びます。

- Reqcove のツールは読むだけですが、例外が 1 つあります。エージェントは、あなたがプリセットにしたルールを有効にできます（[モックのプリセット](#モックのプリセット)、[ほかの種類のプリセット](#map_remotemodify_headersresolve-のプリセット)）。ルールを書いたり変えたりするツールはありません。プリセットがなければ、エージェントが何を呼んでも通信は変わりません。
- エージェントはほかのツールも持っているかもしれません。シェル、ファイルの書き込み、ネットワーク、ほかの MCP サーバーです。サイトが記録に書き込んだ文は、それらを使うようエージェントを誘導しようとすることがあります（Cookie をどこかへ送る、ファイルを編集する）。Reqcove の側からはこれを止められません。止められるのはエージェント自身の設定です。
- Reqcove を読むエージェントには、作業に必要なものだけを与えてください。Reqcove を読んであなたに答えるだけのエージェントが、いちばん安全な形です。Claude Code では Reqcove の読み取りのツールを名前で許可し（`activate_preset` は入れません）、シェルのコマンドやネットワークのツールを一緒に許可しないでください。Codex ではサンドボックスと承認を残してください。
- サイト、アプリ、tailnet が書いたものを返すツールは、どれも説明の中で、それがデータで指示ではないと伝えています。すべてのクライアントに送られるサーバーの instructions も、同じことを伝えています。モデルがこれを守るかどうかは、テストでは示せません。
- 記録からは証明できないこともあります。フローのホストは、アプリが選ぶリクエストの Host です。マーカーの `source` は経路で、証明にはなりません。

[詳細](guide.ja.md#security-agent)

## mitmproxy 自身のコード

mitmproxy とその依存パッケージ（44 個）は、Reqcove に組み込まれたロックファイルから来ます。`run` は `uv run --locked --script` で mitmproxy を起動します。このコマンドはロックに書かれたファイルだけをインストールし、それぞれのハッシュを確かめます。CI は、ロックに既知の脆弱性がないかを監査します（pip-audit）。

- 素の `uvx` はハッシュを与えられても確かめません。素の `uvx` を使うのは、別の `--mitmproxy-spec` のときと、`--uvx` のファイル名が `uvx` でないときです。
- ロックはバージョンを 1 つ上書きしています。mitmproxy 12.3.1 は mitmweb のサーバーである tornado を 6.5.10 までに制限しています。監査は 6.5.10 に 3 つの脆弱性を見つけました。ロックは 6.6.1 に固定しています。6.6 がその 3 つを直し、6.6 自体には CVE-2026-126347 があるからです。この組み合わせで mitmproxy 自身のテストは実行していません。

[詳細](guide.ja.md#security-mitmproxy-code)

## あなたの責任

次のことは、Reqcove ではなくあなたが行います。

- **同意を得る。** ほかの人のデバイスを中継して記録するのは、その人の同意があるときだけにしてください（[下記](#ほかの人のデバイス)）。
- **CA を片付ける。** 使うのをやめるときは、各デバイスからプロファイルを削除してください。状態ディレクトリと、そのコピーやバックアップは、人に渡さないでください（[CA の秘密鍵](#ca-の秘密鍵)、[`reqcove cleanup` のあとに残るもの](#reqcove-cleanup-のあとに残るもの)）。
- **共有のコンピュータに気を付ける。** ほかのユーザーに見えるものと届くものがあります（[ほかのユーザーと共有するコンピュータ](#ほかのユーザーと共有するコンピュータ)）。
- **エージェントが読めるものとできることを絞る。** `--allow-hosts` を狭くし、エージェントには作業に必要なツールだけを与えてください（[プロンプトインジェクション](#プロンプトインジェクション)）。

### ほかの人のデバイス

`--device` にはあなたのものではないデバイスも指定できます。LAN モードは、あなたが許可したアドレスなら何でも中継します。

- デバイスを中継して記録するのは、それを使う人の同意があるときだけにしてください。
- 許可したホストへのリクエストは、復号されて記録されます。エージェントがそこから読んだものは、モデルの提供元に送られます。
- そのデバイスは、プロファイルを削除するまで、あなたが鍵を持つ CA を、すべてのサイトについて信頼します（[CA の秘密鍵](#ca-の秘密鍵)）。
- Reqcove は誰にも尋ねず、同意があるかどうかも確かめません（コードから判断したもので、試していません）。
- 同意なしに人の通信を記録することは、あなたのいる場所の法律に反するかもしれません。
- あなた自身のデバイスの通信にも、ほかの人の言葉が入っています（チャットのメッセージ）。個人データはマスクしません。
