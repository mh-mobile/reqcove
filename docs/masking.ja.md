# Reqcove がマスクするものとしないもの

[English](masking.md)

マスクの目的は [SECURITY.ja.md](SECURITY.ja.md#マスク) にあります。このページはその詳細で、あなたのアプリが送るものがマスクの対象かどうかを確かめるためのものです。シークレットと見なす名前と形、ボディの種類ごとの読み方、記録が保持するもの、記録が残らない接続を説明します。対象は v1.0 です。

Reqcove が見分けられるシークレットは、届いた時点でマスクします。そのため、どのツールもそのシークレットを返せません。見分けられなかったシークレットは、読める状態のまま残ることがあります。どこで残るかは下の表に太字で書いています（**マスクしません**、**拾えません**、**見つけられません**）。`--no-redact` を付けると、マスクをしなくなります。

試していない点と、コードから判断した点には、その場所にそう書いています。テストや実機で確かめたことは、各節の最後の「確認状況」に書いています。mitmproxy はどれも 12.3.1 です。iPhone で試したのは、その行に iPhone と書いてあるものだけです（iOS 27.3）。

## シークレットと見なす名前

ヘッダー、クエリパラメータ、ボディのフィールドは、名前でシークレットと判断します。名前は記号と大文字・小文字の変わり目で語に分けます。そのため、`apiKey`、`XAuth`、`X-Amz-Signature` はシークレットで、`author` と `keyword` はシークレットではありません。

| シークレットと見なす条件 | 語 |
|---|---|
| 次の語のどれかを含む。ほかの語とつながっていても同じです（`accesstoken`、`X-AuthToken`） | token, secret, password, passwd, passphrase, passcode, credential, signature, session, jwt, apikey, privatekey, authorization, authentication, csrf, xsrf, ticket（WebSocket の `wsTicket`）, dpop, hmac, verifier（OAuth の `oauth_verifier`）, privkey, mnemonic（ウォレットの復元フレーズ） |
| 次の語のどれかが、1 語として入っている。語のあとに数字が付いていても同じです（`key1`、`pin2`） | auth, key, sid, sig, sign（アプリのリクエスト署名のヘッダー `sign`）, pwd, pw, pass, otp, totp, pin, code |

| シークレットと見なさないもの | 補足 |
|---|---|
| `auth0`（`Auth0-Client` など） | Auth0 というサービスの名前です |
| 日常の語と並んだ `code` と `key`：`country_code`、`error_code`、`sort_key`、`foreign_key` | `primaryKey` はシークレットです |
| `token_type`、`ticket_id`、`ticketNumber` | |
| `Access-Control-Allow-Credentials` | CORS のヘッダーで、値は `true` しかありません |
| ボディの `"key"` のうち、値がドットで区切った小文字の名前であるもの：`{"key": "service.name", …}` | OpenTelemetry が属性を書く形です。本物のキーは、大文字と小文字が混ざっているか、ドットがありません。URL の `key=` はシークレットのままです |
| レスポンスにある単独の `code` | たいていエラーコードです。`verification_code` と `device_code` はマスクします。リクエストでは単独の `code` もマスクします。ワンタイムコードや OAuth のコードが入るからです |

JWT など、[形で見分けるもの](#フィールドに関係なくマスクする形)は、フィールドの名前に関係なくマスクします。

## 名前と形を探す場所

| 場所 | マスクするもの | 残すもの、拾えないもの |
|---|---|---|
| ヘッダー | シークレットの名前を持つヘッダーの値。値のどこにあっても、認証情報の形 | |
| Cookie | すべての Cookie の値。名前のない値も同じです | 名前と、Cookie の属性 |
| 複数の Cookie をカンマでつないだ `Set-Cookie` の行（サーバーはこの形で送ることがあり、送られたまま記録します） | それぞれの Cookie | あいだに属性のない Cookie どうしは、1 つの値としてマスクします。Cookie の最初の `;` より前のカンマは、`v1,QUJD…==` のように値の一部であることがあるからです |
| URL。現れる場所を問いません。ヘッダー（`Referer`、`Location`、`Link` など）、フラグメント（`#/callback?access_token=`）、別のパラメータの中の URL（2 回や 3 回エンコードされていても同じです）、ボディ、エラーメッセージ | シークレットの名前を持つクエリパラメータ。URL のパスワード（`https://user:…@host`） | |
| レスポンスの理由の文（reason） | 同じようにマスクします | |
| `WWW-Authenticate` | 認証情報の形だけ | チャレンジ（スキーム、realm、エラー） |
| `Sec-WebSocket-Protocol` | そこに入っている認証情報。`access_token` のような名前のあとの値、AppSync の `header-` に続く base64 の JSON、Kubernetes の bearer の接頭辞のあとの値、ドット区切りの名前ではない、認証情報の形をした長い値です | |
| ホスト名（フローの `host`、SNI）、メソッド、`list_passthrough` の接続が提示した ALPN の名前と選ばれた ALPN の名前、ボディの `Content-Encoding` と、それを引用する注記 | 認証情報の形 | 記録の範囲は送られたままのホストで確かめます |
| エラーメッセージ | 形と URL。mitmproxy が引用する生のバイト列（`b'…'`）は、全体をマスクします | |
| gRPC のレスポンスのトレーラー | ヘッダーと同じ | `-bin` で終わるメタデータ（バイナリ）は、サイズだけを残します |
| gRPC の `grpc-message` | デコードしてから、ほかのヘッダーの値と同じように（形と URL で）マスクし、1 KiB に切ります | その中に自由な文で書かれた `password=…` は拾えません |
| WebSocket の close の理由、マーカーの文 | エラーの文と同じ | |

確認状況：テスト。カンマでつないだ `Set-Cookie` の行は E2E テストで確かめています。

## フィールドに関係なくマスクする形

形で見分けられる認証情報は、ヘッダーの値、URL、ボディ、エラーメッセージのどこにあってもマスクします。

| 形 | 補足 |
|---|---|
| 認証情報に見える `Bearer`、`Basic`、`Token` の値 | 文の次の語は対象外です |
| JWT | |
| よく知られた接頭辞を持つキー | GitHub、`sk-…`、Slack、AWS のアクセスキー ID、Google の API キー |
| パーセントエンコードされた上の形 | フォームフィールドや URL パラメータの中でエンコードされた JSON、`Bearer+…` |
| JSON のエスケープの向こうにある上の形 | `Basic\t…`、トークンの中の `\/` や `\u…`。エスケープを含む文字列は、デコードして読みます。最上位でも、文字列の中の JSON でも、途中で切れた文字列でも同じです |
| URL パラメータやフォームフィールドに入った、シークレットを含む JSON オブジェクトの base64 | AppSync の `?header=`。全体をマスクします |

確認状況：テスト。

## ボディの形式ごとの扱い

ボディは 64 KiB まで、メモリにだけ保持します。マスクはその先頭部分に対して働きます。先頭部分は途中で切れていることがあります。閉じる引用符の前で切れた値も、マスクします。上の形は、形式に関係なく、すべてのボディでマスクします。

確認状況：ファズテスト（この節の形を、あらゆる位置で切って確かめます）。

### JSON

Content-Type が何であっても、JSON は JSON として読みます。

| JSON の中 | 結果 |
|---|---|
| シークレットの名前を持つフィールドで、値が文字列か数値のもの | マスクします |
| シークレットの名前を持つフィールドで、値がリストかオブジェクトのもの | 全体をマスクします：`{"password": "[redacted]"}` |
| JSON の中の文字列として送られた JSON と、フォームフィールドとして送られた JSON | 同じようにマスクします。対象は 1 段だけです |
| 単独の `code` | リクエストではマスクし、レスポンスでは残します |
| シークレットだと分からない名前の下にあるシークレット：`{"data": "…"}` | **マスクしません。** `--mask-names` や `--mask-values` で足せます |

確認状況：テストとファズテスト。

### フォーム

| フォームの中 | 結果 |
|---|---|
| シークレットの名前を持つフィールド。単独の `code` も含みます | マスクします。フォームに見えるボディ（1 行のもの。末尾に改行があってもかまいません）も、フォームとして扱います |
| SAML の POST バインディング。アサーションを base64 の `SAMLResponse` フィールドで送ります | **マスクしません。** このフィールドはデコードしないからです |

確認状況：テストとファズテスト。`SAMLResponse` フィールドがそのまま通ることも、テストで確かめています。

### テキストの `name: value` と `name=value` の行

| GraphQL のドキュメントではないテキストのボディと、JSON の文字列の中 | 結果 |
|---|---|
| 名前がシークレットである行。STOMP フレームの `passcode:`（SockJS の JSON の中でも）、YAML のマッピング、ボディに書かれたヘッダー、`.env` ファイルの `API_KEY=…`（`export` のあとでも） | 行の残りを、すべてマスクします。`Bearer`、`Basic`、`Token` のスキームを残すのは、値がその認証情報だけのときです |
| YAML のリスト項目（`- password: …`）と、引用符付きの名前 | **マスクしません。** ここは見ません |

確認状況：テスト。

### GraphQL

ドキュメントは字句解析器で読みます。ドキュメントを見つけるのは、ドキュメントらしく始まっている場所です。最上位の JSON の文字列、文字列の中の JSON にある文字列（キーは問いません。リクエストでも、それを返すレスポンスでも同じです）、ボディ、URL パラメータ（GET の `?query=`。マスクしてからエスケープし直します）が対象です。

| GraphQL のドキュメントの中 | 結果 |
|---|---|
| シークレットの名前を持つ引数、入力オブジェクトのフィールド、変数のデフォルト値 | JSON のフィールドと同じように、値全体をマスクします。値が文字列、数値、リスト、オブジェクトのどれでも同じです。`login(password: "[redacted]", pin: "[redacted]")` |
| enum と真偽値、`$variables`、エイリアス | 残します |
| GraphQL の variables として送られた値 | JSON のフィールドなので、名前でマスクします |
| ドキュメントらしく始まっていて、読めないもの | 全体をマスクします |
| スクリプトのオブジェクトのように始まるもの（`{a: b, …}`。最初の値のあとにカンマがあるもの） | そのまま残します |
| シークレットだと分からない名前の下にあるシークレット | **マスクしません。** そのため、ID は読めるままで、`diff_flows` で比べられます（OpenTelemetry や Apollo のように GraphQL を解析するツールは、クエリに書かれた値をすべて落とします） |
| 前に文章があって、メッセージの途中に引用されたドキュメント | **見つけられません** |

確認状況：テストとファズテスト。

### XML

XML として読むのは、Content-Type が `text/xml`、`application/xml`、`application/*+xml`（SOAP の `application/soap+xml` など）のボディと、`<?xml` で始まるボディです。トークンごとに読み、名前だけでマスクします。ほかの部分は届いたバイト列のまま残します（接頭辞、エンティティ、空白）。その上で、テキストとしてのマスクも当てます。

| XML の中 | 結果 |
|---|---|
| ローカル名がシークレットである要素（`wsse:Password` は `Password` として扱います） | 中身全体をマスクします（テキスト、CDATA、子要素、コメント）。マスクは同じローカル名の終了タグまで続きます。途中に紛れた `</i>` では終わりません。`<wsse:Password>[redacted]</wsse:Password>` |
| ローカル名がシークレットである属性 | 値をマスクします。名前空間の宣言は残します |
| SAML の `Assertion` と `EncryptedAssertion` | 全体をマスクします。これは bearer の認証情報で、持っている人は期限が切れるまで提示できます。そのため、subject も属性も表示しません |
| Apple の plist で、`<dict>` の中の、テキストがシークレットである `<key>` のあとの値 | マスクします：`<key>access_token</key><string>[redacted]</string>` |
| `Key` という名前の要素 | JSON の `key` と同じくマスクします。S3 のオブジェクト名もこれに当たります |
| シークレットの要素や属性の値の中で、先頭部分が切れているか、トークンに分けられないとき | 最後までマスクします |
| ほかの場所で、トークンに分けられないもの（XML 1.1 の宣言、`1 < 2`、不正なコメントや名前） | その先も読み続けます（不正なコメントのあとは `-->` から）。読む時間には上限があります。その部分には、テキストとしてのマスクだけが働きます |
| デコーダーが断る開始タグ（`a=b!c`、引用符のない値） | それでも開始タグとして、名前と属性を読みます |
| DTD | 読みません。エンティティを展開することも、取得することもありません。**DTD の中のものは、名前ではマスクしません**（`<!ENTITY p "…">`） |
| ほかの名前の要素や属性にあるシークレット | **マスクしません** |
| シークレットの要素の外にあるコメント | 名前では**マスクしません** |
| シークレットの要素の外で、要素の中のテキストとして運ばれる XML。エスケープされたもの（`&lt;Password&gt;`）と CDATA の中のもの | **XML として読みません** |
| WebSocket のメッセージ | Content-Type がないので、`<?xml` で始まるときだけ XML として読みます。XMPP の `<auth mechanism='PLAIN'>…</auth>` はそのまま通ります |
| XML とラベルの付いた JSON のボディ（`application/xml`） | XML のマスクはJSON のマスクより先にボディを読みます。文字列の中のタグをマスクすると、マスクした値が文字列の終わりを越え、JSON として読むのに必要な引用符がなくなります。すると、**そのあとのシークレットのフィールドが通ります**：`{"xml": "<b data-token=x\"", "password": "…"}`。HTML とラベルの付いたボディでは、JSON として先に読むので、マスクします |
| 宣言されたエンコーディング | 使いません。先頭部分が有効な UTF-8 でないボディ（ASCII 以外の文字を含む Latin-1 や Shift_JIS、UTF-16）はマスクしません。そうしたボディはどれもマスクしないので、渡しも検索もしません |

XML のマスクが、テキストとしてのマスクの手がかりを消すことがあります（マスクした要素の中の引用符）。そのため、テキストとしてのマスクだけのときにマスクされるものが、すべてマスクされるかどうかは確かめていません。

確認状況：テスト（エスケープされた XML と CDATA、XMPP の `<auth>`、XML とラベルの付いた JSON のボディ、UTF-8 でない先頭部分、読む時間の上限、billion laughs の文書など）。マークアップのファズテスト（失敗しないことと、マークアップより前にあるシークレットの要素と属性がマスクされたままであること）。mitmproxy を通した SOAP のリクエストの E2E テスト。

### HTML と JavaScript

HTML として読むのは、Content-Type に `html` を含むボディと、先頭部分が `<!doctype html` か `<html` で始まるボディです。タグごとに読みます。ブラウザと同じ解析はしません。JSON のマスクはこれより先に先頭部分を読みます。そのため、マスクしたタグが JSON の引用符を消すことはありません（`text/html` とラベルの付いた JSON のボディ）。その上で、テキストとしてのマスクの残りも当てます。

| HTML の中 | 結果 |
|---|---|
| `name`、`id`、`property` がシークレットであるタグ。フォームと同じく、単独の `code` も含みます | `value` と `content` をマスクします。OAuth の `form_post` の hidden の `code` と `id_token`、Rails の `authenticity_token`、ASP.NET の `__RequestVerificationToken`、`<meta name="csrf-token">` がこれに当たります |
| そうした名前の `<textarea>` | テキストをマスクします |
| 属性そのものの名前がシークレットである属性（`data-auth-token`） | XML と同じく、値をマスクします |
| 先頭部分の終わりで切れたタグ | 名前に関係なく、`value` と `content` をマスクします。名前がそのあとに来ることがあるからです。切れたシークレットの `<textarea>` は、テキストを最後までマスクします |
| コメントと、`<script>`、`<style>`、`<textarea>`、`<title>` など、テキストがマークアップではない要素のテキスト | その終わりまでを、ひとまとまりとして読みます。中に引用符や `<` があっても（スクリプトの `"<a x='"`）、そのあとのタグを属性の値として読むことはありません。中のタグは読みます（コメントアウトされたフィールド、スクリプトの文字列の中の HTML） |
| `<textarea>` 以外のタグのテキストにあるシークレットと、シークレットだと分からない名前の下にあるシークレット | **マスクしません** |
| 文字参照で書かれた名前（`&#99;ode`） | **マスクしません** |
| ブラウザが最初の `</script>` を越えて読むスクリプトのテキスト（`<script><!--<script>`） | Reqcove は最初の `</script>` で終わりとして読みます |
| SAML の `SAMLResponse` フィールド | フォームと同じく、**マスクしません** |

| HTML の中と、Content-Type が JavaScript のボディの中 | 結果 |
|---|---|
| 引用符のないシークレットの名前を持つ、オブジェクトのフィールド：`{accessToken: "…"}`、`{pin: 1234}`。JSON と同じく、単独の `code` も含みます | 値が文字列、テンプレートリテラル、数値のとき、マスクします。名前とコロンの前後にコメントがあってもマスクします（コメントは 2 つまで、それぞれ 80 バイト以下）。バックスラッシュのあとで行をまたぐ文字列も、マスクします |
| 名前と値のあいだに、それより長いコメントや、3 つ以上のコメントがあるとき | **マスクしません** |
| 引用符付きの名前：`{'accessToken': '…'}` | **マスクしません** |
| 代入：`x.accessToken = "…"` | **マスクしません** |
| 別のテンプレートリテラルを含むテンプレートリテラル | 内側のテンプレートリテラルの手前までだけマスクします |

確認状況：テストとファズテスト（あらゆる位置で切って確かめます）。

### `multipart/form-data`

Reqcove がパートごとに描画したものを渡します（`view` にそう出ます）。読むパートは 256 個までです。

| アップロードの中 | 結果 |
|---|---|
| 名前がシークレットであるパート（リクエストでは単独の `code` も） | 全体をマスクします |
| シークレットの名前を持つパートのヘッダー | マスクします |
| テキストのパート（ファイル名がなく、種類がテキストか JSON のもの） | ボディと同じようにマスクします |
| ファイルのパート。テキストでないパートと、エンコードされたパート（`Content-Transfer-Encoding: base64`）。`Content-Disposition` が読めないパート、2 回出てくるパート、フィールドもファイルも示さないパート | ヘッダーとサイズだけを残します。バイト列は残しません |
| 折り返されたパートのヘッダー（空白かタブで始まる行） | 折り返しを戻して、1 行として読み、マスクします |
| 行が LF だけで区切られたボディ | パートを表示しません |
| プリアンブルとエピローグ | 表示しません |
| `multipart/mixed` | その中のシークレットは**拾えません** |

確認状況：テストと、Go の multipart ライターを使った E2E テスト。

### protobuf と gRPC

protobuf（Content-Type で分かるものと、gRPC のフレームの中のもの）は、バイト列の代わりに、Reqcove が描画したものを渡します（`view` にそう出ます）。

| protobuf | 結果 |
|---|---|
| 最後まで protobuf として読めないボディ | 何も表示しません |
| 印字できるテキスト | 何も表示しません。全体が文字列とサブメッセージだけとして読めるときは別です（印字できる長さの文字列フィールド 1 つは、印字できるテキストです） |
| 終わりの前で切れた先頭部分 | 読めた部分に、文字列かサブメッセージ全体があったときだけ、読めた部分を表示します |
| スキーマがないとき | 構造だけを表示します。フィールド番号、ワイヤタイプ、長さです。文字列は長さだけで、テキストは表示しません |
| スキーマがないときの数値 | レスポンスでは表示します。リクエストでは1 バイトの数値（0〜127。enum や真偽値のほか、それくらい小さい PIN や CVV も入ります）だけを表示します。それより大きい数値はバイト数として表示します。リクエストで単独の `code` をマスクするのと同じ考え方です |
| 印字できるテキストの並び | 必ず文字列として扱い、メッセージとしては読みません。メッセージとして読むと、そのバイトが数値として表示されてしまうからです |
| ランダムなバイト列（`bytes` フィールド） | メッセージとして読めてしまうことがあります。レスポンスでは、たいていそのバイトのすべてが数値として表示されます（16 バイトの値ではおよそ 100 個に 1 個、32 バイトの値では 1,000 個に 1 個が、全体として読めます）。リクエストではその一部（フィールド番号と 1 バイトの数値）が表示されます |
| 長さ | **表示します。** パスワードの長さも分かります |
| `--proto FILE`（コンパイルしたスキーマ。ガイドの [`protoc` コマンド](guide.ja.md#grpc)で作ります）があり、型が分かるメッセージ。型は、gRPC、Connect、Twirp のメソッドのパスか、Content-Type の `messageType` で分かります | フィールド名（proto の名前です。`json_name` は使いません）を付けて JSON として読み、JSON と同じように名前でマスクします。`bytes` は長さを、スキーマにないフィールドは構造を表示します |
| 古いスキーマや誤ったスキーマ | トークンにシークレットだと分からない名前が付くことがあり、そのトークンは**通ります** |
| 組み込みの一覧がシークレットと見なさない名前の下の値（ヘッダーのマップの `cookie` の項目、`cvv`） | JSON と同じく、**マスクしません** |

| gRPC | 結果 |
|---|---|
| フレームに入った JSON のメッセージ | JSON としてマスクします |
| フレームに入った protobuf のメッセージ | 上のとおりに描画します |
| gRPC の Content-Type で、フレームに入っていないボディ | ボディとしてマスクします |
| レスポンスのトレーラー、`-bin` のメタデータ、`grpc-message` | [上記](#名前と形を探す場所) |

確認状況：テスト。ファズテストは、スキーマなしの読み方が対象です。gRPC は HTTP/2 での E2E テストでも確かめています。ガイドの `protoc` コマンドは、protoc 33.0 で 1 回実行しました。

### WebSocket のメッセージ

テキストのメッセージは、先頭の 4 KiB を、ボディと同じように届いた時点でマスクします。クライアントからのメッセージには、リクエストの規則を使います（単独の `code` も含みます）。

| WebSocket | 結果 |
|---|---|
| マスクが読めたテキストのメッセージ。制御文字のないテキストです。STOMP フレームを閉じる NUL と、SignalR が JSON オブジェクトのあいだに置く 0x1e は、あってもかまいません | マスクして残します |
| クライアントからの、トークンの形をした 1 語だけのメッセージ。そのままでも、1 つの JSON 文字列でも同じです | マスクします |
| クライアントからの、イベントの配列のうち、認証のイベント名のあとの文字列。socket.io の `42["authenticate","…"]` で、名前空間や ack の ID が付いていても同じです | マスクします |
| クライアントからの、SignalR の呼び出しのうち、target がそうした名前のときの引数 | マスクします。SignalR のレコードは 1 つずつ読みます。読むのは最初の `target` だけです |
| 引数のもっと深いところにネストした文字列（SignalR でも socket.io でも） | **マスクしません** |
| ほかの方法で位置によって送られる認証情報。そうしたイベント名のない配列や、独自のバイナリのフレーム | ボディと同じく、**拾えません** |
| バイナリのメッセージと、1 つのソケットで 1 秒におよそ 20 件を超えたメッセージ | サイズだけを残します |
| close の理由 | エラーの文と同じようにマスクします |

1 つのソケットにつき、最初の 5 件と新しい順に 100 件のメッセージを保持します。メッセージを渡すのは、`list_ws_messages`（と `reqcove har`）だけです。

確認状況：テストと、本物のソケットを使った E2E テスト。

## 渡さないボディ

- ボディを渡したり検索したりするのは、マスクがそのボディを見られたときだけです。条件は 2 つで、デコードされていること（元に戻せなかったエンコーディングのままのバイト列ではないこと）と、テキストであることです。
- テキストかどうかはContent-Type で判断します（JSON、XML、フォーム、テキストなど。`application/x-amz-json-1.1` のように `json` を名前に含む別の種類と、Sentry のエンベロープは、制御文字がないときだけ）。Content-Type がなければ、バイト列で判断します。
- それ以外のボディは、マスクが有効な間、渡しも検索もしません。たまたま有効な UTF-8 である protobuf も同じです。`--no-redact` を付けると返します。Content-Type が protobuf のボディは例外で、[描画したもの](#protobuf-と-grpc)を渡します。
- ボディを返すのは、ツールがボディを求められたとき（`get_flow` と `search_flows` の `bodies`）と、ボディを比べる `diff_flows` だけです。`diff_flows` が返すのは、違っている値とキーで、300 バイトに切ります。テキストでないボディについては、マスクが有効な間は何も返しません。
- メールアドレスや名前などの個人データは、マスクしません。デバッグに必要だからです。

## あなた自身の規則（`--mask-names`、`--mask-values`）

どちらも起動時に固定します。`--no-redact` のときは何もしません（`run` が警告します）。

| フラグ | 足すもの | 制限 |
|---|---|---|
| `--mask-names` | シークレットとして扱う名前。名前で判断するすべての場所で働き、組み込みの例外（OpenTelemetry の `key`、チャレンジを残す `WWW-Authenticate`、Cookie の属性）より先に当てます | 一致するのは名前全体だけです。表記の違いは問いません。`clientRef` は `client_ref` と `Client-Ref` に一致し、`X-Client-Ref` には一致しません |
| `--mask-values` | RE2 のパターン。一致した部分を、どこにあってもマスクします。どの名前のヘッダーでも（User-Agent の `key=…` も）、URL でも、ボディでも、エラーの文でも同じです | パターンは 32 個まで、それぞれ 512 バイトまでです。空の文字列に一致するパターンは使えません。エラーは、パターンを番号で示し、中身は示しません |

- `capture_stats` は、名前ごと、パターンの番号ごとに一致の数を数えます（1 つの値を 2 回以上数えることがあります）。
- コマンドラインに書いたパターンは `ps` で見えます。シークレットそのものを書くときは `@FILE` に入れてください。`\Q…\E` で囲むと、`+`、`/`、`.` がその文字そのものに一致します。

確認状況：テスト。

## 記録が保持するもの

| 対象 | 上限 |
|---|---|
| フロー | 10,000 件まで。メモリにあり、`reqcove run` が止まると消えます。Reqcove 自身はフローをディスクに書きません |
| すべての記録を合わせたテキスト。ボディの先頭部分、ヘッダー、URL、そのほかのテキストです | 64 MiB まで |
| ボディ | 先頭の 64 KiB |
| WebSocket のテキストのメッセージ | 先頭の 4 KiB。ソケットごとに、最初の 5 件と新しい順に 100 件 |
| サイトの理由の文、`Content-Encoding`、エラーメッセージ | それぞれ 1 KiB、64 バイト、1 KiB に切ります |
| 一覧と要約に出す User-Agent、ALPN の名前、`diff_flows` の JSON のキーのうち単純な名前でないもの | 256 バイトに切る、印字できる ASCII だけにする、引用符で囲む（`$["a.b"]`） |
| マーカー（`reqcove mark`、`add_marker`） | 記録と一緒にメモリにあります。1 行で 80 文字までで、超えると断ります。エラーの文と同じようにマスクします。source ごとに 100 件までで、ログには出しません（コードから判断したものです） |
| Host がホスト名でもアドレスでもないリクエスト | 中継しますが、記録しません |

確認状況：テスト（そうした Host のリクエストを記録しないこと。マーカーのマスクと、断る場合）。

## 中身なしで記録する接続

次の 2 種類の接続は接続の記録だけを残します。運んだ中身は残しません。

### `--pass-hosts` のホスト

許可したホストのうち、アプリが Reqcove の証明書を拒否するホストは、復号せずに通します。記録するのは接続だけです。

| `--pass-hosts` | 結果 |
|---|---|
| 記録するもの | クライアントが指定したホスト（SNI）、サーバーのアドレス、開始と終了、それぞれの向きのバイト数、提示されたプロトコル。TLS の中のものは保持せず、見ることもしません |
| 範囲 | 記録は `--allow-hosts` ともう一度照合します。そこにないホストは何も残しません |
| バイト数 | 接続全体のものです。その接続に相乗りした別のホストへのリクエストも、見えないまま数に入ります（コードから判断したものです） |
| pass host への TLS の接続 | `--rules` も `--upstream-proxy` も通らず、サーバーへ直接進みます |
| pass host への平文の HTTP と、別のホストの復号された接続に相乗りした pass host へのリクエスト（HTTP/2） | これらは復号されます。範囲外として数え、記録はしません。`--upstream-proxy` があれば、そこを通して送ります。検証は上流プロキシを通すほかの HTTPS と同じです（`--upstream-ca` だけと照合します。なければ公開の CA と照合します）。`--rules` は通りません（コードから判断したものです） |
| Apple の一覧にある pass host | mitmproxy が自分で素通しするので、記録は残りません。`run` が警告します |
| `reqcove status` が `--pass-hosts` 用に勧めるホスト | スマートフォンの TLS から来たものです（SNI。アプリが自由に選べます）。勧めるのはホスト名と IPv4 アドレスだけです（ホストを示さないクライアントは、接続先のアドレスで素通しします）。mitm.it は勧めません。コマンドはシェル用に引用符で囲みます |
| `@FILE` の一覧 | ホストとして読むだけで、実行しません。ホストでない行があると `run` が止まります。その行は行番号だけで示すので、誤ったファイル（たとえば .env）の中身を表示することはありません |

確認状況：テスト（pass host の復号されたリクエストが `--upstream-proxy` を通ること。Apple の一覧にある pass host。勧めるホスト。`@FILE` の行）。

### raw TCP

許可したホストへの接続のうち、mitmproxy が HTTP として読まずに raw TCP として運ぶものには、中身についてのフローがありません。記録するのは接続だけで、`list_passthrough` に `reason: raw_tcp` として出ます。

| raw TCP | 結果 |
|---|---|
| mitmproxy が知らない ALPN の名前（TLS では復号したあと） | raw TCP にするのは、サーバーが先に送信するときと、クライアントのバイト列が HTTP に見えないときだけです。それ以外は HTTP/1 として読みます。別のプロトコルを使うクライアントでは、これは失敗します |
| HTTP に見えないバイト列 | raw TCP にします |
| WebSocket 以外の `101` でリクエストが切り替わった先 | raw TCP にします。リクエスト自体はフローになります |
| 記録するもの | クライアントが指定したホスト（SNI。平文の HTTP の `101` のあとはリクエストのホスト。どちらもなければアドレス）、サーバーのアドレス、開始と終了、クライアントが提示したプロトコルと選ばれたプロトコル、それぞれの向きに中継したバイト数（TLS では TLS の中のバイト数）。バイト列そのものは記録しません |
| 範囲 | 記録は `--allow-hosts` と `--pass-hosts` ともう一度照合します。`--allow-hosts` にないホストと、`--pass-hosts` にあるホストは何も残しません |

確認状況：平文の HTTP での E2E テスト（`101` と、記録するもの）。テスト（範囲の照合）。知らない ALPN の名前と、TLS での `101` は、2026-11-15 に mitmproxy 12.3.1 で試しました。iPhone では試していません。

## 記録が残らない接続

次のものは、記録されず、数えられもしません。mitmproxy が自分で素通しする接続は、mitmproxy のフックを 1 つも呼びません（mitmproxy 12.3.1 のコードから判断したものです）。

| 接続 | 起きること | 確かめ方 |
|---|---|---|
| Apple のホストと、`--allow-hosts` にないホスト | mitmproxy が素通しします | コードから判断したもの |
| mitmproxy がアドレスでしか知らない接続 | 素通しします。`--allow-hosts` にそのアドレスを書いたときは別です | コードから判断したもの |
| SNI のない TLS | アドレスでしか分かりません。Remote Proxy、LAN モード、ローカルプロキシでも同じです。`CONNECT` の名前は mitmproxy に届かないからです | コードから判断したもの |
| 平文の TCP（80 番と 443 番ポートは mitmproxy に行きます）のうち、最初のバイト列が、mitmproxy の読み方では許可したホストを示さないもの。HTTP でないもの、サーバーが先に送信するもの、TLS なしの HTTP/2（事前の了解による h2c。mitmproxy 12.3.1 は受け付けません）、`Host` のない HTTP/1.0、コロンのあとに空白のない `Host:` | アドレスでしか分かりません | 2026-11-15 に mitmproxy 12.3.1 で試しました。iPhone では試していません |
| 許可したホストへの HTTP/2 のリクエストのうち、クライアントが一覧にない名前のために開いた接続に相乗りしたもの。その名前は証明書とアドレスを許可したホストと共有しています | その接続と一緒に、復号されずに進みます。URLSession は接続をこのように使い回します（HTTP/2 の connection coalescing。Apple の WWDC 2020 のセッション「Boost performance and security with modern networking」によります）。CDN は兄弟のホストに 1 つの証明書を与えます。そのため、アプリが先に兄弟のホストに届いていると、許可したホストへのリクエストが抜けることがあります。証明書を共有する名前をまとめて許可してください（`*.example.com`） | 2026-11-15 に Go の HTTP/2 クライアントで試しました。iPhone では試していません |
| Encrypted Client Hello を使う TLS | mitmproxy に見えるのは、プロバイダーの公開名だけです。その名前を許可していなければ、接続は素通しされます。公開されている情報によると、iOS はデフォルトでは ECH を使いません。ただし、アプリは自分の接続で ECH を有効にできます | 2026-11-15 に Go の ECH のクライアントとサーバーで試しました。iPhone では試していません |
| 許可したホスト（SNI）への HTTP/1 の接続のうち、最初のリクエストが `Host` で Apple のホストを指定したもの | 接続全体が、あとのリクエストも含めて、復号されたまま中継されます。mitmproxy が、TLS のあとで名前をもう一度確かめるからです | 2026-11-15 に mitmproxy 12.3.1 で試しました。iPhone では試していません |
| `--allow-hosts` にアドレスがあり、SNI に名前がある接続 | 接続はアドレスによって復号されます。その HTTP のリクエストは、範囲外として数えます。mitmproxy がそのあと raw TCP として運ぶ接続は、名前で照合されるので、何も残しません | 2026-11-15 に mitmproxy 12.3.1 で試しました。iPhone では試していません |
| TLS のハンドシェイクを終えたあとで mitmproxy の証明書を拒否して閉じるクライアント | TLS の失敗も、フローも、数も残りません。mitmproxy から見ると、ハンドシェイクは成功しているからです | 2026-11-15 に、OpenSSL 4.1 の curl で試しました（TLS 1.2 と 1.3） |
| ハンドシェイクを終えて、リクエストを送らずに閉じるクライアント | 同じです | E2E テスト |
| ハンドシェイクを最後まで進め、証明書を自分で確かめてから閉じる iPhone のアプリ | 上と同じく、何も残しません | 2026-11-15 に iPhone で試しました |

ハンドシェイクの途中で拒否するクライアントは、ここには入りません。TLS の失敗として一覧に出ます（`list_tls_failures`）。

| TLS の失敗として一覧に出るもの | 確かめ方 |
|---|---|
| ハンドシェイクの途中で拒否する Python と Go のクライアント | TLS 1.2 と 1.3 で試しました。Go のクライアントは E2E テストです |
| URLSession のデリゲートか Network.framework の verify block で拒否してピンニングする iPhone のアプリ | 2026-11-15 に iPhone で試しました |
